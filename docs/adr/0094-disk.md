# ADR-0094: Диск — папки и файлы пространства, доступ, публичные ссылки, корзина, место (2026-10-14)

## Контекст
Владелец, 14.10: «раздел как Google Drive / Яндекс Диск: папки, загрузка файлов, доступ к папкам и файлам как в других местах, файл публичным по ссылке; история; понятная индикация свободного места — в ней показываем и занятое файлами вне диска — и порог тарифа; сразу закладываем докупку места пакетами +10 / +100 / +500 ГБ / +1 ТБ допом к подписке; корзина — удалённое попадает в неё, срок автоудаления настраивается (по умолчанию никогда), есть «очистить корзину»; всё с учётом прав; вид — плитки и список».

Что уже есть и переиспользуется:
- одна таблица `files` и blob-хранилище (`internal/blob`, ADR-0011); сервер сам отдаёт байты (`GET /api/files/{id}`, Range); квота пространства — `workspaces.storage_used_bytes` / `storage_quota_bytes`, предел = `min(quota, plan.storage_mb)` (ADR-0024), `ReserveQuota`/`ReleaseQuota`, `413 FILE_QUOTA_EXCEEDED`; «файлы» уже лимит тарифа (ADR-0086);
- сборщик сирот `files.CleanupOrphans` (24 ч, перечисляет все ссылающиеся таблицы в `ListOrphanFiles`);
- права досок: `board_permissions(target_type, target_id, allow, deny)`, `ComputeBoard` в Go и TS, общие векторы `proto/testdata/permissions.json`, приватная доска = роли не дают `VIEW_BOARD`;
- журнал `task_activity(kind, before, after)` с таймлайном (ADR-0091);
- публичные коды форм досок (`board_forms.code`, 32 случайных байта base64url, анонимный маршрут `/api/public/…` с лимитами Redis);
- биллинг: предоплаченный баланс, **суточные** списания по SKU (`billing_prices.sku`, `billing_charges`; ADR-0080 §14 — «каталог растёт по SKU, будущие add-on»); подписок у провайдеров нет (§11.1).

## Решение

### 1. Модель
Диск — раздел **пространства** (как «Доски»): один корень на пространство, в нём папки и файлы.
- `disk_items(id uuidv7, workspace_id, parent_id NULL=корень, kind folder|file, name, file_id → files NULL для папок, owner_id, restricted bool, created_at, updated_at, trashed_at NULL, trashed_by, trashed_root bool)`.
  - `UNIQUE(workspace_id, parent_id, lower(name)) WHERE trashed_at IS NULL` — внутри папки имена уникальны без учёта регистра; загрузка с занятым именем получает суффикс «(2)», как в Finder. Версий файлов в v1 нет (загрузка не заменяет файл; ниже «Отложено»).
  - Файл диска — обычная строка `files` (workspace_id = пространство), `disk_items.file_id` — ещё одна ссылка; `ListOrphanFiles` и `UnattachedBytesByUploader` учитывают `disk_items`.
  - Глубина ≤ 32, перемещение проверяет циклы; `path` не храним — вычисляем рекурсивным CTE по `parent_id` (пространства небольшие, крошки нужны только для открытой папки).
- `workspaces.disk_trash_days int NULL` — срок автоудаления из корзины, `NULL` = никогда (по умолчанию). Меняет держатель `DISK_MANAGE` в настройках пространства → «Диск».
- `workspace_storage_addons(id, workspace_id, size_mb, sku, active bool, created_at, ended_at)` — купленные пакеты места; **эффективный лимит** = `min(storage_quota_bytes, plan.storage_mb + Σ active size_mb)`. В v1 таблица и расчёт есть, покупки нет (§6).

### 2. Права
Три бита уровня пространства (по образцу биллинга — константы вне enum, uint64):
- `1 << 35 DISK_VIEW` — видеть раздел и всё не-restricted; у роли «участник» по умолчанию (миграция выдаёт существующим ролям участника);
- `1 << 36 DISK_WRITE` — создавать папки, загружать, переименовывать/перемещать/удалять в корзину **своё**; по умолчанию у участника;
- `1 << 37 DISK_MANAGE` — любой элемент, настройка срока корзины, очистка всей корзины, снятие чужих публичных ссылок; входит в `ADMINISTRATOR` (в отличие от биллинга).
Гости и боты: 0, кроме явного доступа к элементу (ниже). Бит `ATTACH_FILES` на диск не влияет.

Доступ к элементу — `ComputeDiskItem` в Go (`internal/perm/disk.go`) и TS (`diskPermissions`), общие векторы в `proto/testdata/permissions.json`:
1. база — биты ролей пространства, затем `disk_permissions(item_id, target_type role|user, target_id, allow, deny)` **ближайшего предка с переопределениями и самого элемента** (как override комнаты: сначала роли по position, затем личный);
2. `restricted` папка/файл (переключатель «Только выбранные», как приватная доска): роли теряют `DISK_VIEW`/`DISK_WRITE`, остаётся владелец элемента, `DISK_MANAGE` (admin обходит, как у досок — исключение ADR-0078 не повторяем) и те, кому выдан `allow`;
3. дочерний элемент наследует результат родителя; `restricted` у потомка сужает заново;
4. владелец элемента всегда имеет `DISK_WRITE` на него (переименовать, переместить в доступную папку, удалить в корзину, поделиться);
5. нет `DISK_VIEW` на элемент → **404**, не 403 (не раскрываем имя).
Доступ выдаётся в диалоге «Доступ» (ролям и людям: «Просмотр» = `DISK_VIEW`, «Правка» = `DISK_VIEW|DISK_WRITE`), выдавать может владелец элемента или `DISK_MANAGE`; гостю выдать можно только явно по человеку.

**Дополнение (2026-10-14): боты — как участники.** Владелец, 14.10: «боты могут с диском и вики общаться — должны иметь возможность всё там менять, добавлять и т. д., как пользователь может». Правило «боты: 0» снято: бот — участник с ролью `member` (ADR-0031), биты диска получает от своих ролей и переопределений элементов ровно как человек (`perm.DiskOf`/`ComputeTree` без признака бота, TS — без `bot`). Все маршруты Диска (кроме публичных — они анонимны) открыты бот-токену в таблице `botroutes.go`: список, папки, загрузка, переименование/перенос, доступ и ссылка (владелец или `DISK_MANAGE`), корзина, история, настройки (`DISK_MANAGE`). SDK — `client.disk` (`packages/bot-sdk`). Гости — без изменений.

### 3. Публичная ссылка
- `disk_links(item_id UNIQUE, code text UNIQUE CHECK(length=43), created_by, created_at, expires_at NULL, revoked_at NULL, downloads int)`.
- Только для **файлов** в v1 (папки — отложено). Включает владелец файла или `DISK_MANAGE`; выключение — там же; `DISK_MANAGE` видит все ссылки пространства.
- Анонимно: `GET /api/public/disk/{code}` — JSON-мета, `GET /api/public/disk/{code}/content` — байты (Range), лимиты Redis как у форм (`FormReadLimit`/`FormIPLimit` → свои `DiskLinkLimit`), `X-Robots-Tag: noindex`. Файл в корзине или restricted — ссылка работает, пока не снята (как в Google Drive); удалённый навсегда — 404.
- Страница ссылки на вебе: имя, размер, превью картинки/видео, кнопка «Скачать»; без входа.

### 4. Корзина
- «Удалить» → `trashed_at = now(), trashed_by`, у корня удаления `trashed_root = true`; потомки получают `trashed_at` той же меткой (одним UPDATE по CTE). В корзине показываются только `trashed_root` (как в Google Drive), восстановление возвращает поддерево; если родитель тоже в корзине/удалён — в корень.
- Место в корзине **считается** в квоте (как у всех), индикатор показывает долю отдельно и даёт «Очистить корзину».
- Вижу в корзине то, что могу видеть; «Очистить корзину» удаляет навсегда всё, что держатель вправе удалить (владелец — своё, `DISK_MANAGE` — всё). Удаление навсегда: `DELETE disk_items` → файл становится сиротой → `CleanupOrphans` (24 ч) освобождает байты; **квота освобождается сразу** (`ReleaseQuota` в той же транзакции, как при удалении сообщения).
- Воркер `disk.TrashSweep` раз в час: `trashed_at < now() − disk_trash_days` → удалить навсегда; advisory lock, `SKIP LOCKED` не нужен — пакетами по пространствам.

### 5. История
`disk_activity(id uuidv7, workspace_id, item_id, actor_id SET NULL, kind, before jsonb, after jsonb, created_at)` по образцу `task_activity`. Виды: `create`, `upload`, `rename`, `move`, `share` (изменение `disk_permissions`/restricted), `link_on`/`link_off`, `trash`, `restore`, `delete`. Снимки имён в `before/after` (имя папки назначения, кто получил доступ). Показ: «История» элемента (панель, свежее сверху, курсор по id, `GET /api/disk/items/{id}/activity`) и «История диска» пространства для `DISK_MANAGE` (`GET /api/workspaces/{id}/disk/activity`, фильтр по человеку). Склейка повторов за 5 мин (ADR-0081) — только `rename`.

### 6. Место и пакеты
- `GET /api/workspaces/{id}/disk/usage` → `DiskUsage{quota_bytes, plan_bytes, addon_bytes, used_bytes, disk_bytes, trash_bytes, other_bytes}`: `other_bytes` = вложения чата/досок/стикеры и т. д. (`used − disk`), `disk_bytes` включает корзину, `trash_bytes` — её часть. Считается одним запросом по `files ⋈ disk_items` (с индексом по `workspace_id`); кэш в Redis 30 с, сбрасывается при изменении `storage_used_bytes` не нужен — панель запрашивает при открытии и по `WORKSPACE_UPDATE`.
- Индикатор (в шапке диска и в «Тариф»): полоса с тремя сегментами (диск / корзина / вне диска), подпись «12,4 ГБ из 300 ГБ · тариф Team», при ≥ 90 % — предупреждение; `413` при загрузке показывает ту же полосу и «Докупить место».
- **Пакеты места** (+10 / +100 / +500 ГБ / +1 ТБ) — SKU `storage.10gb.day`, `storage.100gb.day`, `storage.500gb.day`, `storage.1tb.day` в `billing_prices` (цена за сутки, в UI — за месяц × 30), списываются суточно с баланса вместе с местами (`billing_charges.plan` становится NULL-able), покупка — `BILLING_MANAGE`, отключение — с конца оплаченных суток; при выключении пакета, когда использование выше нового предела, — отказ `PLAN_LIMITS_EXCEEDED` (ADR-0086). В v1: таблица `workspace_storage_addons`, эффективный лимит, кнопка «Докупить место» ведёт в «Тариф» и показывает пакеты с ценами, **кнопки покупки заблокированы, пока платежи выключены** (ADR-0080 §0). Реализация списаний — отдельная задача после включения платежей.

### 7. Протокол и маршруты
`proto/calaba/v1/disk.proto`: `DiskItem{id, workspace_id, parent_id, kind, name, file (FileMeta), owner_id, restricted, shared bool (есть переопределения), link (DiskLink), trashed_at, created_at, updated_at, my_bits}`, `DiskLink{code, expires_at, created_by}`, `DiskUsage`, `DiskActivity`, запросы/ответы. REST (все под `private`, права на сервере):
- `GET /api/workspaces/{id}/disk/items?parent=&trashed=&cursor=&sort=` — содержимое папки (или корзины), только видимое;
- `POST …/disk/folders`, `POST …/disk/upload?parent=` (через `files.UploadInto`, квота, ≤ лимит размера из `files`), `PATCH /api/disk/items/{id}` (rename/move/restricted), `POST …/trash`, `POST …/restore`, `DELETE /api/disk/items/{id}` (навсегда), `POST …/disk/trash/empty`;
- `GET/PUT /api/disk/items/{id}/permissions`, `POST/DELETE /api/disk/items/{id}/link`;
- `GET …/disk/usage`, `GET …/disk/activity`, `GET /api/disk/items/{id}/activity`, `GET /api/disk/items/{id}/path`.
События gateway: `DISK_ITEM_UPSERT = 98` / `DISK_ITEM_REMOVE = 99` (`workspace_id, item_id, parent_id`), фильтр по получателю как у досок (`internal/gateway/boards.go`): без `DISK_VIEW` на элемент событие не уходит; клиент перечитывает открытую папку и корзину. Скачивание — существующий `GET /api/files/{id}`, `files.CanRead` получает ветку «файл диска → `ComputeDiskItem` ≥ VIEW».

### 8. Интерфейс
- **Десктоп**: раздел «Диск» на рейле (ADR-0074) после «Досок», иконка — папка/облако из `assets/nav/icons`. Экран: шапка (`Bar`: крошки пути · поиск по диску · переключатель «Плитки | Список» (`Segmented`, запоминается в `prefs`) · сортировка · «+» (Папка / Загрузить) ) · область с drag&drop файлов из системы · слева/внизу индикатор места. Плитки 160 px с превью (`thumbnail`) или иконкой типа; список — имя, владелец, изменён, размер. Контекстное меню элемента: Открыть, Скачать, Переименовать, Переместить ▸, Доступ…, Ссылка (вкл/выкл, копировать), История, В корзину. Корзина — пункт слева/в крошках с «Очистить» и «Восстановить». Перетаскивание элементов между папками мышью; на телефоне — через «Переместить ▸».
- **Телефон** (ADR-0095): корневой экран «Диск» (из «Ещё» или закреплённый), папки — вложенные экраны стеком, те же плитки/список, «⋯» → меню элемента (карточка по центру, ADR-0073 §8), загрузка — системный пикер файлов; корзина и место — пункты «⋯» шапки.
- Превью/открытие: картинки и видео — существующий `Lightbox`/`MediaPlayer`, остальное — скачивание (на десктопе через ADR-0068-подобный путь сохранения, на телефоне — ссылка).
- Все списки — строки/плитки в `memo`, селекторы по id (CLAUDE.md «Ререндеры»); скрытый раздел не держит подписок.

## Последствия
- Протокол, права и миграции — Opus и второе ревью (CLAUDE.md §9).
- Индекс `files(workspace_id)` нужен для `DiskUsage` — добавить в той же миграции, если нет.
- `CleanupOrphans` и `UnattachedBytesByUploader` обязаны учитывать `disk_items`, иначе сборщик удалит файлы диска через сутки — покрыть тестом.
- `docs/04-data-model.md` (биты 35–37, `disk_*` таблицы), `docs/08-design.md` («Диск»), `docs/09` — пункты бэклога из §«Отложено».
- Телефонная навигация меняется (ADR-0095).

## Отложено (не v1)
- Версии файлов (загрузка поверх с историей версий) и восстановление версии.
- Публичная ссылка на папку, ссылка с паролем, запрет скачивания.
- Личный диск («Мои файлы» вне пространства) и перенос вложений чата в папку.
- Покупка пакетов (списания) — после включения платежей; офлайн-доступ и синхронизация папки на диск компьютера.

## Альтернативы
- **Папки как строки `files`** (колонки `parent_id`/`kind` в `files`): смешивает вложения чата и дерево, ломает `ListOrphanFiles`; отклонено.
- **Отдельный blob-бакет диска с presigned URL**: другой путь выдачи байтов, двойные правила `CanRead`; текущая отдача сервером с Range достаточна, presigned — отдельный ADR, если упрёмся в трафик.
- **Корзина как отдельная таблица**: восстановление требует копирования поддерева; флаг `trashed_at` проще и даёт частичные индексы.
- **Пакеты места как подписка Stripe**: второй планировщик, запрещён ADR-0080 §11.1; суточный SKU на балансе — единый путь с местами.
