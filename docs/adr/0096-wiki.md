# ADR-0096: Вики — страницы пространства с WYSIWYG, совместным редактированием, доступом и публикацией (2026-10-14)

## Контекст
Владелец, 14.10: «раздел а-ля wiki, где есть WYSIWYG, чтобы удобный был; разделы всякие, всё по доступам; делиться можно; правки — коллаборация, условно как Notion».

Что есть: ни одного документного редактора (чат, задачи, заметки — `textarea` + markdown-lite `lib/markdown/parse.ts`; почта — `contenteditable` + DOMPurify); нет Yjs/Tiptap; WS-шлюз — protobuf-события без `bytes`, лимит входящего кадра 64 КиБ, 50 кадров/с, эфемерный путь только для typing (`encEvent.ephemeral()`), буфер переподключения 1000 кадров; Redis pub/sub `ws:<wsId>`/`user:<id>`. Дерево с правами, корзиной, публичной ссылкой и журналом уже есть у Диска ([ADR-0094](0094-disk.md)): `disk_items`, `ComputeDiskItem`, `disk_links`, `disk_activity`, `TrashSweep`. Поиск — ADR-0062 (GIN-индексы по выражению, `SearchType`).

## Решение

### 1. Модель
Вики — раздел **пространства** (как Диск): дерево страниц, страница внутри страницы (Notion).
- `wiki_pages(id uuidv7, workspace_id, parent_id NULL=корень, title text ≤ 200, icon text (эмодзи) NULL, cover_file_id NULL, position int, owner_id, restricted bool, plain_text text, preview text ≤ 200, doc_size int, updated_by, created_at, updated_at, trashed_at, trashed_by, trashed_root)`. Глубина ≤ 32, порядок — `position` среди соседей (перетаскивание в дереве), цикл при переносе проверяется.
- `wiki_page_updates(page_id, seq bigserial, update bytea ≤ 64 КиБ, author_id, created_at)` — журнал Yjs-обновлений после последнего снимка.
- `wiki_page_snapshots(page_id PRIMARY KEY, state bytea ≤ 2 МиБ, through_seq, saved_by, saved_at)` — текущий снимок (`Y.encodeStateAsUpdate`).
- `wiki_page_versions(id uuidv7, page_id, state bytea, plain_text, title, authors uuid[], created_at)` — история версий: не чаще раза в 5 минут на страницу, только если `plain_text`/заголовок изменились; хранится ≤ 200 версий на страницу (старые — прореживаются до одной в день).
- `wiki_permissions`, `wiki_links`, `wiki_activity`, `wiki_page_files(page_id, file_id)` — ровно по образцу `disk_*`; `wiki_page_files` держит картинки/вложения страницы в квоте пространства («вне диска» в индикаторе) и вне сборщика сирот.
- `workspaces.wiki_trash_days int NULL` (никогда по умолчанию), тот же `TrashSweep`.

### 2. Права
Биты `1 << 38 WIKI_VIEW`, `1 << 39 WIKI_WRITE`, `1 << 40 WIKI_MANAGE` — семантика и дефолты как у Диска (участник: VIEW|WRITE; ADMINISTRATOR включает; гости/боты — только явно по странице). **Один общий расчёт дерева**: `ComputeDiskItem` обобщается в `perm.ComputeTree(kind, …)` (Go) / `treeItemPermissions` (TS), Диск и Вики — два набора битов над одним алгоритмом (цепочка предков с переопределениями, `restricted`, владелец, 404 без VIEW). Общие векторы — `proto/testdata/permissions.json`. В отличие от Диска, **`WRITE` на страницу даёт править её содержимое любому, у кого он есть** (страница — общий документ, а не чужой файл); структура (переименовать/перенести/в корзину/доступ) — владелец страницы или `WIKI_MANAGE`, плюс все с `WRITE` могут создавать подстраницы.

**Дополнение (2026-10-14): боты — как участники.** Решение владельца 14.10 (см. ADR-0094 §2, дополнение): бот получает `WIKI_*` от своих ролей и переопределений страниц, как человек; все REST-маршруты вики открыты бот-токену, сокет `/sync` принимает бот-токен первым текстовым кадром с теми же проверками (`WIKI_VIEW` — чтение, `WIKI_WRITE` — приём правок; перепроверка — повторной аутентификацией токена, у бота нет строки сессии). SDK — `client.wiki` (`packages/bot-sdk`): Markdown ↔ документ через общий пакет `packages/wiki-doc` (§4). Гости — без изменений.

### 3. Редактор
Tiptap (ProseMirror) — новая зависимость рендерера, грузится отдельным чанком только в разделе «Вики» и на публичной странице. Набор v1: заголовки H1–H3, абзац, списки (маркированный, нумерованный, чек-лист), цитата, разделитель, код (Prism-подсветка через существующий `syntax.ts`), таблица, картинка (загрузка через `files`, вставка/перетаскивание/paste → `wiki_page_files`), ссылка, упоминание `@человек` (из `MentionPopover`-данных; уведомлений v1 нет), callout, toggle (сворачиваемый блок), выделение (жирный/курсив/зачёркнутый/код/цвет). `/`-меню блоков и всплывающая панель форматирования при выделении, markdown-шорткаты (`#`, `-`, `1.`, `[]`, `>`, ```). Вставка markdown-текста конвертируется. Экспорт страницы в Markdown — пункт меню (простой сериализатор).
Картинки никогда не инлайнятся в документ — только `file_id`; лимит страницы 2 МиБ Yjs-состояния (сервер отклоняет снимок больше, клиент предупреждает).

### 4. Совместное редактирование
CRDT **Yjs** + `y-prosemirror`; курсоры и имена соавторов (awareness). **Сервер — ретранслятор и хранилище, Yjs не исполняет** (нет зрелой Go-реализации; все слияния — на клиентах, где они и так происходят).
- Отдельный WebSocket `GET /api/wiki/pages/{id}/sync` (тот же `coder/websocket`, auth как у шлюза, требует `WIKI_VIEW`; без `WRITE` — только приём). Не через основной шлюз: обновления не должны попадать в буфер переподключения и под его лимиты, а бинарные кадры не нуждаются в protobuf.
- Протокол (бинарные кадры, первый байт — тип): `0 SNAPSHOT{through_seq, state}` и `1 UPDATE{seq, update}` от сервера при подключении (снимок + все обновления после него; Yjs идемпотентен, state-vector-диф не нужен), затем `1 UPDATE` в обе стороны (сервер присваивает `seq`, пишет в `wiki_page_updates`, публикует в Redis `wiki:<pageId>`, все подключённые к странице получают); `2 AWARENESS` — эфемерно, не хранится, троттлинг 10/с на соединение; `3 COMPACT_REQUEST` — сервер просит снимок, когда обновлений после снимка > 500 или их суммарный размер > 1 МиБ; `4 SNAPSHOT_POST{through_seq, state, plain_text, title, preview}` — клиент с полным документом присылает снимок; сервер проверяет `through_seq ≥` текущего, сохраняет, удаляет обновления `≤ through_seq`, обновляет `wiki_pages.plain_text/preview/doc_size/updated_at` и при условиях §1 пишет версию. Кроме запроса сервера, клиент сам присылает снимок через 3 с бездействия после своих правок и при закрытии страницы.
- Лимиты: кадр ≤ 64 КиБ (большее обновление клиент дробит — Yjs позволяет слать по транзакциям), ≤ 20 обновлений/с на соединение (сверх — закрытие 4008), ≤ 10 соединений на страницу на человека.
- Клиент: обновления батчатся 200 мс; при скрытом окне awareness не шлётся; страница монтирует один редактор; не на экране — провайдер отключён (никаких фоновых сокетов на все страницы).
- Доверие: снимок присылает любой с `WRITE` — то же доверие, что к правкам; защита от порчи — история версий и восстановление (§5).
- Офлайн не делаем (Electron-клиент всегда онлайн); при разрыве провайдер переподключается и получает снимок+обновления заново.

### 5. История версий и журнал
- «История» страницы: список версий (кто, когда, превью диффа текста через существующий `lib/textDiff.ts`), «Восстановить» — клиент загружает `state` версии и применяет содержимое как новую транзакцию в живой документ (история остаётся линейной, соавторы видят восстановление как правку).
- `wiki_activity`: `create`, `rename`, `move`, `share`, `link_on/off`, `trash`, `restore`, `delete`, `icon`, `cover`, `version` (снимок версии). Правки текста в журнал не пишутся — их держат версии.

### 6. Публикация и доступ
- Диалог «Доступ» — тот же компонент, что у Диска (роли/люди, Просмотр/Правка, «Только выбранные»).
- Публичная ссылка: `wiki_links(page_id, code, include_children bool, expires_at, revoked_at, views)`; веб-маршрут `/w/{code}` (как `FormPublicPage`): читаемая страница с заголовком, иконкой, обложкой, при `include_children` — боковое оглавление подстраниц (только тех, что не `restricted`); рендер тем же Tiptap в режиме чтения; картинки — по публичному маршруту `GET /api/public/wiki/{code}/files/{fileId}` (только файлы из `wiki_page_files` этой ветки); лимиты и заголовки как у публичных файлов Диска; `noindex` по умолчанию, переключатель «Разрешить индексацию» — v2.

### 7. Поиск, уведомления, телефон
- `SearchType.WIKI`: GIN по `to_tsvector('russian'|'simple', title || plain_text)` + `pg_trgm` по `title`; фильтр доступа — `ComputeTree`; сниппет — `ts_headline`.
- `@упоминание` на странице уведомляет упомянутого (`WikiMention` в задачных уведомлениях — v2; v1 без уведомлений).
- Телефон: раздел «Вики» в «Ещё» (ADR-0095); дерево — экраны стеком (страница → подстраницы списком внизу), чтение и правка тем же редактором с упрощённой панелью (жирный/курсив/список/чек-лист/заголовок, «+» блок); `/`-меню — карточка по центру. Курсоры соавторов на телефоне не показываем (только счётчик «ещё 2 редактируют»).

### 8. Протокол и маршруты
`proto/calaba/v1/wiki.proto`: `WikiPage{id, workspace_id, parent_id, title, icon, cover (FileMeta), owner_id, restricted, shared, link, preview, updated_at, updated_by, trashed_at, my_bits, has_children}`, `WikiVersion`, `WikiActivity`, `WikiLink`, запросы/ответы. REST: `GET /api/workspaces/{id}/wiki/pages?parent=&trashed=` (дерево верхнего уровня, дети лениво), `POST …/wiki/pages`, `PATCH /api/wiki/pages/{id}` (title/icon/cover/parent/position/restricted), `…/trash`, `…/restore`, `DELETE`, `POST …/wiki/trash/empty`, `GET/PUT …/permissions`, `POST/DELETE …/link`, `GET …/versions`, `GET …/versions/{vid}` (state), `GET …/activity`, `POST /api/wiki/pages/{id}/files` (загрузка картинки), `GET …/export.md`, `GET/PUT …/wiki/settings`. События шлюза `WIKI_PAGE_UPSERT = 100` / `WIKI_PAGE_REMOVE = 101` (структура дерева, с фильтром по получателю как у Диска); содержимое — только через `/sync`.

### 9. Интерфейс
- Десктоп: раздел «Вики» на рейле (после «Диска»); слева колонка-дерево (сворачиваемые узлы, перетаскивание, «+ страница», поиск по заголовкам, «Корзина»), справа страница: обложка, иконка, заголовок (H1, редактируется), «последнее изменение · соавторы (аватары онлайн)», тело; шапка `Bar`: крошки · «Поделиться» · «⋯» (История, Экспорт, Доступ, Переместить, В корзину). Плотность и типографика — как в docs/08 «Система»; ширина текста ≤ 760 px по центру.
- Все списки — `memo` + селекторы по id; редактор — единственный «тяжёлый» компонент, монтируется один; подсветка кода — в idle.

## Последствия
- Новые зависимости рендерера: `@tiptap/*`, `prosemirror-*`, `yjs`, `y-prosemirror`, `y-protocols` (только awareness-кодек). Бандл раздела лениво грузится.
- Протокол, права, `/sync`, публичные маршруты — Opus и второе ревью.
- Рефакторинг `ComputeDiskItem` → `ComputeTree` без изменения поведения Диска (векторы Диска остаются).
- docs/01 (новый компонент sync), 04, 05 (отдельный сокет), 08 («Вики», правила редактора), 16.
- Квота: файлы страниц — в `used_bytes`, в индикаторе Диска — «вне диска».

## Отложено (v2)
Комментарии к блокам, уведомления об упоминаниях, базы данных/таблицы-коллекции как в Notion, шаблоны страниц, встраивание задач/досок блоком, экспорт в PDF, индексация публичных страниц, офлайн-правки, гостевой доступ по ссылке с правкой.

## Альтернативы
- **Без CRDT: последний пишущий побеждает + «сейчас редактирует Х»** — проще, но это не «как Notion»; конфликты при двух редакторах неизбежны; отклонено.
- **Hocuspocus/y-websocket на Node рядом с Go** — ещё один процесс и язык в проде; ретранслятор на Go + компакция клиентом даёт то же без Yjs на сервере.
- **Обновления через основной шлюз** — буфер переподключения и лимиты кадров не рассчитаны на поток правок; `bytes` в `DispatchEvent` не нужен.
- **Markdown-редактор (textarea + предпросмотр)** — не WYSIWYG, владелец просил удобный; отклонено.
- **Lexical/Slate** — Yjs-привязки менее зрелые, чем `y-prosemirror`.
