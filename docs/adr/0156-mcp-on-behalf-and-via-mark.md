# ADR-0156: MCP от имени человека, задачи разработчика в MCP и пометка «через MCP» (2026-11-02)

**Статус: предложено.** Дополняет [ADR-0114](0114-mcp-endpoint-for-bots.md) (MCP только как бот) и опирается на
[ADR-0106](0106-bot-acts-as-owner.md) / [ADR-0111](0111-bot-acts-for-consenting-member.md) (от имени владельца /
участника). Переезд разработки GPTunneL с Linear: агент разработчика (Claude Code, Codex) должен вести задачи в
Calab так же, как в Linear MCP — от имени самого разработчика, с пометкой, что действие сделано агентом.

## Контекст
По ADR-0114 MCP работает только как сам бот: «от имени» на эндпоинте закрыто. Для команды это значит, что
задачи и комментарии агента пишутся от бота, а не от разработчика, и правило «взял задачу — назначь себя» не
выполнить: в MCP нет исполнителей, меток, приоритета, правки описания и списка своих задач. В REST всё это
есть, включая «от имени» по согласию. В Linear действие агента видно в истории: «Имя via MCP».

## Решение
1. **«От имени» через MCP.** `/api/mcp` принимает `Calab-On-Behalf` (`owner` или id участника) на тех же
   условиях, что любой REST-маршрут бота: переключатель владельца (ADR-0106) или согласие участника
   (ADR-0111), SSO-политика, активное участие. Обработчик пускает `Identity.Machine()` (бот или бот «от имени»),
   сессии людей — по-прежнему 403. Заголовок передаётся во внутренние вызовы инструментов, и каждый вызов
   заново проходит проверку «от имени» по таблице маршрутов (`onBehalfRoutes`): закрытое «от имени» в REST
   закрыто и через MCP. Своих проверок прав у MCP по-прежнему нет. В таблице маршрутов бота `/api/mcp`
   больше не `onBehalfClosed`.
2. **Канал запроса — пометка «через MCP».** Внутренний вызов инструмента получает в контексте канал
   `mcp` (`auth.WithChannel`; ставит только сервер, в процессе — заголовком или токеном его не подделать).
   Его сохраняют записи **собственного актора запроса**: `messages.via` и `task_activity.via` (`'mcp'` или
   NULL, миграция 00143; nullable-колонки и `CHECK … NOT VALID` — без сканирования больших таблиц). Правила,
   Git-события и сервер не помечаются. API: `Message.via`, `TaskActivity.via` (`"mcp"` / пусто). Клиент
   пишет после имени: «(через бота X · MCP)» — человек через своего бота, «(через MCP)» — сам бот;
   сообщение через MCP открывает свою группу, как «через бота»; правка поля через приложение не
   склеивается с правкой через MCP (ADR-0081). Создатель задачи — `tasks.created_by` (человек при «от
   имени»), «как создана» — запись журнала `created` с `via_bot_id` / `via`.
3. **Новые инструменты** — только поверх существующих маршрутов (правило ADR-0114):
   - `list_tasks` — `GET /api/workspaces/{id}/tasks/search` (доска по id или ключу `DEV`, статусы и метки по
     имени, исполнитель `me` / имя / ник / id, `state`, `sort`, курсор); `mine: true` без доски —
     `GET /api/me/tasks?scope=assigned&open=1`;
   - `update_task` — `PATCH /api/tasks/{id}`: только переданные поля (название, описание, приоритет, срок,
     начало, оценка, родитель, метки целиком или `add_labels` / `remove_labels` по имени);
   - `assign` — `PUT /api/tasks/{id}/assignees`: `add` (по умолчанию) / `remove` / `set`, люди как `me`, id,
     имя или ник (неоднозначное имя — ошибка со списком), `lead`; заметки и лидер текущих сохраняются;
   - `read` задачи дополнительно отдаёт метки, лидера, Git-связи (MR и ветки; коммиты — числом) и релизы;
     `create_task` принимает ключ доски.
   `me` — личность запроса: бот, а «от имени» — человек. Ключи доски и задачи уникальны только в
   пространстве: инструмент ищет ключ в каждом пространстве вызывающего (`/api/t/{key}?workspace_id=`),
   совпадение в нескольких — ошибка со списком (никогда не первое: запись не должна уйти в чужое
   пространство); `workspace` сужает поиск; пространства, где ключа нет или бота нет (404/403), пропускаются.
   Сервер отвечает одним 404 и на «ключа нет», и на «не видно», поэтому пишущие инструменты возвращают
   `workspace` и `board`, куда легла запись: агент и человек видят, если ключ ушёл не туда. `list_tasks` без `sort` — порядок сервера (новые первыми, с `q` — по
   релевантности), `mine` режет страницу `/api/me/tasks` по `limit` и продолжает с последней показанной задачи
   (keyset-курсор API: закрытые между страницами задачи ничего не сдвигают); `key_task` — первым, только без
   других фильтров и с той же доски; `assign` без изменений не пишет
   журнал; доска, которую не удалось прочитать, оставляет в списке id статусов, а не роняет ответ.
   **От имени участника** (ADR-0111) открыты только маршруты пространства согласия: задачи по id, доски по id
   с `workspace`; поиск по ключу, `find`, `mine` — агрегатные маршруты, закрыты (`403 ON_BEHALF_ROUTE`).
4. **Подключение разработчика**: личный бот (создатель = владелец; создание бота требует `MANAGE_BOTS`),
   «Действовать от моего имени», в MCP-клиенте — адрес, `Authorization: Bearer <токен бота>` и
   `Calab-On-Behalf: owner`.

## Последствия
- Токен такого бота действует как владелец и через MCP — то же предупреждение, что в ADR-0106; отзыв
  переключателя или токена действует сразу.
- Комментарии и правки агента видны всем как действия разработчика с пометкой «через бота X · MCP».
- Лимиты — бота (ADR-0031), как и раньше.
- `tools/list` вырос с 6 до 9 инструментов (порог теста — 6000 байт).
- Один вызов инструмента — несколько REST-вызовов в лимите бота (`list_tasks` читает доски задач,
  ключ доски — доски всех пространств); при упоре в лимит — `429` как ошибка инструмента.
- `assign` и метки в `update_task` — чтение и запись без версии: правка между ними другого человека
  перетирается (как у клиента без `If-Match`).

## Что не делаем
- OAuth-авторизация MCP (личный вход без бота) — сделано в [ADR-0158](0158-mcp-oauth-personal-access.md).
- Пометку других каналов (REST-клиенты, SDK) — только MCP; поле `via` расширяемо.
- Пометку в уведомлениях и почте — только сообщения и журнал задачи.
