# ADR-0068. Телефон: скачивание файлов веба через WKDownload и системный лист «Поделиться»

Статус: принято (2026-10-02). Дополняет [ADR-0067](0067-phone-shared-web-host.md), п. 3 и 5.

## Контекст

Веб скачивает файл одним путём: `platform.files.download` → `apiFetch` с Bearer → blob →
`<a download>` (`platform/web.ts`). Через тот же `<a download>` своего blob: идут CSV досок и
расшифровка записи. Сессией владеет только веб (ADR-0015). В оболочке iOS WebKit сообщает такой
клик как навигацию. react-native-webview 13.16.1 не умеет отвечать загрузкой: WKDownload нет ни в
этой версии, ни в upstream master. JS-политика блокирует blob:, файл не сохраняется.

Другие варианты отклонены:

- **Мост `onMessage`** с байтами или путём файла — новый канал полномочий через JS, копия
  данных и отдельное доказательство изоляции iframe.
- **`navigator.share` из веба** — после `await fetch` пользовательская активация может истечь.
  Поддержка типов файлов в WKWebView не доказана, нужна правка веба.
- **Переход на `/api/files/{id}`** — сервер принимает только Bearer, refresh-cookie живёт на
  `/api/auth`. Второй контроллер авторизации запрещён.

## Решение

1. **Нативное решение, без JS.** Патч `patches/react-native-webview@13.16.1.patch`
   (`pnpm.patchedDependencies`, только `apple/RNCWebViewImpl.m`, iOS 14.5+) отвечает загрузкой
   (`WKNavigationActionPolicyDownload`), только если выполнены все условия:
   - у ссылки есть атрибут `download` (`shouldPerformDownload`);
   - URL — `blob:` того же origin, что `source.uri` WebView (https, хост и порт);
   - инициатор — основной фрейм (`sourceFrame.isMainFrame`) с `securityOrigin` этого origin.

   Все признаки берутся из WebKit, а не из полей страницы или JS. Остальное идёт прежним путём,
   и JS-политика блокирует blob:. Сторонние iframe полномочий не получают.
2. **Файл.** WebKit сам пишет blob потоком (сетевой процесс, блоки по 512 КБ) в новый каталог
   `tmp/rnc-webview-downloads/<uuid>/`. Имя берётся из атрибута `download` и очищается:
   убираются разделители, управляющие и bidi-символы, точки и пробелы по краям; длина до
   200 байт, расширение сохраняется. Путь от страницы в ОС не передаётся.
3. **Выдача.** Когда файл записан, открывается системный лист «Поделиться»
   (`UIActivityViewController`): «Сохранить в Файлы», «Сохранить изображение», AirDrop, другие
   приложения. Своих экранов нет.
4. **Очистка и жизненный цикл.**
   - Каталог удаляется при закрытии листа, при ошибке и при отмене.
   - Остатки после завершения процесса удаляются при первой загрузке следующего запуска.
   - Одновременно идёт одна загрузка или открыт один лист; следующая загрузка отклоняется.
   - Если WebView удалён («Повторить»), загрузка в полёте отменяется.
5. **Веб не меняется.** Результат (сохранено или отменено) в веб не возвращается: моста нет.
   Тост «скачано», как и в браузере, означает «передано системе».
6. **Android не входит.** `DownloadListener` библиотеки не принимает blob:
   (`DownloadManager` работает только с http/https), и загрузка не начинается. Этот вопрос
   решается вместе с воротами Android (ADR-0067).

## Последствия

- Любая фича веба, которая скачивает свой blob: через `<a download>`, работает на iPhone без
  нативного кода и пересборки. Другие операции ОС по-прежнему требуют ADR моста.
- В `Info.plist` нужен `NSPhotoLibraryAddUsageDescription`: без него «Сохранить изображение»
  завершает приложение.
- Патч пересматривается при каждом обновлении react-native-webview (хэш хранится в
  `pnpm-lock.yaml`). Если upstream добавит WKDownload, переходим на него.
- Веб держит весь blob в памяти страницы до клика. Так было и раньше; нативная часть пишет
  файл потоком. Потоковое скачивание в вебе — отдельная задача.
