# Calaba — заметки для Claude Code

Voice-first десктоп-мессенджер для команды (Electron + LiveKit + Go + Postgres). Общение с пользователем — по-русски; код, комментарии в коде и коммиты — по-английски.

## Обязательно прочитать перед изменениями
- `docs/01-architecture.md` — компоненты и потоки
- `docs/02-media.md` — аудио/видео; **правила эхоподавления нарушать нельзя** (remote-звук только через `<audio>`, никакого WebAudio на выходе)
- `docs/04-data-model.md` — права: единственная функция `computePermissions` в `packages/protocol`
- `docs/08-design.md` — дизайн-система и UX-правила; любой UI-код им соответствует, визуальные тесты обязательны
- `docs/adr/` — почему принято каждое решение; менять решение = новый ADR

## Структура
- `apps/desktop` — Electron (main / preload / renderer). Медиа-логика в renderer. Renderer без Node.
- `apps/server` — Go: REST + WS gateway (`net/http`, `coder/websocket`, `pgx`+`sqlc`, `rueidis`). Stateless, состояние в Postgres/Redis. Лёгкость и низкая задержка — приоритет: без тяжёлых фреймворков и ORM.
- `proto/` — protobuf-контракт (buf), источник правды. `make gen` → Go в `apps/server/gen`, TS в `packages/protocol/src/gen`. **Сгенерированный код коммитим** (агентам и CI не нужен `buf` для сборки; CI проверяет дрейф: `buf generate` + `git diff --exit-code`). После правки `.proto` — `make gen` и коммит вместе.
- `packages/protocol` — TS-сторона контракта + `computePermissions` (дублируется в Go `internal/perm`, общие тест-векторы в `proto/testdata`).
- `infra/docker` — compose (prod-like и dev), `Caddyfile` + Dockerfile Caddy (caddy-l4), шаблон LiveKit `livekit.yaml.tpl`, `deploy.sh` (рендер шаблона через envsubst + `compose up`).

## Правила
- TS strict на клиенте; Go — `gofmt`, `go vet`, `golangci-lint` **только через `make lint` в `apps/server`** (конфиг `.golangci.yml` в корне, `--build-tags integration`, версия как в CI v2.14.0) — прямой `golangci-lint run ./pkg/...` без конфига пропускает правила (noctx и др.) и даёт ложный «0 issues». Типы контракта только из сгенерированного кода, руками не писать.
- Все права проверяются на сервере; LiveKit-grant повторяет права. Клиент лишь скрывает UI.
- Конфигурация — только через env. Никаких хостов/секретов в коде.
- **Производительность — приоритет продукта** (владелец, 27.09: у сотрудников не у всех мощные компьютеры). Любая фича в голосе/видео/ленте проверяется на CPU: без звонка ≤ 1 % CPU, в голосе без речи ≤ 5 %, при просмотре стрима — не больше, чем декодер; скрытое окно не декодирует видео и не крутит таймеры/анимации. **`backdrop-filter`/стекло — запрещено** (владелец, 28.09): материалы сплошные; бесконечные анимации — только лоадеры; тяжёлые эффекты — только на видимом и с `prefers-reduced-motion`/режимом «слабый компьютер». Замеры и бюджет — `docs/14-energy.md`, скрипт `tools/energy-bench.py`; новая оптимизация — с цифрами до/после.
- **Ререндеры под контролем** (владелец, 28.09: «не допускать, чтобы пол-интерфейса перерисовывалось, когда меняется пара пикселей»). Правила для любого UI-кода: Zustand-селекторы возвращают примитив или `useShallow`-срез по id, а не объект пространства/комнаты целиком; списки (лента, участники, комнаты) — строки в `memo`, колбэки стабильные (`useCallback`/из стора), пропсы без новых объектов на каждый рендер; часто меняющееся (уровни, speaking, таймеры, typing, статистика) — в листовые компоненты со своим подписчиком (`useNow`, селектор по id), стор обновляется только при пересечении порога, не на каждый тик; контексты не несут изменчивых значений. Проверка перед мержем фичи в голосе/ленте/панелях: `CALABA_REACT_PROFILING=1` + `tools/perf-call.ts` (коммиты/с и ms/с по компонентам, docs/14 «Ререндеры в звонке») — событие (VOICE_STATE, PRESENCE, typing, tick) не должно перерисовывать больше строк, чем оно затрагивает; ревьюер проверяет это по отчёту.
- Приоритет — качество и продуманность, не скорость. Перед нетривиальным решением — короткое обоснование, при смене архитектуры — ADR.
- **Диск владельца**: локальная сборка десктопа (`electron-builder`) оставляет `apps/desktop/dist` (~1.5 ГБ) — удалять после использования; Docker build cache и неиспользуемые образы чистить `docker builder prune -af` / `docker image prune -af --filter until=24h`, если свободно < 15 ГБ. Стенд-агент перед релизом проверяет свободное место.
- **Локальные прогоны Caddy** — только с тестовыми хостами (`*.test`/`localhost`) и `local_certs`/`auto_https off`; никогда не поднимать локально Caddy с боевыми `APP_HOST/RELEASES_HOST/LANDING_HOST` — он идёт за сертификатом в Let's Encrypt и тратит лимиты боевого домена.
- Тестовый стенд `root@141.105.69.177`: там работает чужая GPU-задача (python/ffmpeg/chromium, порты 8000–8400, 9100, 9400) — **не останавливать, не менять**. Наши порты: 80, 443, 7881, 7882.

## Как работаем (модели и роли)
- **Архитектура, сложные решения, ревью дизайна** — Fable (эта сессия).
- **Написание кода** — делегировать субагентам на Opus 5.5 (`model: opus`), с чёткой постановкой и ссылками на нужные docs/ADR.
- **Тестирование/прогон** — владелец делает отдельно через `claude-pool --glm` (GLM 5.3, дешевле). Оставлять тестируемому агенту понятные инструкции: что запустить, что ожидается.

## Скорость и токены — правила работы с агентами (2026-09-26)
Причины замедления, которые мы увидели: долгоживущие агенты с огромным контекстом, лид как единственный коммитер, общее рабочее дерево/базы (коллизии, откаты), ревью, порождающие новые ревью, полные визуальные прогоны. Поэтому:
1. **Свежий агент на задачу.** Задача → новый субагент (модель по п. 9) с точной постановкой (что, где, какие docs/ADR, критерий готовности) → отчёт → агент завершён. Долгоживущий только один: инфра/стенд (держит состояние деплоя). Не переписываться с агентом десятками сообщений — если задача выросла, это новая задача.
2. **Изоляция.** Каждый кодовый агент — в своём `git worktree` и ветке, со своими портами/БД: `CALABA_VISUAL_MOCK_PORT`, `MOCK_LIVEKIT_ROOM_PREFIX`, `TEST_REDIS_URL` (свой номер DB), `TEST_PG_URL` (своя база). Два агента в одном дереве — запрещено.
3. **Агент коммитит сам** на своей ветке (мелкими осмысленными коммитами, английский, с чек-листом проверок в сообщении). Лид только мержит (`rebase`/fast-forward на main) и тегирует. Лид не редактирует файлы за агентов.
4. **Отчёт — ≤ 15 строк по шаблону:** что сделано · файлы · какие проверки прошли (команды и цифры) · риски/что не проверено. Без пересказа задачи, без дублирования в idle-уведомлении. **Один отчёт на задачу, один раз** (владелец, 27.09: дубли жгут токены): агент не шлёт отчёт через SendMessage и не выходит в idle с промежуточными «жду CI/деплой» — каждый выход в idle приходит лиду отдельным сообщением с полным текстом. Ожидания (CI, Actions, деплой, очередь на тесты) — внутри одного хода фоновыми/блокирующими командами (`gh run watch`, `until … sleep`), ход завершается один раз — итоговым текстом, он и есть отчёт. Лид на дубли не отвечает.
5. **Одно ревью на изменение.** Фиксим только blocker/major; minor и «спорное» — строкой в `docs/09-ui-backlog.md` (UI) или `docs/12-tech-backlog.md` (сервер/инфра), не новой задачей. Второе независимое ревью — только для security-путей (auth, права, токены, CI с секретами) и изменений протокола.
6. **Релиз важнее полировки.** Пока идёт релиз, на main попадают только исправления блокеров этого релиза. Всё остальное — в ветку и после тега.
7. **Тесты экономно.** В цикле разработки: typecheck/lint/unit + целевой интеграционный тест. Полный интеграционный набор — один раз перед мержем ветки. Визуальные — только `-g` по экранам (спека per-screen), полный набор — один раз перед релизом (ниже). Глобальные UI-правки (островок, сайдбар, токены) копим и перезаписываем эталоны одним разом.
8. **Параллельно ≤ 4 агентов**, у каждого непересекающиеся пути. Больше — не быстрее: растут коллизии и время лида.
9. **Модели по задаче.** Архитектура/спорные решения — Fable. **Код: небольшие фичи и фиксы — Sonnet 5.5, серьёзные — Opus 5.5** (владелец, 30.09 после 1.3.2: «для фич используй sonnet 5.5 если они небольшие, а если серьёзные то opus 5.5»). Что остаётся на Opus: протокол/права/безопасность (`proto`, `computePermissions`, auth, токены, CI с секретами) и их второе ревью, отладка без ясной причины, большие фичи с новыми сущностями в нескольких слоях. Механика (changelog, правка docs по готовому тексту, триаж PR, notices, QA скриншотами) — Sonnet/Haiku уже сейчас; прогон тестов — GLM у владельца до 1.4.0.
11. **CI на main — зелёный всегда** (владелец, 27.09: «CI падает, а мы всё кидаем и кидаем»). Лид после каждого пуша в main ждёт результат `ci.yml` (`gh run watch`, фоново) и не сливает следующую ветку, пока предыдущий прогон красный; красный CI — блокер, чинится раньше любой фичи. Агенты перед коммитом гоняют те же проверки, что CI: `make gen` + `git diff --exit-code` (proto/sqlc), `make lint`, `go test -race`, `pnpm -s typecheck/lint/test`. Форма `ci.yml` (30.09, цель ≤ 4 мин): интеграционные тесты — 4 параллельных шарда (`internal/app` по первой букве после `Test` — `APP_1..3`, шаг проверки покрытия падает, если тест не попал ни в один шард; `rest` — остальные пакеты), обязательная проверка «go integration tests» — сводный джоб; интеграционные шарды — только на PostgreSQL 17 (прод на PG17, владелец 2026-10-01/02). Пуши только с `docs/**`/`*.md` CI не запускают (PR — всегда), поэтому после такого пуша ждать нечего. Известная ловушка: gofmt в разных версиях Go по-разному форматирует комментарии с отступами — в `.proto` комментариях не делать строк, начинающихся с пробелов (иначе `apps/server/gen` дрейфует между локальным Go и Go из `ci.yml`).
10. **Лид не раскручивает хвосты.** Из отчёта агента новая задача ставится, только если это блокер релиза или пункт из утверждённого бэклога.

**Статистика затрат** (владелец, 26.09): перед каждым тегом релиза выполнять `python3 tools/usage-stats.py` и коммитить `docs/13-usage.md` (токены по моделям/дням, время). Делает агент подготовки релиза. Агент подготовки релиза пишет в секции версии CHANGELOG блок `### Коротко` (3–7 строк простым языком) — бот публикует в «что нового» только его, без ссылок (владелец, 02.10 и 03.10).

Где срезаем углы (не в ущерб качеству):
- **Стенд:** e2e-web гоняем только на `app.calab.io` (chromium; `.ru` — алиас, владелец 02.10); `meet.gptunnel.ru` — только smoke (`/healthz`, `/api/version`, TLS). Firefox — раз в сутки в nightly, не в релизе.
- **Интеграционные тесты:** в цикле — только пакет, который трогали (`go test -tags integration ./internal/<pkg>`); весь набор — один раз перед мержем ветки, не после каждого фикса.
- **Ревью:** один проход, только blocker/major; ревьюер сам правит очевидное и коммитит — без круга «отчёт → лид → задача → отчёт».
- **Документация:** правим docs только при изменении поведения/контракта; TESTING.md — сценарий ≤ 15 строк, без «как мы это выясняли». Отчёты агентов — по шаблону, не эссе.
- **Эталоны:** diff ниже порога не перезаписываем; глобальные UI-правки копим в одну перезапись; per-screen спека, чтобы `-g "<screen>"` гонял один экран.
- **Модели:** механику (changelog, notices, триаж PR, правка docs по готовому тексту) — Sonnet/Haiku.
- **Не делаем:** второе ревью вне security/protocol, «попутные» улучшения в релизной ветке, повторные полные прогоны «для уверенности».

## Визуальные тесты — экономно (владелец, 26.09: «смотрим только что поменялось»)
- **Визуальные прогоны сейчас не запускаем вовсе** (владелец, 30.09, после релиза 1.2.0: «визуальный прогон я бы пока не делал вообще — оставь код, но не запускай его»): ни nightly (воркфлоу `visual-nightly` выключен через `gh workflow disable`, файл остаётся), ни локальные `e2e:visual*`, даже `-g`. Лид не ставит визуальные прогоны в брифы; остаются typecheck/lint/unit и один QA-проход скриншотами (Sonnet) по новым экранам. Включить обратно — только по слову владельца (`gh workflow enable visual-nightly`).
- **С 1.3.0 — никакой регрессии всего интерфейса перед релизом** (владелец, 30.09: «чет прям много тестов гоняет, не будем с 1.3.0 так прям всё тестировать»). Перед релизом не перезаписываем устаревшие эталоны пачками и не гоняем группы «для контроля»; в релиз идут только `-g` тех экранов, что менялись в этом релизе, и один QA-проход скриншотами (Sonnet) по новым экранам. Устаревшие локальные эталоны из-за глобальных правок (шапка, тайтлбар) просто остаются устаревшими — их обновляет nightly на Linux; локально экран перезаписывается, когда его в следующий раз трогают.
- **Визуальные прогоны — только при изменении разметки/стилей этого экрана** (владелец, 28.09: «в них нет изменений, а он гоняет»). Перф-правки, рефакторинг, логика сторов, сервер, документация — визуальные тесты не запускать вовсе, даже «контрольно»; достаточно typecheck/lint/unit. Лид не ставит `-g` в бриф, если задача не трогает UI.
- **Никаких полных прогонов на машине владельца** — ни в работе, ни перед релизом. Только затронутые экраны: `pnpm -F @calaba/desktop e2e:visual -g "<screen|group>"`, перезапись только их (`e2e:visual:update -g …`), один контрольный `-g`.
- **Локальные эталоны — минимальный десктоп `dark 960×600` + мобильный веб `dark 390`** (владелец, 26.09: «минимальный размер десктоп + мобильный, на весь экран не тестить»), только ключевые экраны (~25: вход, онбординг, чат, вложения/превью, DM, голосовая комната в состояниях, стрим, камера, 2–3 вкладки настроек, меню участника, join-карточка; мобильные: чат, шторка, полоса звонка, DM, настройки, онбординг). Каждый пункт меню отдельно не снимаем. Полная матрица (light, 1440, все экраны) — только nightly CI на Linux (`CALABA_VISUAL_ALL=1`).
- **Один экземпляр приложения за раз**: `CALABA_VISUAL_WORKERS=1` (дефолт), два **тестовых** Electron одновременно не запускать; два агента не гоняют визуальные/e2e-тесты параллельно — второй ждёт. Установленный `/Applications/Calab.app` владельца — не тестовый экземпляр, его наличие прогон не блокирует (проверять только процессы Playwright/`out/`-сборок).
- **Тесты без звука**: Electron и chromium в тестах запускаются с `--mute-audio`.
- Глобальные UI-правки (островок, рейл, токены) копим и перезаписываем одним `-g` по группам, не по одной.

## Команды
```
pnpm install && make gen
pnpm infra:dev                          # postgres, redis, minio, livekit --dev
cd apps/server && go run ./cmd/server   # или make dev-server
pnpm dev:desktop
make test                               # go test + pnpm test
```
