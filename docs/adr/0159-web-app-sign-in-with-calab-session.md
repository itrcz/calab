# ADR-0159: Вход в веб-приложение пространства по сессии Calab (2026-11-05)

**Статус: предложено.** Уточняет [ADR-0050](0050-workspace-apps.md) §4 (изоляция сайта ярлыка) и
опирается на OAuth-провайдер [ADR-0054](0054-workspace-identity.md) п. 8 и
[ADR-0102](0102-oauth-clients-without-reauth.md). Контракт не меняется; сервер только перестаёт
выдавать код провайдера гостю по роли в пространстве (п. 3).

## Контекст
Пространство заводит OAuth-клиент для своего внутреннего сайта («Войти через Calab») и ярлык на этот
сайт в рейле. Сайт в ярлыке живёт в отдельной сессии `persist:app-<id>` (ADR-0050 §4), сессии Calab
там нет. Поэтому человек, уже вошедший в Calab, при первом открытии ярлыка видит форму входа Calab
внутри сайта и входит второй раз. Владелец: «если человек в нашем пространстве, ему не надо ещё
раз подтверждать, что он в Calab». И: «доступ только внутри своего пространства».

## Решение
1. **Что перехватывается.** Только навигация главного фрейма вью ярлыка (`will-navigate`,
   `will-redirect`) на `/oidc/workspaces/<id>/authorize` **своего** сервера (origin текущего сервера
   Calab, только https), где `<id>` — пространство этого ярлыка, а `redirect_uri` клиента — на
   origin адреса ярлыка (https; http — только частный хост по правилу ADR-0050 §1). Запрос должен
   быть обычным code flow: `response_type=code`, PKCE S256, `state`, `nonce`, каждый параметр один
   раз, без `prompt`, `max_age`, `id_token_hint`, `login_hint`, `request`. Всё остальное грузится
   как раньше. Попапы и дочерние окна ярлыка не перехватываются.
2. **Как отвечаем.** Main повторяет запрос сайта к провайдеру с `prompt=none` и `Authorization:
   Bearer` текущей сессии Calab (сервер это уже принимает, `identitywiring.go`
   `providerSessionResolver`). Код из `Location` уходит во вью, только если адрес — тот же
   `redirect_uri` (origin и путь). `consent_required` — один раз спрашиваем человека диалогом Calab
   в главном окне (Modal дизайн-системы, не системное окно; renderer только показывает тексты
   сервера и возвращает ответ, принимается ответ только главного окна и только на открытый
   запрос; «Запретить» в фокусе, Esc и 2 минуты без ответа — отказ): main открывает обычный запрос согласия (`authorize` без
   `prompt` → `/oauth/consent?request=`), показывает то, что вернул `bind` (клиент, пространство,
   аккаунт, сайт, данные), и отправляет `decision` (`allowRefresh: false`). Привязка запроса к
   «браузеру» — cookie в сессии API десктопа (`persist:calaba-api`); молчаливый запрос идёт без
   cookie, только с Bearer. Разрешение сервер запоминает, следующий вход молчаливый; отозвать —
   в настройках, раздел приложений с доступом. Отказ сервер не запоминает: до закрытия вью ярлыка
   десктоп больше не перехватывает, сайт входит своим путём. Пока один ответ в работе, повторный
   запрос сайта не открывает второй диалог.
3. **Кто проходит.** Решает сервер, как и для браузера: участник пространства, не гость, не
   приостановлен, тариф с провайдером, политика входа пространства (`identitypolicy`:
   `MembershipRequired`, `ScopeDenied` для гостей). Этим же решением гость по роли в пространстве
   (зарегистрированный аккаунт, впущенный по ссылке комнаты: `users.is_guest` у него false) тоже
   получает `ScopeDenied` на операциях провайдера: раньше провайдер отказывал только гостевым
   аккаунтам. Любой отказ (`login_required`,
   `interaction_required`, ошибка сети, нет сессии, вью не на экране для диалога) — грузим исходный
   запрос сайта: провайдер покажет свою форму, как до этого решения.
4. **Граница изоляции ADR-0050 §4 сохраняется.** Токен и cookie Calab во вью не попадают; сайт
   получает только редирект провайдера на свой `redirect_uri` с одноразовым кодом, который без
   секрета клиента и PKCE verifier сайта не обменять. Main не читает и не меняет содержимое сайта.
5. **Петля.** Не больше 3 ответов на ярлык в минуту; дальше запрос сайта идёт как раньше.

## Почему так
- Привязка «пространство ярлыка = пространство входа» и «`redirect_uri` на origin ярлыка» не даёт
  сайту одного ярлыка получить код чужого пространства или клиента с адресом возврата на другом
  сайте. Два клиента одного пространства с возвратом на один origin взаимозаменяемы: это та же
  возможность, что у этого origin в обычном браузере.
- Согласие остаётся явным для каждого человека (ADR-0054 п. 8, ADR-0102): первый раз — диалог Calab,
  дальше — сохранённое согласие, как `prompt=none` в браузере.
- Без изменений протокола: используются существующие `authorize`, `bind`, `decision`. На сервере
  меняется только отказ гостю по роли (п. 3).

## Последствия
- Веб-клиент и телефон не меняются: там сайт в iframe/новой вкладке, вход через Calab идёт обычным
  путём браузера.
- Десктоп с сервером-алиасом (сохранён `app.calab.ru`, а issuer `app.calab.io`) не совпадёт по origin
  и войдёт по-старому.
- Пространство с обязательным корпоративным входом получит `interaction_required` без свежего
  подтверждения SSO и войдёт по-старому.
- `allowRefresh: false`: если клиент уже получал согласие с refresh в браузере, а затем сменил имя
  или расширил scopes, новое согласие из десктопа сузит его и закроет прежние гранты клиента на
  всех устройствах (`RevokeReplacedOAuthGrants`). Для клиентов без refresh это ничего не меняет.
