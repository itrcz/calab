# ADR-0169: Имена спикеров в транскрипте встречи (2026-11-24)

**Статус: принято (24.11, владелец: «нужно уметь определять спикеров поименно»; переработано после ревью
24.11).** Дополняет [ADR-0025](0025-meeting-transcription.md) (запись встреч и транскрибация через GPTunneL);
п. 1 (одна смешанная дорожка room composite) не меняется. Не нарушает [ADR-0013](0013-livekit-minimal-client.md)
(в API нет LiveKit SDK).

## Контекст

Запись встречи — одна смешанная дорожка (room composite, AAC/MP4). Её распознаёт GPTunneL (ElevenLabs Scribe v2,
запасной — Deepgram Whisper; сверено с `services/meetings/transcribeModel.ts` 13.11) и сам делит речь на голоса:
в транскрипте `speaker` — номер 0, 1, …, имён нет. Подсказки имён у GPTunneL нет.

Проверка альтернативы 24.11: NVIDIA Nemotron 3 Diarization (сервер владельца): голоса делит хорошо, имя выводит
только из речи по обращениям — 2 из 3 в тесте, текста реплик не отдаёт. Угадывать имя по речи ненадёжно.

Калаба знает, кто говорит, точнее любого распознавания: клиент каждого участника сам решает, когда его микрофон
в эфире — VAD-гейт или PTT (`useVoice.transmitting`, docs/02). Вне гейта дорожка молчит, значит в смешанную
запись попадает речь участника ровно в интервалы `transmitting`.

Первая версия ADR (скрытый участник LiveKit в API, `SpeakersChanged`) отвергнута ревью: скрытый участник без
подписки не получает чужих спикеров (livekit-server `participant_signal.go` шлёт их только подписчикам), lksdk
требует рабочий ICE от пода API до медиа-хоста, LiveKit SDK в API нарушает ADR-0013, скрытый участник не даёт
комнате закрыться.

## Решение

1. **Шкала речи сообщает клиент — только о себе.** Пока в комнате идёт запись (клиент знает по
   `ROOM_RECORDING`), голосовой сервис копит свои интервалы `transmitting` (вкл → выкл, по таймеру
   `performance.now()`) и раз в 10 с, а также при стопе записи, выходе из комнаты и переходе в другую, шлёт их
   по сокету: `RecordingSpeech {room_id, recording_id, intervals: [{ago_start_ms, ago_end_ms}]}` — время
   **назад от момента отправки**, а не часы клиента: сервер переводит в своё время (`получено − ago`), ошибка
   ≈ половина RTT, синхронизация часов не нужна. Кто говорил — сервер берёт из сессии сокета (user_id),
   клиент не может прислать интервалы за другого. Нового таймера в покое нет: копим по событиям гейта, сброс —
   только пока идёт запись. При выходе/переходе отчёт уходит до разрыва голосового подключения; последний
   отчёт, который не ушёл (сокет не READY), повторяется по тому же таймеру в пределах минуты после стопа, потом
   отбрасывается. Мобильный клиент — тот же веб-клиент (ADR-0067).
2. **Сервер** принимает только для записи в статусе `recording` этой комнаты (или остановленной меньше минуты
   назад — последний отчёт стопа), от участника её голосового подключения; от того, кто уже вышел, но сообщал
   по этой записи раньше (отчёт выхода, повтор упавшей отправки), — только интервалы, кончающиеся не позже
   его последнего принятого отчёта + 15 с (`room_recording_speech.reported_at`); режет до разумного
   (≤ 200 интервалов за сообщение, ≤ 20 000 на человека за запись, интервалы внутри окна записи, склейка пауз
   < 0,5 с) и пишет в `room_recording_speech(recording_id, user_id, start_ms, end_ms, reported_at)`, `start_ms` — от
   `started_at` записи. Без Valkey-замков: пишет любой экземпляр API, к которому подключён сокет.
3. **Отсчёт времени.** Начало файла — `FileInfo.started_at` из вебхука конца egress (добавить в `rtc.FileResult`),
   запасной — `room_recordings.started_at`. Перед сопоставлением подбираем один общий сдвиг в пределах ±2 с
   (шаг 100 мс) по максимуму перекрытия шкалы с репликами транскрипта — он снимает и задержку старта egress,
   и запаздывание распознавания.
4. **Сопоставление** (`internal/recording/speakers.go`, чистая функция, табличные тесты): по `user_id`
   (несколько устройств одного человека — один участник). Каждый номер спикера решается **независимо**
   (несколько номеров на одного участника допустимы — распознавание дробит голос): сначала по «сольным»
   отрезкам шкалы (в эфире ровно один участник), если их мало (< 3 с у номера) — по общему перекрытию.
   Номер получает участника, если тот покрывает ≥ 50 % речи номера и вдвое больше следующего. Если номер
   явно склеил двух людей (двое по ≥ 30 %) — решение по каждой реплике отдельно тем же правилом. Реплика
   без спикера (`-1`) — по своему перекрытию. Не решилось — «Участник N», как сейчас.
   **Без клиента** (SIP-абонент, бот без поддержки, старый клиент) интервалов нет; если после сопоставления
   неопознанным остался ровно один номер транскрипта (все остальные получили участника), у него заметная речь
   (≥ 10 % записи) и во время записи в комнате был ровно один телефонный номер (`sip_calls`, разные номера),
   номер спикера получает его. Два и больше неопознанных номера (например, сотрудник со старым клиентом и
   абонент) — не угадываем. Остаётся риск: абонент молчал, а сотрудник со старым клиентом говорил — его номер
   получит телефон; журнала голосовых участников записи нет, отличить нельзя.
5. **Хранение**: `room_recordings.speakers_json` (`[{speaker, user_id?, name?}]`) и `user_id` у реплики,
   пересчёт при каждом получении транскрипта. Имя людей пространства не копируется — клиент берёт его и
   аватар из своего справочника (удалённый аккаунт — как автор сообщения удалённого аккаунта); `name` — только
   для тех, кого в справочнике нет (гость — имя гостя, SIP — номер/контакт). Мягкое удаление записи
   (`DeleteRecording`) в том же запросе очищает `room_recording_speech` и `speakers_json`.
6. **Контракт**: `TranscriptSegment.user_id` (пусто — не опознан), `GetRecordingTranscriptResponse.speakers`
   (`TranscriptSpeaker {speaker, user_id, name}`); клиент показывает имя и аватар вместо «Спикер N», поиск и
   `.txt` — с именами. Права те же (`visibleRecording`): кто видит транскрипт, видит и имена; API ботов
   (`GET …/transcript`) получает те же поля, включая `user_id`. Саммари GPTunneL не переписываем — в docs/08
   отметить, что в саммари могут остаться номера.
7. **Движок не важен**: сопоставление работает с любым распознаванием, которое даёт номера и тайминги
   (GPTunneL сейчас; Nemotron/свой Whisper — если заменим). Шкала — наша.
8. **Раскатка и выключатель.** Старый сервер закрывает сокет на незнакомый кадр (`4001`), поэтому клиент
   шлёт `RecordingSpeech` только если последний `HELLO` сокета объявил бит `Hello.capabilities`
   `SERVER_CAPABILITY_RECORDING_SPEECH` (HELLO приходит на каждый сокет до IDENTIFY/RESUME, READY/RESUMED
   позже и при RESUME не повторяет READY). Откат API или старые поды при раскатке — бита нет, клиент ничего
   не копит и не шлёт, без таймера; переподключение к такому серверу сбрасывает накопленное. env
   `RECORDING_SPEAKER_NAMES=off` (по умолчанию `on`) — выключатель: бит не объявляется, пришедшие кадры
   молча игнорируются (не закрытие), сопоставление не запускается, сохранённое (`speakers_json`, `user_id`
   реплик) не отдаётся — транскрипт с номерами, как до ADR.
9. **Доверие**: клиент сообщает только о себе. Лгущий клиент («я говорил всегда») сольных отрезков не
   получает, пока говорят другие, — чужие номера отнять не может, хуже только себе. Для внутреннего
   инструмента команды этого достаточно.

## Отвергнуто

- **Скрытый участник LiveKit в API** (первая версия) — см. Контекст.
- **Отдельный агент на медиа-хосте** (как `cmd/ivr`, с подпиской на все микрофоны) — работает и для SIP, но
  новый деплой и N потоков Opus на запись ради того, что клиент знает точнее; вернуться, если нужна будет
  шкала для телефонных записей (ADR-0131) без клиентов.
- **Имена от распознавания** (Nemotron `name`, подсказка GPTunneL) — угадывание по речи.
- **Отдельная запись дорожки каждого участника** (track egress) — ×N стоимость распознавания и egress CPU.
