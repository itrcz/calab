# ADR-0082. Задержка уведомления согласующих

Статус: принято (2026-10-09). Развивает ADR-0049 §3, §5 и ADR-0058 (настройки доски).
Владелец: согласующего часто добавляют по ошибке и сразу убирают — уведомление уже ушло.
Нужна настраиваемая задержка; правка задачи, сбросившая голос, тоже должна звать согласующего
заново — отдельным текстом.

## Решение

### 1. Настройка доски
- `boards.approval_notify_delay_seconds integer not null default 60`, CHECK ∈ {0, 60, 300, 900, 1800, 3600}
  (миграция `00073`, без блокировок на заполненной БД: NOT VALID + VALIDATE, индекс CONCURRENTLY; существующие доски — тоже 1 минута).
- Контракт: `Board.approval_notify_delay_seconds = 30`, `UpdateBoardRequest.approval_notify_delay_seconds = 13`
  (optional). Право — как у остальных настроек доски (`MANAGE_BOARD`, `PATCH /api/boards/{id}`);
  другое значение — `422` (`field: approvalNotifyDelaySeconds`). Смена задержки не двигает уже
  запланированные уведомления. Настройку можно менять и при выключенном `APPROVALS` (клиент её прячет).
- Клиент: «Фичи» → карточка «Согласование» → «Уведомлять согласующих»: Сразу / Через 1, 5, 15, 30 мин / Через 1 час;
  видна, только пока `APPROVALS` включён.

### 2. Отложенная доставка
- `task_approvers.notify_due_at timestamptz null` (частичный индекс `WHERE notify_due_at IS NOT NULL`),
  `notify_reason text` (`requested` — стал согласующим | `re_requested` — голос сброшен правкой).
  Строки, существовавшие до миграции, — `NULL` (уже уведомлены).
- Добавление согласующего (создание задачи, `PUT …/approvers`, правило `set_approvers`) и сброс голоса
  ставят `notify_due_at = now() + delay` (время БД). При задержке 0 — как раньше: уведомление в том же
  запросе после коммита, `notify_due_at` не ставится. Автору изменения уведомление не планируется.
- Воркер `boards.Service.RunApprovalNotices` — тикер 15 с на каждом экземпляре, без Redis-блокировки:
  выбирает задачи с наступившим сроком (по частичному индексу — в простое это пустой индексный запрос),
  на каждую задачу — своя транзакция: `UPDATE … SET notify_due_at = NULL … FOR UPDATE SKIP LOCKED RETURNING`,
  затем отправка через общий путь (`sees` → подписка → `decide` → `sendNotices`). Ошибка задачи — лог,
  повтор на следующем тике (строка не очищается — транзакция откатилась).
- Не отправляется: согласующего убрали (строки нет), голос уже отдан (`state ≠ pending`), задача или доска
  в архиве, на доске выключен `APPROVALS`. Срок при этом всё равно снимается.
- Отданный голос сразу снимает неотправленное уведомление (`SetApproverVote`), сброс голосов — тоже: сброс
  при задержке 0 (или после её смены) не отправит уведомление второй раз воркером.
- `actor_id` отложенного `requested` — `added_by`; у `re_requested` — пусто.
- Ежедневное напоминание считается от фактической отправки: захват ставит `requested_at = now()`,
  `reminders = 0`; `DueApprovalReminders` не берёт строки с ещё не отправленным уведомлением.

### 3. Повторный запрос после правки
- Сброс голосов (ADR-0049 §3) переводит в `pending` только **отданные** голоса и планирует им
  `re_requested`; согласующие, чей голос и так `pending`, сохраняют своё расписание (уведомление
  и напоминания не дублируются). Раньше при сбросе звали всех согласующих.
- Контракт: `TaskNotice.re_requested = 7` (bool) при `kind = APPROVAL_REQUESTED`. Выбрано поле, а не
  новый `TaskNoticeKind`: старые клиенты показывают обычный запрос согласования, а правило обязательности
  (`taskNotifies`, общие тест-векторы) не меняется. Текст клиента — «Задача изменена — нужно согласовать повторно».
- Push на мобильный для уведомлений задач сервер пока не шлёт (категория `task` в `push` только
  зарезервирована) — отображение push не меняется.

## Последствия
- Протокол меняется (`boards.proto`): `make gen`, генерированный код в коммите.
- Задержка — до ~15 с позже срока (период тикера); для 1 минуты по умолчанию это приемлемо.
- Отложено: задержка для правил автоматизации отдельно от ручного добавления; отмена уведомления при
  смене задержки.
