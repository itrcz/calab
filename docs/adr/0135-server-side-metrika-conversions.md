# ADR-0135: Серверные конверсии в Яндекс Метрику для Яндекс Директа (2026-10-26)

**Статус: принято (26.10).** Решение владельца (26.10): сервер сообщает счётчику 113761661 о
(1) регистрации и (2) оплате с суммой, валютой и тарифом; Директ оптимизируется сначала по
регистрациям, потом по оплатам. Дополняет ADR-0080 (оплаты), docs/04 «Атрибуция», docs/05
`RegisterRequest.attribution`.

## Контекст

Лендинг (calab.io) с согласия посетителя грузит Метрику и шлёт JS-цели кликов
(`download_click` … `docs_open`), а к ссылкам на `app.calab.io` дописывает `utm_*`/`yclid`.
Регистрация и оплата происходят в приложении и на сервере (вебхуки Stripe / Точки / OnPay):
Метрика лендинга их не видит, а JS в приложении мы не грузим (без трекеров в продукте). Связать
факт с рекламным кликом можно только по идентификатору посетителя Метрики — **ClientID**
(`_ym_uid`, `ym(id, 'getClientID', cb)`).

Measurement Protocol (документация Яндекса, «Загрузка данных» / «Использование Measurement
Protocol», проверено 26.10):
- `POST https://mc.yandex.ru/collect`, обязательные `tid`, `cid` (целое ≥ 0), `t`, `ms` (токен
  опции, у счётчика включена, токен уже есть). Пакет: общие параметры в query, хит — строка тела.
- JS-цель: `t=event&ea=<идентификатор цели типа «JavaScript-событие»>`; ценность — `ev` + `cu`.
  Покупка ecommerce: `t=event&pa=purchase&ti=…&tr=…&cu=…&pr1id/nm/pr/qt`.
- Событие, которое нельзя привязать к визиту, **не записывается**: визит создаётся `pageview`.
  Дополнять визит можно ≤ 12 ч после него; `et` старше 12 ч отклоняется. Историю ClientID Метрика
  держит 21 день.
- Режима отладки нет: `200 <!-- OK -->` = принято (не значит «попало в цель»), `400` + причина в
  HTML-комментарии.

## Решение

1. **Ключ атрибуции — ClientID, только после согласия.** Лендинг после загрузки тега (= после
   согласия на `analytics`) берёт `getClientID` и дописывает `ym_cid` к ссылкам на приложение;
   отзыв согласия его забывает. Без согласия уходят только `utm_*`/`yclid` (как раньше).
2. **Веб-клиент** при первом открытии забирает `utm_*`, `yclid`, `ym_cid` из адреса
   (`renderer/lib/attribution.ts`), убирает их из адресной строки и хранит в `localStorage`
   (first touch: новая кампания не перезаписывает свежую, срок 90 дней). Регистрация отправляет их
   один раз в `RegisterRequest.attribution`, после успеха забывает. Телефон (WebView веб-клиента,
   ADR-0067) — так же.
3. **Сервер** в транзакции регистрации пишет `user_attribution` (одна строка на аккаунт, обрезка до
   200 символов, ClientID — только цифры), отдельная таблица, а не колонки `users`: маркетинговые
   данные с другим жизненным циклом не раздувают горячую таблицу. Нет ClientID — UTM хранится,
   в Метрику ничего не уходит.
4. **Outbox `metrika_conversions`** с уникальным `dedupe_key` (`signup:<user>`,
   `purchase:<payment>`) пишется в транзакции факта — это и есть «маркер отправки»: повторный
   вебхук, pull-sync и сверка дают `ON CONFLICT DO NOTHING`. Воркер (`internal/metrika`, на каждой
   реплике, `FOR UPDATE SKIP LOCKED` + аренда 2 мин, опрос раз в 30 с) шлёт пакет; `400` — сразу
   `failed_at` (повтор не поможет), сеть/5xx — повтор через 1 м, 5 м, 30 м, 2 ч, 6 ч, после 6
   попыток — `failed_at`. Сеть только вне транзакции; регистрацию и платёж ничто из этого не
   роняет (кроме отказа той же БД). Без `YM_MP_TOKEN` строки не пишутся и воркер не стартует.
5. **Хиты одной конверсии** одним пакетом: `pageview` (`dl` = `PUBLIC_APP_URL`, `dt=Calab`) —
   открывает визит для ClientID, потом цель `ea=signup` / `ea=purchase` (`ev` = сумма в основных
   единицах, `cu` = валюта платежа), для оплаты ещё ecommerce `pa=purchase` (`ti` = id платежа,
   `tr`, `pr1id` = тариф аккаунта `team`/`enterprise`). `et` = время факта, если ему < 11 ч, иначе
   не передаётся (время приёма) — конверсия не теряется. Атрибуция к рекламе — моделью Метрики/Директа
   по ClientID (наш визит «прямой», значимым источником остаётся рекламный клик в пределах 21 дня).
6. **Что считается.** `signup` — создание аккаунта (`POST /api/auth/register`): аккаунт пригоден к
   работе сразу (подтверждение email не точка активации, `EMAIL_VERIFICATION=optional`), а быстрый
   сигнал важнее для Директа и 12-часового окна. `purchase` — каждый **подтверждённый** платёж,
   который получил лот пополнения (`core.CreditPayment`, новый хук `Hooks.PaymentCredited` — одна
   точка для Stripe, Точки и OnPay; старт checkout не считается), включая автопополнение
   («продление» в балансовой модели ADR-0080: суточные списания платежами не являются). ClientID —
   владельца пространства аккаунта (он платит). Платежи `livemode=false` (Stripe test) не шлются.
7. **Без PII**: только ClientID, цель, сумма, валюта, тариф, id платежа. Ни email, ни имени, ни IP.
8. **Цели в Метрике** — JS-события `signup` (674710541, «Регистрация (сервер)») и `purchase`
   (674710542, «Оплата (сервер)»), созданы через Management API 26.10; ценность передаётся в хите,
   отдельного типа цели не нужно. Ecommerce-отчёт требует включённой электронной коммерции счётчика
   (у лендинга `ecommerce: 'dataLayer'`).

## Env

`YM_MP_TOKEN` (секрет; пусто = выключено), `YM_COUNTER_ID` (113761661), `YM_MP_URL`
(`https://mc.yandex.ru/collect`). В прод — через Vault `kv/app/calab` → `calab-env` (docs/06).

## Ограничения

- **Десктоп**: установщик скачивается с лендинга, но параметры ссылки до установленного приложения не
  доходят (нет deep link при установке) — регистрации в десктопе не атрибутируются. Регистрация в
  вебе и последующая установка десктопа атрибутируются (аккаунт уже несёт ClientID).
- Оплата через > 21 день после последнего визита на сайт создаёт в Метрике нового посетителя —
  к рекламному клику не привяжется. Отказы `400` видны в `metrika_conversions.error` и метрике
  `calaba_metrika_conversions_total{result="failed"}`.
- Каждая конверсия создаёт в Метрике короткий «прямой» визит (pageview) — небольшая добавка к визитам.

## Дополнение (2026-11-02): нативная оболочка телефона никогда не атрибутируется

Задача CBF-143: сторные формы приватности (App Store / Google Play) честно отвечают
«Tracking: No» только если регистрация из нативной оболочки телефона (`apps/mobile`, ADR-0067)
не может породить конверсию Метрики ни при каких условиях — иначе риск оставался «[?]»
(`docs/mobile/store-listing.md` §3.1). Решение — по обе стороны границы клиент/сервер, каждая
независимо:

1. **Клиент** (`apps/desktop/src/renderer/lib/attribution.ts`) в нативной оболочке
   (`inNativeShell()`, `platform/nativeShell.ts`) не берёт `ym_cid`/`utm_*` из ссылки, на которой
   открылось приложение, и не хранит их; `storedAttribution()` ничего не отдаёт даже если в
   `localStorage` осталась атрибуция, записанная версией клиента до этой правки.
2. **Сервер** (`internal/auth/service.go`, `Service.Register`) отдельно не создаёт строку
   `user_attribution` и не шлёт конверсию `signup`, если запрос регистрации несёт маркер оболочки
   в User-Agent (`SHELL_UA_MARKER` = `CalabShell/1`, `apps/desktop/src/shared/nativeShell.ts`,
   `apps/mobile/src/App.tsx`, DEV-4947) — это тот же сигнал, которым клиент и так помечает себя
   WebView'у (`applicationNameForUserAgent`), доступен без нового поля протокола и не ослабляется
   старой или подделанной версией приложения.

Итог: регистрация из нативной оболочки никогда не производит ни строку атрибуции, ни конверсию,
независимо от того, что пришло в `RegisterRequest.attribution`.

## Альтернативы

- Офлайн-конверсии (CSV через Management API) — для событий старше 12 ч; сейчас не нужно, `et`
  опускаем. Вернуться, если понадобится точное время старых оплат.
- Отправка из транзакции / в горутине без outbox — теряет конверсии при падении и не даёт
  идемпотентности при повторных вебхуках.
