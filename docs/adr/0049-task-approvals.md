# ADR-0049. Согласование задач: согласующие, кворум, вето

Статус: принято (2026-09-30), к следующему минорному релизу. Развивает ADR-0042 (доски).
Владелец, 30.09: «хочу добавить в таски функционал согласования: таску создаём и можно добавить
людей, которые согласовывают таску, и без этого нельзя её перенести дальше, пока они апрув не
поставят; причём можно задать, сколько человек должны апрув поставить — все или условно 2/3».
Решения владельца по вопросам (30.09): блокируется **движение вперёд**; «Отклонить» — **вето**;
правка названия/описания **сбрасывает** голоса.

## Решение

### 1. Модель
- Таблица `task_approvers` (миграция `00053`): `task_id`, `user_id`, `state` (`pending|approved|rejected`),
  `comment` (≤ 500, обязателен при `rejected`), `decided_at`, `added_by`, `added_at`; PK `(task_id, user_id)`.
- `tasks.approval_required smallint not null default 0`: сколько одобрений нужно; **0 = все**.
  Действующий кворум = `min(required, число согласующих)` (при `0` — число согласующих).
- Согласующих ≤ 10; только участники пространства, видящие доску (`VIEW_BOARD`), не гости, не боты.
  Исполнитель может быть согласующим (не запрещаем — маленькие команды).
- Производное состояние задачи (сервер считает, клиент берёт готовым):
  `NONE` (согласующих нет) · `PENDING` · `APPROVED` (одобрений ≥ кворума и нет отклонений) ·
  `REJECTED` (есть хотя бы одно `rejected` — вето, кворум не важен).

### 2. Правило блокировки (сервер — единственный арбитр)
Если состояние не `APPROVED` и не `NONE`, **запрещён переход в статус «дальше»**: статус с большей
позицией на доске, чем текущий, **или** любой статус типа `COMPLETED`. Разрешены: назад (меньшая
позиция), внутри той же колонки (порядок), в статус типа `CANCELLED` (отмена не требует согласия).
Проверяется во **всех** путях смены статуса: `PATCH /api/tasks/{id}` (`status_id`, в т.ч. kanban-move),
массовые операции, API ботов. Перенос на другую доску (`board_id`) не-согласованной задачи
разрешён (согласующие и голоса переезжают вместе с ней), кроме случая, когда её статус — `COMPLETED`
(тогда согласование уже было не нужно или задачу закрыли до добавления согласующих — переносим как есть). Отказ — `409` с кодом `TASK_APPROVAL_REQUIRED` и деталями
`{approved, required, rejected}`. Обхода «для админа» нет: `EDIT_TASKS` может убрать согласующих
(это видно в журнале) — осознанное действие, а не тихий обход.
Добавление согласующих к задаче, которая уже «далеко», её не двигает назад — правило действует на
следующие переходы.

### 3. Голоса и сброс
- Голосует только сам согласующий: `APPROVE`, `REJECT` (с комментарием), `WITHDRAW` (обратно в `pending`).
  Решение можно менять в любой момент.
- Правка `title` или `description` (включая вложения описания) сбрасывает **все** голоса в `pending`
  (журнал `approvals_reset`, уведомление согласующим «задачу изменили — согласуйте заново»).
  Исполнители, даты, метки, приоритет, статус, подзадачи, комментарии — не сбрасывают.
- Убрали согласующего — его голос исчезает; добавили — `pending` (при «все» задача снова `PENDING`).

### 4. Права
Новых битов нет (`computePermissions` не меняется). Задавать согласующих и кворум: создатель задачи,
ведущий исполнитель, `EDIT_TASKS` — то есть тот, кто вправе править задачу (правило ADR-0042).
Голосовать: только сам согласующий, пока видит доску; потерял доступ к доске — голос сохраняется,
но менять его нельзя (задачу разблокирует `EDIT_TASKS`, убрав его).

### 5. Контракт (`boards.proto`, `gateway` — без новых событий)
- `enum TaskApprovalState { UNSPECIFIED; NONE; PENDING; APPROVED; REJECTED }`,
  `enum ApproverState { UNSPECIFIED; PENDING; APPROVED; REJECTED }`.
- `message TaskApprover { user_id; ApproverState state; comment; decided_at; added_by; added_at }`.
- `Task`: `repeated TaskApprover approvers = 36; uint32 approval_required = 37; TaskApprovalState approval_state = 38;`
- `PUT /api/tasks/{id}/approvers` `SetTaskApproversRequest { repeated string user_ids; uint32 required }` → `TaskResponse`
  (полный список; `required` > числа согласующих → 422; новые — подписка и уведомление).
- `POST /api/tasks/{id}/approval` `TaskApprovalRequest { enum decision APPROVE|REJECT|WITHDRAW; comment }` → `TaskResponse`.
- `CreateTaskRequest`: `repeated string approver_ids`, `uint32 approval_required`.
- Фильтр: `TASK_FIELD_APPROVAL_STATE` (`none|pending|approved|rejected`) и `TASK_FIELD_APPROVER_PENDING`
  (user ids | `me`: согласующий, чей голос ещё `pending`) — для вида «Ждут моего согласования».
- Журнал `TaskActivity.kind`: `approvers` (before/after — списки и кворум), `approval`
  (`{user_id, state, comment}`), `approvals_reset`.
- `TASK_UPDATE` несёт задачу целиком — отдельных событий не нужно.
- Уведомления (`TaskNotice.kind`) — **обязательные** (владелец, 30.09: «важно, чтобы через уведомления
  нужным людям приходили обязательно»): доставляются **в обход** уровня задач/доски/пространства и
  «Отписаться» (`muted`), как прямое упоминание. `APPROVAL_REQUESTED` → каждому новому согласующему и
  всем согласующим при сбросе голосов; `APPROVED` (кворум набран) и `REJECTED` (с комментарием) →
  создателю задачи и ведущему исполнителю — тоже обязательно; остальным исполнителям и подписчикам —
  по их уровню. Каждое такое уведомление: запись в центре уведомлений + бейдж (всегда), системное
  уведомление ОС (всегда, кроме «Не беспокоить» — тогда без звука/баннера, но в центре остаётся),
  push на мобильный веб, если он есть для упоминаний. Напоминание: если голос согласующего `pending`
  24 ч — одно повторное `APPROVAL_REQUESTED` (свипер досок, не чаще раза в сутки, максимум 3 раза).
- Задержка уведомления согласующих (настройка доски, по умолчанию 1 мин) и повторный запрос только тем,
  чей отданный голос сброшен правкой (`TaskNotice.re_requested`), — ADR-0082.

### 6. Клиент (`docs/08` «Доски», ориентир — Linear/Jira approvals; D&D обязателен)
- Панель задачи: секция «Согласование» под исполнителями — аватары согласующих со значком состояния
  (✓ `success`, ✗ `danger` с комментарием в подсказке, часы — ждём), строка «Нужно: Все ▾ / 2 из 3»,
  «+ Согласующий» (тот же пикер, что у исполнителей). Для меня-согласующего — кнопки «Согласовать»
  (primary) и «Отклонить» (диалог с обязательным комментарием); после голоса — «Отозвать».
- Карточка на канбане/в списке: бейдж `✓ 1/2` (ждём), зелёный `✓` (согласовано), красный `✗` (отклонено);
  без согласующих — ничего.
- **Перетаскивание**: при drag не-согласованной задачи колонки «дальше» затемняются и не подсвечиваются
  как цель; drop туда — задача возвращается, тост «Нужно согласование: 1 из 2» (или «Отклонено: <имя>»).
  Клиентская проверка — чистая функция `mayMoveTo(task, fromStatus, toStatus)` (для UI), сервер решает.
- Вид «Ждут моего согласования» — пункт в быстрых фильтрах доски; счётчик на иконке доски — позже.
- Мобильный: та же секция в листе задачи; drag на телефоне — как сейчас.

## Последствия
- Протокол меняется (`boards.proto`): `make gen`, генерированный код в коммите; второе ревью (протокол).
- Миграция `00053`, sqlc-запросы, проверка во всех путях смены статуса — один helper в `internal/boards`
  (`checkApprovalGate(task, from, to)`), покрыт интеграционными тестами на каждый путь.
- Боты не согласуют и подчиняются правилу при смене статуса.
- Отложено: шаблон «согласующие по умолчанию» на доске, согласование по этапам (цепочкой),
  дедлайн согласования, согласование гостями.

## Контракт для клиента (сервер готов, 30.09)

Типы — только из `@calaba/protocol` (`boards_pb.ts`), руками не писать.

**Поля задачи** (`Task`, во всех ответах: список, `GET`, `PATCH`, поиск, «Мои задачи», `TASK_CREATE/UPDATE`):
- `approvers: TaskApprover[]` — по `addedAt`; `{userId, state: ApproverState.PENDING|APPROVED|REJECTED, comment, decidedAt?, addedBy, addedAt}`.
- `approvalRequired: number` — `0` = «Все», иначе N (≤ числа согласующих).
- `approvalState: TaskApprovalState.NONE|PENDING|APPROVED|REJECTED` — **читать готовым**, не пересчитывать.
  Кворум для подписи «1 из 2» клиент считает сам: `quorum = approvalRequired === 0 ? approvers.length : Math.min(approvalRequired, approvers.length)`,
  одобрений — `approvers.filter(a => a.state === APPROVED).length`.

**Маршруты** (ответ — `TaskResponse` с полной задачей; остальным приходит `TASK_UPDATE`):
- `PUT /api/tasks/{id}/approvers` `SetTaskApproversRequest {userIds, required}` — полный список (порядок сохраняется) и кворум.
  Право: как правка задачи — `EDIT_TASKS`, или `CREATE_TASKS` у своей/назначенной задачи (иначе `403`); архивная — `409`.
  `422` (`field`): `userIds` / `userIds[i]` — больше 10, дубль, не видит доску, гость, бот; `required` — больше числа согласующих.
  Оставшиеся сохраняют голос; убранные теряют; новые — `PENDING`.
- `POST /api/tasks/{id}/approval` `TaskApprovalRequest {decision: APPROVE|REJECT|WITHDRAW, comment}` — только свой голос.
  Не согласующий — `403`; не видит доску — `404`; бот — `403` reason `BOT_NOT_ALLOWED`; `REJECT` без комментария или комментарий > 500 — `422` (`field: comment`);
  `decision` не задан — `422`. `WITHDRAW` очищает комментарий. Повтор того же голоса — `200` без изменений.
- `POST /api/boards/{id}/tasks` — `approverIds`, `approvalRequired` (те же проверки, поля `approverIds` / `approvalRequired`); создание с согласующими сразу в статусе типа `COMPLETED` — `409 TASK_APPROVAL_REQUIRED` (как блокировка).

**Блокировка** (сервер — арбитр; клиенту `mayMoveTo(task, from, to)` только для подсветки колонок):
`blocked = (approvalState === PENDING || approvalState === REJECTED) && from.id !== to.id && to.type !== CANCELLED && (to.type === COMPLETED || to.position > from.position)`.
Отказ — `409` `code: CONFLICT`, `reason: "TASK_APPROVAL_REQUIRED"`, `used` = одобрений, `limit` = кворум
(при вето — те же числа; кто отклонил и почему — из `task.approvers`, в теле ошибки этого нет). Тост: `used`/`limit` →
«Нужно согласование: 1 из 2»; `approvalState === REJECTED` → «Отклонено: <имя>». Массовые действия — по запросу на задачу:
часть задач может вернуть `409`. Перенос на другую доску не блокируется (кроме попадания не-согласованной задачи в `COMPLETED`).
Удаление статуса с `move_to` «вперёд», где лежит не-согласованная задача, — тоже `409 TASK_APPROVAL_REQUIRED`.

**Сброс:** `PATCH` с новым `title`/`description`/вложениями описания переводит все голоса в `PENDING`
(если в том же `PATCH` есть переход вперёд — он проверяется уже после сброса, т. е. `409`).

**Фильтры** (`TaskField`): `APPROVAL_STATE` — values `"none"|"pending"|"approved"|"rejected"`, ops `IS/ANY_OF/IS_NOT/NONE_OF`;
`APPROVER_PENDING` — values user ids / `"me"`, ops `IS/ANY_OF/IS_NOT/NONE_OF/EMPTY/NOT_EMPTY`.
«Ждут моего согласования» = `{field: APPROVER_PENDING, op: IS, values: ["me"]}`. Локальный фильтр клиента (`lib/boards/filter.ts`)
уже понимает оба поля (состояние — из `approvalState`, pending — согласующие с `PENDING`); в `FILTER_FIELDS` они пока
`hidden` с `kind` `text`/`user` — пикеры и показ в списке полей делает клиентская задача.

**Журнал** (`TaskActivity.kind`): `approvers` — before/after `{user_ids: [], required}`; `approval` — before/after
`{user_id, state: "pending"|"approved"|"rejected", comment}`; `approvals_reset` — before `{approved, rejected}`;
в `created` при согласующих — `after.approvers`, `after.approval_required`.

**Уведомления** (`TaskUpdate.notice.kind`, в `user:<id>`, задача помечается `unread`):
`APPROVAL_REQUESTED` — стал согласующим / голоса сброшены / напоминание (у напоминания `actorId` пустой);
`APPROVED` — кворум набран; `REJECTED` — вето (комментарий — в `task.approvers`).
`APPROVAL_REQUESTED` всем и `APPROVED`/`REJECTED` создателю и ведущему исполнителю сервер шлёт **в обход** уровня задач,
mute пространства и «Отписаться» — клиент обязан показать запись в центре уведомлений + бейдж и системное уведомление ОС
(«Не беспокоить» — только без звука/баннера). Остальным `APPROVED`/`REJECTED` приходят по уровню (как `STATUS`).
Общее правило — `taskNotifies` в `@calaba/protocol` (виды `approval_requested|approved|rejected`, флаг `mandatory`).
Напоминание: голос `pending` 24 ч — раз в сутки, максимум 3; не шлётся по отклонённой, завершённой, архивной задаче.
