# 02 — Медиа: аудио, видео, эффективность

Ориентир по эффективности и качеству — Zoom/Meet. Всё ниже основано на возможностях libwebrtc (Chromium в Electron) и LiveKit OSS.

## Аудио

### Публикация микрофона

| Параметр | Значение | Комментарий |
|---|---|---|
| Кодек | Opus, mono | Стерео не нужно для голоса и удваивает трафик |
| Битрейт | **уровень качества комнаты**: Низкое / Нормальное / Хорошее (default) / Отличное; дефолт задаётся на workspace | Уровень = битрейт **и полоса** Opus, см. «Битрейт (уровни качества)»; клиент берёт значение из `room.media` |

### Битрейт (уровни качества)

В UI — только слова, без чисел (владелец, 28.09). Уровень задаёт комната (`RoomMediaSettings.audio_bitrate_kbps`, дефолт — workspace), личный потолок «Не выше: …» (Настройки → Голос, `UserSettings.audio_bitrate_kbps`, по умолчанию нет) только понижает.

| Уровень | kbps | Полоса Opus (`maxplaybackrate`) | FEC | Звучит как |
|---|---|---|---|---|
| Низкое | 8 | NB, до 4 кГц (8000) | off | телефон; экономит трафик на плохой связи |
| Нормальное | 16 | WB, до 8 кГц (16000) | off | «HD-голос» мобильной связи |
| Хорошее (default) | 32 | SWB, до 12 кГц (24000) | on | обычный звонок в Zoom/Meet |
| Отличное | 64 | FB, до 20 кГц (48000) | on | слышно только с хорошим микрофоном |

- **Почему не только битрейт.** `RTCRtpEncodingParameters.maxBitrate` Chromium для Opus соблюдает, но полосу libopus выбирает сам и уже с ~14 kbps кодирует fullband: 16, 32 и 64 kbps отличались только точностью, на голосе почти неслышно (жалоба 28.09). Слышимая разница — полоса, поэтому уровень ограничивает и её.
- **Как.** libwebrtc настраивает кодер отправки по fmtp *удалённого* описания (ответа SFU): `maxplaybackrate` → `OPUS_SET_MAX_BANDWIDTH`, `maxaveragebitrate` → стартовый битрейт, `useinbandfec` → LBRR. `setCodecPreferences` fmtp не несёт, поэтому `lib/media/opusTier.ts` правит ответ только для m-секции микрофона (обёртка `PCTransport.setRemoteDescription` издателя, ставится на `LocalSenderCreated`, как H.264 в ADR-0032); заодно убирается `stereo=1` из ответа LiveKit — микрофон моно. Плюс `maxBitrate` в encodings.
- **Смена на лету** (ROOM_UPDATE, дефолт workspace, личный потолок): `sender.setParameters` (битрейт сразу) + `engine.negotiate()` (полоса/FEC из нового ответа). Без переподключения и без перепубликации: sid трека и `<audio>` у всех остаются. Раньше уровень брался только при входе в комнату.
- **Старые значения** 24 и 48 kbps (строки до уровней) сервер принимает, клиент показывает и применяет ближайший уровень, при равенстве — верхний (24 → Хорошее, 48 → Отличное).
- **Замер 28.09** (`pnpm -F @calaba/desktop e2e:media -g opus`, dev LiveKit, Chromium, белый шум, исходящий `outbound-rtp` и спектр у слушателя, дБ по полосам 0,3–3,4 / 4–7 / 8,5–11 / 13–19 кГц):

  | kbps | было (только maxBitrate) | стало (уровень) |
  |---|---|---|
  | 8 | 6 kbps · −61 / −110 / −142 / −142 | 5 kbps · −61 / −110 / −142 / −141 |
  | 16 | 12 kbps · −60 / −60 / −60 / −60 (fullband) | 13 kbps · −60 / −61 / **−91** / −141 |
  | 32 | 27 kbps · −60 / −63 / −59 / −58 (fullband) | 28 kbps · −60 / −63 / −58 / **−134** |
  | 64 | 64 kbps · −58 / −58 / −58 / −58 | 59 kbps · −60 / −62 / −58 / −58 |

  Смена 64 → 8 → 32 на лету: 61 → 5 → 28 kbps, спектр следует за уровнем через ~2 с.
- Статистика медиа показывает фактический битрейт микрофона и уровень: «mic 15.8 kbps · Нормальное».

### Эхоподавление — правила, которые нельзя нарушать

1. **Удалённый звук воспроизводится только через `<audio>`-элементы (WebRTC-рендер).** Chromium AEC3 использует как референс только звук, который сам WebRTC вывел. Всё, что пройдёт через WebAudio (`AudioContext`), для AEC невидимо → эхо. Поэтому `webAudioMix: false` (дефолт), никаких «эквалайзеров» на remote-треках.
2. **Смена устройства вывода — через `setSinkId` на тех же `<audio>`**, не пересоздавая пайплайн. После переключения — обязательный тест на эхо (есть исторические жалобы).
3. **Нет двойной обработки.** RNNoise применяем к треку *после* AEC3 (AEC работает на уровне capture-устройства, RNNoise — в worklet поверх результата). Не отключаем встроенный AEC ради «своего». При включённом RNNoise встроенный `noiseSuppression` выключаем (два шумодава подряд дают «булькающий» голос); выключил RNNoise — встроенный включается обратно.
4. **Системный звук при стриме экрана** — главный источник эха: loopback Windows захватывает и голоса участников. Стратегия:
   - Electron `setDisplayMediaRequestHandler` с `audio: 'loopback'` (все платформы, `main/systemAudio.ts`), в constraints `restrictOwnAudio: true`. Chromium тогда открывает устройство `loopbackWithoutChrome`: захват всей системы **без процесса аудиосервиса Calab**. macOS 14.2+ — Core Audio process tap (фича `MacCatapLoopbackAudioForScreenShare`, по умолчанию включена, закрепляем явно), Windows 11 — WASAPI process loopback `EXCLUDE_TARGET_PROCESS_TREE` (Windows 10 — нет, см. ниже). Голоса собеседников в стрим не попадают, ведущий их слышит.
   - **`loopbackWithMute` не использовать никогда** (docs/09 #68): он глушит *весь* локальный вывод, пока идёт захват (macOS — tap с `CATapMuted`, Windows — `IAudioEndpointVolume::SetMute` на устройстве вывода), поэтому ведущий никого не слышит. Вдобавок с ним Chromium игнорирует `restrictOwnAudio`: устройство остаётся `loopbackWithMute`, наш звук попадает в захват.
   - Замер 28.09 (macOS 27, Electron 44.4.5, тон 1 кГц, уровень полосы 1 кГц в захваченном треке через `AnalyserNode`, фон ≈ −80 дБ):

     | Режим | тишина | наш `<audio>` | `afplay` извне | трек |
     |---|---|---|---|---|
     | `loopback` + `restrictOwnAudio` | −78 дБ | **−65…−69 дБ** (исключён) | **−33 дБ** (слышен) | `deviceId: loopbackWithoutChrome`, `restrictOwnAudio: true` |
     | `loopbackWithMute` + `restrictOwnAudio` | −58…−85 дБ | −32 дБ (попадает) | −33 дБ | `deviceId: loopbackWithMute` |
     | `loopback`, `restrictOwnAudio: false` | −83 дБ | −32 дБ | −52 дБ (Glass) | `deviceId: loopback` |
     | `loopback` + restrict, `--disable-features=MacCatapLoopbackAudioForScreenShare` | −63 дБ | −32 дБ (попадает) | −34 дБ | ScreenCaptureKit, `restrictOwnAudio: false` |

     Флагов `MacLoopbackAudioForScreenShare` / `MacSckSystemAudioLoopbackOverride` в Chromium 152 нет, прежний спайк (−11,7 дБFS «не исключается») мерил `loopbackWithMute`. После остановки стрима tap закрывается, наш тон в системном миксе снова −32 дБ (тот же уровень, что до захвата; сторонний наблюдатель-процесс). `<audio>`-элементы собеседников стрим не трогает.
   - Проверка на лету: `ownAudioExcluded(track.getSettings())` (`restrictOwnAudio: true` или `deviceId: loopbackWithoutChrome`); если нет — предупреждение в лог. macOS < 14.2 (нет process taps → ScreenCaptureKit без исключения) — `systemAudioLoopback: 'experimental'`: звук по умолчанию выключен, в пикере предупреждение, что собеседники попадут в стрим. Linux — не поддерживается.
   - **Windows: системный звук без своего голоса собеседников** (docs/09 #122; по исходникам Chromium 152.0.7977.130 / Electron 44.4.5, на живой Windows не мерили). Electron при `restrictOwnAudio` меняет `loopback` на `loopbackWithoutChrome` (`shell/browser/electron_browser_context.cc`, ветка и для `IS_WIN`); WASAPI открывает его как process loopback с `TargetProcessId` = процесс аудиосервиса и `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` (`media/audio/win/audio_low_latency_input_win.cc`) — наши `<audio>` в захват не попадают. Но Blink передаёт `restrictOwnAudio` в браузер, только если `media::IsRestrictOwnAudioSupported()` (`third_party/blink/.../user_media_request.cc`), а на Windows это `IsWindowsProcessLoopbackCaptureSupported()` = `base::win::GetVersion() >= WIN11` (`media/base/media_switches.cc`). На **Windows 10** флаг молча сбрасывается, устройство остаётся `loopback` (весь вывод) — голоса собеседников уходят в стрим. Другого пути нет: системный пикер (`useSystemPicker`) в Electron только для macOS и идёт через тот же флаг, `applicationLoopback` — тот же process loopback. Поэтому `systemAudioSupport` на Windows: сборка ≥ 22000 (`process.getSystemVersion()`) — `supported`, иначе `experimental`: звук по умолчанию выключен, в пикере предупреждение «Windows 10: звук участников тоже попадёт в стрим». Приглушать собеседников у ведущего не делаем (ведущий должен слышать людей).
5. **Опциональный OS-AEC** (macOS voice processing) — сравнить с AEC3 на тесте с 3 говорящими и колонками. Включается `CALABA_SYSTEM_AEC=1` (фича `EnforceSystemEchoCancellation`, см. «Эхо: колонки»), по умолчанию выключен.
6. **Приглушение микрофона («Динамики») — только на входном пути:** GainNode стоит после AEC3 и RNNoise, перед публикацией. Выход не трогаем.

### Шумоподавление

- **RNNoise (WASM в AudioWorklet)** — несколько сотен КБ; бодрствующий — ≈ 7 % ядра Apple M4 (замер, docs/14-energy.md), на слабом CPU кратно больше. **Выключен по умолчанию** (владелец, 27.09: экономия CPU на слабых машинах; работает встроенный `noiseSuppression` Chromium), включается в настройках или поповере шумоподавления; пока он включён, встроенный `noiseSuppression` выключен. **Работает по требованию** (`lib/media/denoiseSleep.ts`): всегда — пока микрофон в эфире (гейт открыт, PTT зажат или хвост отпускания) или на экране индикатор уровня; в режиме «голос» при закрытом гейте засыпает через 2 с сырого уровня ниже «порог − 3 дБ» (такой кадр гейт открыть не может — ему нужен уровень *после* шумодава выше порога) и просыпается на первом громком кадре, прогнав через RNNoise 50 мс предыстории; PTT отпущен или mute — выключен. Захват не останавливается никогда (AEC3 продолжает сходиться); во сне worklet отдаёт тишину (трек и так выключен) и шлёт уровень раз в 100 мс вместо 20.
- Бонус: RNNoise выдаёт вероятность речи → используем как **VAD** для voice-activation (см. ниже), не пишем свой детектор.
- **DeepFilterNet3** — вариант «повышенного качества» на будущее (тяжелее, ~12 MB модель).
- Krisp в LiveKit — только Cloud, нам недоступен.

### Режимы микрофона

**Voice activation (по умолчанию):**
- Сигнал: VAD-вероятность RNNoise + RMS-порог (настраиваемый слайдер).
- Гистерезис: открыть при p > 0.6 в течение 2 фреймов, закрыть после 400 мс тишины (hangover). Иначе будут обрубаться концы слов.
- Когда «закрыт» — трек не unpublish'ится и **не мьютится в LiveKit**: выключается только `mediaStreamTrack.enabled` (отправляется тишина, Opus DTX ≈ 0), так что открытие мгновенное и нет сигнализации. `track.mute()` (видимый всем «микрофон выключен») — только явный self-mute/deafen: сервер выводит `muted` в voice-state из mute микрофонного трека (webhooks), и мьют по VAD превращал бы каждую паузу в событие для всех участников (реализация этапа 3, см. «Клиент: факты реализации»).
- В UI — индикатор уровня и порог (как в Discord).

**Push-to-talk:**
- Глобальная клавиша через `uiohook-napi` в main-процессе (keydown → unmute, keyup → mute), IPC в renderer.
- macOS: нужны разрешения Accessibility/Input Monitoring — при первом включении PTT показываем подсказку.
- Linux Wayland: uiohook видит только X11/XWayland. На GNOME/KDE — XDG GlobalShortcuts portal (Electron 44+). На Sway/Hyprland глобального PTT нет — PTT работает только при фокусе окна, честно сообщаем.
- **Задержка отпускания** — настройка `prefs.pttReleaseMs` («Голос и устройства», ползунок 0, 20, 50, 100, 250, 500, 750, 1000…2000 мс; по умолчанию **20 мс**, как в Discord; из «Горячих клавиш» — ссылка). До 0.3.x хвост был зашит в 200 мс и к нему прибавлялось удержание кольца «говорит» 300 мс (`lib/speaking.ts`) — владелец видел выключение через 0,5–1 с. Теперь: отпускание клавиши (hold) → `lib/pttRelease.ts` держит эфир N мс; повторное нажатие в окне отменяет выключение (гейт не закрывался — ни щелчка, ни сигнализации). По истечении гейт закрывается **синхронно**: `mediaStreamTrack.enabled = false` первым действием `applyTransmit`, до обновления стора/кольца/дака и не дожидаясь идущего `mute()`/`unmute()` LiveKit; моё кольцо в режиме PTT гаснет в тот же тик (без 300 мс удержания; в режиме VAD удержание остаётся). Без задержки: режим «переключение» (`PttEvent.immediate`), сброс гейта (смена биндинга, сон), mute/deafen/выход — обрывают хвост сразу. Замер в DevTools: `[ptt] key-up → gate closed { ipcMs, gateMs, releaseMs }` (console.debug). У собеседников кольцо — от LiveKit ActiveSpeakers и локального уровня входящего звука (+200 мс удержания, см. «Индикация речи собеседников») — звук при этом уже тишина.
- Клавиша захватывается тоже в main (uiohook), а не DOM: подходит любая — F13–F24, одиночные ⌘/⌥/⌃/⇧, Numpad, Caps Lock, кнопки мыши 3–5. Храним код uiohook + тип (`key`/`mouse`) + режим (`hold`/`toggle`); имя клавиши считается из кода (`shared/pttKeys.ts`). На вебе — DOM-фоллбек, только пока вкладка активна.
- **Caps Lock на macOS** (`patches/uiohook-napi@1.5.5.patch`): основной путь — **IOHIDManager-слушатель** клавиатур в darwin-части патча (usage page 0x07, usage 0x39), на том же run loop, что и CGEventTap. Он видит физическое нажатие/отпускание Caps Lock независимо от «Caps Lock переключает раскладку» (tap при этой настройке не получает ничего, а F18 от `hidutil`-ремапа до tap тоже не доходил — владелец, 0.2.1); так же делает Discord. Событие приходит как код 58 с `source: 'hid'` (бит `CALABA_EVENT_SOURCE_HID` в `reserved`; в JS у key-событий есть `source`, `rawcode`, `mask`). Tap и HID сводятся в `shared/keySource.ts`: дубль текущего состояния отбрасывается, а после первого HID-события клавиши её tap-копии игнорируются (поздняя tap-копия иначе нажала бы клавишу повторно). Захват: HID Caps Lock → сразу «удержание, source hid»; режим переключения работает через `mode: 'toggle'`. Слушателю нужен «Мониторинг ввода»: при неопределённом статусе вызывается `IOHIDRequestAccess` (вне потока хука), статус — `PttStatus.hid` (`running` / `denied` / `restart`), в биндере подсказка и кнопка «Открыть настройки ОС». Старые биндинги (≤ 0.2.1: ремап Caps → F18 и смена замка `0x0F3A`) при работающем HID слушают физический Caps Lock (`resolveKeyBinding`), `hidutil` не трогается. **Фолбэк без HID** (нет разрешения): прежний путь — смена замка `0x0F3A` (только переключение), проба 350 мс на настоящее нажатие (код 58 из `NX_SYSDEFINED`), ремап Caps → F18 на время захвата и опция «Caps Lock не меняет регистр» (`hidutil`, чужие `UserKeyMapping` сохраняются, оригинал в `<userData>/ptt-remap.json`, восстановление при снятии биндинга, выходе и после краша). Диагностика: пока захват взведён, main пишет в лог каждое сырое событие (`[ptt] raw { source, keycode, rawcode, flags, down }`), а биндер показывает «Последняя нажатая клавиша: … (источник)». `check-native.mjs` требует в macOS-бинаре маркеры `CALABA_UIOHOOK_PATCH_V2` и `CALABA_HID_CAPS_V1`.
- Тот же патч исправляет баг libuiohook на macOS: отпускание кнопок мыши 3–5 приходило как нажатие, и PTT на боковой кнопке не отпускался.
- Windows / Linux X11: Caps Lock приходит из хука обычным нажатием/отпусканием (код 58) → удержание, путь общий. Wayland: хука нет, портал GlobalShortcuts Caps Lock не поддерживает — в биндере подсказка.

**Одно устройство в голосе** (владелец, 29.09; docs/05 «Несколько устройств»): вход в голос с другого устройства выводит из голоса предыдущее (`VOICE_DISCONNECTED{OTHER_DEVICE}`) — два устройства одного человека в одной комнате (эхо, двойной звук) больше не встречаются.

**Звонок один на один (ADR-0034):** голос звонка — тот же тракт, что в комнате (`voice.join(dmRoomId, '', { call: true })`, remote-звук через `<audio>`, AEC3 → RNNoise). На время звонка режим принудительно «по голосу»: `micModeFor(prefs.micMode, call)` (`lib/voiceLogic.ts`), PTT-биндинг снимается (`platform.ptt.setBinding(null)`), клавиша игнорируется, в островке и меню микрофона нет PTT; выбор пользователя в prefs не меняется и возвращается, когда сессия звонка закрыта. Гудок и рингтон (`call-outgoing` / `call-incoming`, MP3 из `tools/gen-event-sounds.py`) — тоже простые `<audio>` на устройстве вывода, не WebAudio.

### Воспроизведение

- Каждый remote-трек → свой `<audio autoplay>`; громкость по участнику (`element.volume`), локальный мьют участника.
- **Deafen** (docs/09 #70, issues #11/#12). Семантика Discord (`lib/voiceLogic.ts`): deafen ⇒ микрофон выключен, состояние микрофона до deafen запоминается (`mutedBeforeDeafen`), снятие deafen возвращает его (был выключен — остаётся выключенным; модераторский mute — остаётся). Кнопка микрофона при deafen снимает и deafen, и mute. PTT при mute/deafen игнорируется: гейт не открывается, звуков `pttOn`/`pttOff` нет; deafen при зажатой клавише выключает PTT сразу, без звука. Заглушение — только `element.muted`/`volume` (без WebAudio), и пишет их **одно место** — `lib/media/remoteAudioOut.ts` (`RemoteAudioOut`): при каждом attach (новый участник, реконнект, смена комнаты), после каждой смены устройства вывода, на `devicechange` (macOS переключает выход при подключении зарядки/дока), на `RoomEvent.ActiveDeviceChanged` (LiveKit сам делает `setSinkId` на наших элементах) и на `volumechange`, если значение не наше (LiveKit `Room.startAudio()` ставит `muted = false` всем remote-элементам). После смены sink громкость «проталкивается» в плеер заново, даже если атрибуты не изменились. Утечка до исправления: на смене вывода muted/volume не переприменялись, а LiveKit менял sink в обход нас. **Плюс deafen = ничего не принимаем** (02.10, жалоба на 2.0.0 «при deafen иногда слышно некоторых коллег»): `applyAudioSubscriptions` (`services/voice.ts`) снимает подписку со всех микрофонов и со звука стрима, undeafen возвращает (один круг сигнализации); новый микрофон при deafen не подписывается. Причина: Chromium микширует все удалённые WebRTC-приёмники в один вывод (`WebRtcAudioRenderer`), `muted` элемента обнуляет только те приёмники, которые этот элемент играет, а приёмник, который ещё не играл ни один элемент, звучит с усилением 1.0, пока играет любой другой (заглушённый тоже) элемент. У LiveKit есть пути, где подписанный трек остаётся без элемента: `TrackSubscribed` отложен на время `Reconnecting`, публикация не найдена → `TrackSubscriptionFailed`. Без подписки SFU ничего не шлёт — утекать нечему, заодно нет декодирования Opus и трафика. Кольца «говорит» при deafen — от ActiveSpeakers сервера.
- Стерео-панорамирование не делаем (потребовало бы WebAudio → ломает AEC).

### Индикация речи собеседников

Зелёное кольцо у собеседника горит, если **любой** из двух источников говорит «речь» (OR; несколько устройств человека — одно кольцо на userId):
- **Сервер** — LiveKit `ActiveSpeakersChanged`. Конфиг `audio` в `infra/docker/livekit/livekit.yaml.tpl`: `active_level: 40` (шкала 0–127 в −dBov, 0 — громче всего: больше значение — тише допустимая речь; дефолт 35, прежние 30 отсекали тихих), `min_percentile: 40`, `update_interval: 150` мс (было 400), `smooth_intervals: 2`. До этого кольцо запаздывало на 0,4–0,8 с и у тихих не зажигалось вовсе.
- **Клиент** — уровень входящего звука без WebAudio (правило эха 1): раз в 100 мс RFC 6464 `audioLevel` (0..1) из `RTCRtpReceiver.getSynchronizationSources()` каждого remote-микрофона (`lib/remoteSpeaking.ts`, unit-тесты). Включение — два замера подряд ≥ 0,02 (≈ −34 dBov), выключение — < 0,01 (≈ −40 dBov) 250 мс подряд, между порогами состояние держится (гистерезис). Уровень старше 250 мс — тишина. Трек судится отдельно (два устройства — два трека). Один `setInterval` на комнату, запускается подпиской на remote-микрофон и сам останавливается, когда читать нечего. Нет `getSynchronizationSources` (веб в Firefox/Safari) — только серверный источник. Громкость/локальный мьют участника на кольцо не влияют (меряем то, что прислал отправитель).
- Дальше общий путь `lib/speaking.ts`: появление сразу, удержание **200 мс** (было 300), батч store 50 мс. Моё кольцо — по-прежнему локальный VAD/PTT.

### Эхо: колонки

Жалоба владельца: «в Discord собеседник слышит себя через мои колонки, в Zoom — нет». Zoom на колонках работает в полудуплексе: пока говорит собеседник, микрофон приглушён. Discord (Chromium AEC3) остаётся в полном дуплексе, и хвост эха, который AEC не вычел, уходит обратно.

**Аудит пути (2026-09-26, нарушений не найдено):**
- Захват: `audioCaptureConstraints` (`packages/protocol/src/media.ts`): `echoCancellation: true`, `autoGainControl: true`, `noiseSuppression` = `!rnnoise`, mono. Что применил браузер, пишется в лог: `[mic] capture settings {echoCancellation: true, …}` (`micPipeline.ts`, `track.getSettings()`).
- RNNoise/VAD-worklet и новый GainNode работают на выходе getUserMedia (это уже результат AEC3). Встроенная обработка не заменяется.
- Удалённый звук: `webAudioMix: false`, каждый трек → `track.attach()` → `<audio>` в `#remote-audio-sink`, громкость только `element.volume`/`muted`. У видео `<video muted>`. `AudioContext` в renderer один — у микрофона (вход). LiveKit создаёт свой контекст, но только для локальных треков, к remote он не подключён.
- Вывод: `setSinkId` на тех же `<audio>` (`applyOutputDevice`, при attach). Chromium передаёт устройство WebRTC-рендера в захват (`SetOutputDeviceForAec`), и опорный сигнал AEC идёт с того же устройства. Звуки интерфейса — `<audio>` на том же устройстве. При Chrome-wide AEC они тоже попадают в опорный сигнал.

**Флаги Chromium** (`src/main/echoFeatures.ts`). Имена проверены по строкам Electron Framework 44.4.5 = Chromium 152.0.7977.130. В новом макросе `BASE_FEATURE` имя хранится как `kИмя`.

| Фича | В 152 | Что делаем |
|---|---|---|
| `ChromeWideEchoCancellation` | есть, вкл. по умолчанию | закрепляем явно: AEC3 в audio service, опорный сигнал — весь звук Chromium на устройство вывода |
| `WebRtcAudioNeuralResidualEchoEstimation` | есть | **включаем**: нейросетевая оценка остаточного эха в AEC3 (как раз «хвост» на колонках). Если модель не загрузится, Chromium пишет `Failed to initialize neural residual echo estimator.` и работает как раньше. Выключить: `CALABA_NEURAL_AEC=0` |
| `EnforceSystemEchoCancellation` (параметры `allow_agc_in_tandem`, `allow_ns_in_tandem`) | есть | opt-in `CALABA_SYSTEM_AEC=1`: системный AEC вместо AEC3. На macOS это VoiceProcessingIO, как в FaceTime (в бинаре `OpenVoiceProcessingAU`). Он приглушает звук других приложений и меняет тембр, поэтому не включён по умолчанию |
| `SystemLoopbackAsAecReference` | есть | не включаем: опорный сигнал — весь системный микс (эхо *чужих* приложений), это не наш случай |

Как проверить, что всё активно (`chrome://media-internals` в приложении нет):
1. `logs/main.log`: `chromium features { enable: [ChromeWideEchoCancellation, WebRtcAudioNeuralResidualEchoEstimation, …] }`.
2. Тот же `logs/main.log`: `[renderer] [mic] capture settings {"echoCancellation":true,"autoGainControl":true,…}`.
3. Dev-статистика (Настройки → О программе → «Статистика медиа»), строка `aec erl … erle … dB · echo r …`. `erl`/`erle` — `media-source` из `RTCRtpSender.getStats()`. Chromium заполняет их только когда публикуется сам трек getUserMedia, то есть при выключенном шумоподавлении в режиме «Наушники». С RNNoise там «—». `echo r` — корреляция детектора (ниже), считается всегда.
4. Нейросетевой оценщик: запуск с `--enable-logging=stderr --v=0`. Строки `Failed to initialize neural residual echo estimator` быть не должно.

**Детектор «собеседник слышит себя»** (`lib/media/echo.ts`, `EchoRiskDetector`, unit-тесты на синтетике). Каждые 50 мс: уровень удалённых голосов — RFC 6464 `audioLevel` из `RTCRtpReceiver.getSynchronizationSources()` × `element.volume` (без WebAudio на remote). Плюс уровень моего микрофона после AEC/RNNoise и признак «в эфире». Раз в 2 с (вместе с getStats) — два независимых признака:
- **ERLE**, если Chromium его отдаёт: ERLE < 6 дБ при ERL < 20 дБ, пока собеседник говорит (≥ 50 % периода), а мой микрофон в эфире (≥ 30 % его речи), 5 с подряд. Порог: сошедшийся линейный фильтр AEC3 на колонках ноутбука даёт 10–25 дБ. Ниже 6 дБ фильтр не сошёлся: не совпал опорный сигнал или задержка, дрейф часов, искажают динамики. ERL ≥ 20 дБ — это наушники, там низкий ERLE значит «нечего вычитать».
- **Корреляция** (работает всегда, в том числе с RNNoise): окно 5 с, огибающая того, что я *отправляю*, повторяет огибающую собеседника с задержкой 0–400 мс (r ≥ 0,6). При этом хотя бы в 40 % его речи я в эфире выше −60 dBFS, и так два окна подряд (≈ 7 с). Одновременная речь даёт r ≈ 0, диалог по очереди — r < 0, эхо — r → 1. Детектор меряет ровно то, что слышит собеседник: после AEC, RNNoise и гейта. Эхо, которое не открывает гейт или не уходит при отпущенном PTT, не считается.

Признак держится до конца звонка, сбрасывается сменой микрофона или устройства вывода (duck снижает то самое эхо, которое меряем; без «липкости» он бы включался и выключался). Результат — `voice.echoRisk`. Тост показывается один раз за звонок, переподключение — не новый звонок. В «Наушниках»: «Похоже, собеседник слышит себя. Наденьте наушники или включите режим «Динамики»» с кнопкой «Включить «Динамики»».

**Режим «Как вы слушаете»** (Настройки → «Голос и устройства» → «Колонки и эхо», per-device `prefs.echoMode`):
- **Наушники** (по умолчанию): без приглушения. Без RNNoise публикуется сырой трек getUserMedia, как раньше.
- **Динамики**: пока говорит собеседник (уровень ≥ 0,02 ≈ −34 dBov, удержание 150 мс), мой микрофон −18 дБ. Атака 20 мс, отпускание 300 мс (`setTargetAtTime` на GainNode). Не до нуля: перебить собеседника можно, он услышит, просто тише. Уровень для гейта и индикатора берётся до приглушения.
- **Авто**: как «Динамики», но только после `echoRisk`.
- PTT: пока клавиша нажата, приглушения нет — человек сам взял слово. Deafen — тоже нет, мы ничего не воспроизводим.
- GainNode — на входном пути (`micPipeline.ts`): `worklet (RNNoise) → gain → MediaStreamDestination`. Без RNNoise граф есть только в «Динамики»/«Авто». Смена режима пересобирает захват и меняет трек через `replaceTrack`, без republish.

**«Проверка эха»** (там же, кнопка «Проверить», во время звонка неактивна). 3 с тестового сигнала: синтетическая гласная, основной тон 110–190 Гц, гармоники до 3,4 кГц, −28 dBFS. Шум не подходит: RNNoise и NS убрали бы его как шум. Первая секунда — непрерывно, чтобы AEC сошёлся. Потом 2 с вспышек по фиксированному неровному шаблону. Играет **тем же путём, что и голоса**: WebAudio-источник → RTCPeerConnection-петля внутри страницы → `<audio>` с `setSinkId`. Если петля не поднялась, играет `<audio>` с WAV. Одновременно пишется микрофон с настройками пользователя (AEC3 + RNNoise/NS), уровни по 20 мс. Оценка (`lib/media/echoCheck.ts`, unit-тесты): корреляция с шаблоном при задержке 0–400 мс и разница «вспышка − пауза».
- r < 0,3, или < 3 дБ, или возврат < −65 dBFS → «Эхо не обнаружено».
- ≥ 10 дБ и возврат выше порога активации → «Сильное эхо» (собеседник услышит себя) → «наденьте наушники / режим «Динамики»».
- Остальное → «Слабое эхо» → «сделайте колонки тише / режим «Авто»».

### Режим музыканта (ADR-0052)

Живой инструмент и пение без речевой обработки. Личный переключатель на время звонка (`prefs.musicianMode`, не сохраняется, выключается при выходе из голоса): «Голос и устройства» → «Обработка» и пункт меню «…» голосовой панели. Только тариф Team и выше (`PlanLimits.musician_disabled`, docs/04), на Free — под замком.

| | Голос (как было) | Режим музыканта |
|---|---|---|
| `echoCancellation` / `noiseSuppression` / `autoGainControl` | true / `!rnnoise` / true | false / false / false (`musicianCaptureConstraints`) |
| `voiceIsolation` | дефолт | false |
| Каналы захвата | 1 | `{ideal: 2}`: стерео, если устройство стерео |
| RNNoise | по настройке | выключен (настройка сохраняется) |
| Opus (ответ SFU, `opusTier.ts`) | уровень комнаты, моно, `usedtx=1` | `stereo=1` (кодер libwebrtc в режиме AUDIO, без речевого ФВЧ), `maxplaybackrate=48000`, `useinbandfec=1`, `usedtx=0` |
| Битрейт | 8–64 кбит/с | 128 (моно-источник) / 192 (стерео), уровень комнаты и личный потолок не действуют; лимит звука тарифа — действует |
| `contentHint` | — | `music` |
| Гейт VAD | глушит паузы | не глушит (микрофон открыт); кольцо «говорит» — по порогу, PTT остаётся PTT |

- **Смена на лету**: `restartMic` (новый захват, `replaceTrack`) + `applyMicTier` (`setParameters` + ренеготиация с новым fmtp, включая `usedtx`) — без перепубликации. Проверено `tools/perf-call.ts --bench C [--musician]`: голос — `maxaveragebitrate=32000;maxplaybackrate=24000;usedtx=1;useinbandfec=1`, 1,4 кбит/с в тишине; музыкант (фейковый стерео-захват) — `maxaveragebitrate=192000;maxplaybackrate=48000;stereo=1;usedtx=0;useinbandfec=1`, 9,2 кбит/с в тишине.
- **Правила эха не нарушаются**: режим меняет только входной путь; удалённый звук — те же `<audio>`, WebAudio на выходе нет. Но без AEC звук собеседников из колонок возвращается к ним, поэтому: при включении — «Нужны наушники…», устройство вывода с «динамиковым» названием (`lib/media/outputKind.ts`) — усиленное липкое предупреждение с «Выключить режим музыканта»; тост `EchoRiskDetector` в этом режиме предлагает выключить режим. Приглушение «Динамики»/«Авто» работает, если выбрано. `ChromeWideEchoCancellation` применяет AEC3 только к захватам с `echoCancellation: true` — другие захваты (проверка эха, голосовые сообщения) не меняются.
- **Другим видно**: `VoiceState.musician` (docs/05) — гитара у имени в комнате и в панели участников, «Режим музыканта: звук без обработки»; у себя — строка в голосовой панели с «Выключить».
- CPU — docs/14 «Режим музыканта».

### Голосовые сообщения (docs/09 #43)

- **Формат** — Ogg/Opus, моно, 48 кГц, VBR ~24 кбит/с, `application=voip`, кадр 20 мс, страница Ogg ≈ 1 с: речь разборчива, вес как у Telegram. Замер (фейковый микрофон Chromium, 10 с): 29,7 КБ → **≈ 24 кбит/с, ≈ 180 КБ за минуту**, 5 мин ≈ 0,9 МБ (лимит сервера 1,5 МБ).
- **Почему не MediaRecorder**: Chromium/Electron пишет только WebM/Opus, а его не играет Safari; Ogg/Opus — стандартный контейнер голосовых. Кодируем на клиенте WASM: `opus-recorder` 8.0.5 (MIT; libopus 1.3.1 и speexdsp — BSD, тексты в THIRD-PARTY-NOTICES) — его `encoderWorker.min.js` работает как AudioWorklet (`encoder-worklet`) и сам муксит Ogg; грузится лениво при первой записи (385 КБ, `?url`-ассет, CSP уже разрешает `'wasm-unsafe-eval'`).
- **Захват** — отдельный `getUserMedia` (устройство из настроек, `echoCancellation`, `noiseSuppression`, `autoGainControl`, моно), свой `AudioContext` 48 кГц (Firefox с другой частотой устройства — контекст на частоте устройства, энкодер ресэмплит). Граф только входной: источник → энкодер-ворклет и `AnalyserNode` (уровень раз в 50 мс → живой индикатор и волна ≤ 100 столбиков); к `destination` ничего не подключено — правило эха 1 не затронуто. Пайплайн звонка не трогаем: мьют/PTT/гейт звонка запись не глушат, громкость собеседников не меняется; играющий трек чата ставится на паузу.
- **Воспроизведение** — общий плеер чата (`<audio>` + `setSinkId`). `canPlayType('audio/ogg; codecs=opus')`: Electron/Chromium и Firefox — `probably`; Safari/iOS — Ogg появился только в **18.4** (macOS 15.4, iOS 18.4): на Safari 17–18.3 Opus есть лишь в MP4/CAF, поэтому там вместо play — «Скачать».

### Звуки в комнату (саундборд, ADR-0036)

- **Клип не идёт через медиа-трек.** Нажатие — `POST /api/rooms/{id}/sounds/play {sound_id}`; сервер шлёт `SOUND_PLAY {room_id, sound_id, user_id, at}` тем, кто в звонке этой комнаты (их user-каналы), и каждый клиент играет клип **сам**: обычный `<audio>` (пул из 4 элементов, `services/soundboard.ts`) на выходном устройстве голоса (`setSinkId`) — никакого WebAudio на выходе и ничего в микрофонном треке (правило эха 1; клип не пережимается кодеком 8–64 кбит/с, не глохнет при мьюте, не ломает VAD/DTX).
- **Громкость**: «Громкость звуков» 0–200 % × громкость наушников ▾; `element.volume` ≤ 1, поэтому выше 100 % — только компенсация убавленной общей громкости (как у громкости участника). «Слабый компьютер» не влияет.
- **Кто слышит**: все в звонке, нажавший тоже; «звук выключен» (deafen) — никто из клипов; «Не воспроизводить звуки других» — только свои нажатия. Серверный мьют нажимать не мешает.
- **Опоздавшие**: событие, пришедшее позже 3 с после `at`, пропускается (повтор после переподключения). Часы не сравниваются в лоб: задержка считается от лучшей задержки последних 16 событий (`lib/soundboard.createLateness`) — отстающие на минуты часы звуки не глушат.
- **Клипы**: встроенные — `assets/sounds/*.ogg` + `manifest.json` (сейчас 6 клипов владельца; `tools/import-sounds.mjs <dir>` пересобирает набор, `tools/gen-sounds.mjs` — синтетическая замена на случай без исходников); пространства — файлы, которые сервер сам делает из загрузки админа. Формат обоих — Ogg/Opus 48 кГц моно, 96 кбит/с, `loudnorm` −16 LUFS (TP −1,5 dBTP), ≤ 5 с (длиннее — обрезается), ≤ 200 КБ: `ffmpeg` образа api (статический 8.0, общий с HEIC-конвертацией и его единственным слотом), таймаут 20 с, временный каталог; локальный импорт встроенных — тот же набор аргументов (`files.SoundArgs`). На Safari < 18.4 Ogg не играет (как у голосовых сообщений).

### Захват

- `desktopCapturer` + собственный пикер (экраны/окна с превью). На Wayland — портал PipeWire показывает свой пикер, свой скрываем.
- Максимальный пресет и лимит стримов задаются на комнате (`room.media.maxStreamPreset`, `maxStreams`), пользователь выбирает пресет не выше разрешённого.
- Пресеты (выбор в UI, запоминается). **Битрейт — потолок, не расход**: кодек шлёт только изменившиеся области, статичный текст/код — обычно 50–300 kbps, потолок достигается только на видео/анимации (у Zoom «50–150 kbps на шаринг» — именно средний расход статики):

| Пресет | Разрешение | FPS | Потолок AV1/VP9 | Потолок H.264, `detail` (+40 %) | Типичный расход (текст/код) |
|---|---|---|---|---|---|
| Экономия | 1280×720 | 5 | 0.4 Mbps | 0.56 Mbps | 30–100 kbps |
| 720p | 1280×720 | 15 | 1.0 Mbps | 1.4 Mbps | 50–200 kbps |
| 1080p (по умолчанию) | 1920×1080 | 15 | 2.0 Mbps | 2.8 Mbps | 80–300 kbps |
| original | нативное (Retina → 2560×1600+) | 30 | 4.0 Mbps | 5.6 Mbps | 100–500 kbps |

- H.264 сжимает текст хуже AV1, поэтому у `detail`-стрима в H.264 оба слоя получают +40 % к потолку (слой превью 250 → 350 kbps; ADR-0032 §4, `screenBitrate`). У `motion` потолки те же.
- Автору при `qualityLimitationReason: bandwidth` (getStats) предлагаем переключиться на «Экономию».
- **Зритель не зависит от пресета автора**: SVC + оценка полосы (TWCC) → SFU отдаёт зрителю тот слой, что влезает в его канал (роуминг/мобильный интернет → ~480p/5fps, 150–300 kbps), автор ничего не меняет.
- `contentHint`: `'detail'` по умолчанию (текст/код — держим резкость, жертвуем fps); `'motion'` — переключатель «видео/игра».
- Режим масштабируемости зависит от `contentHint`:
  - `detail` → **`L1T3`**: одно пространственное разрешение, 3 временных слоя. Текст всегда резкий, медленному зрителю SFU срезает fps, а не разрешение.
  - `motion` → **`L3T3_KEY`**: 3 пространственных × 3 временных слоя, зритель на слабом канале получает меньшее разрешение с плавностью.
  - Следствие: для `detail`-стримов adaptive stream не может дать превью низким разрешением — миниатюра тянет полное разрешение с низким fps. Медиа-спайк (этап 1) обязан замерить, не лучше ли компромисс `L2T3_KEY`; это открытый пункт в docs/07.
- FPS 15 для текста практически неотличим от 30, но вдвое дешевле; при статичном экране кодек сам опускает fps до 1–5.

### Кодек (ADR-0032: по железу)

- **Выбор при публикации** стрима и камеры — `pickPublishCodec(kind, pref)` (`lib/media/codecSelect.ts`): `navigator.mediaCapabilities.encodingInfo({type: 'webrtc', video: {contentType, width, height, framerate, bitrate}})` для H.264 → AV1 → VP9, берётся первый с `powerEfficient: true` (аппаратный энкодер). Ответ кэшируется на сессию.
- **Аппаратного энкодера нет** → самый дешёвый программный: для экрана **AV1** (libaom со screen-content tools, ~45 % лучше VP9 по тексту), для камеры **VP9**. Не H.264: на M4 в Electron 44 OpenH264 на стриме 720p15 стоит 38,7 % ядра против 23,2 % у AV1 (docs/14 «Кодек по железу»). Это поправка к ADR-0032 §1 («иначе H.264»), см. заметку в ADR.
- **Вне Chromium** (веб-клиент в Firefox/Safari) — только H.264 или VP8: rid-simulcast VP9/AV1 со `scalabilityMode` там ненадёжен.
- **Настройка «Кодек стрима»** («Голос и устройства → Показ экрана», и она же в «Дополнительно» пикера): «Авто (по железу)» — по умолчанию; «Качество текста (AV1)» — выше качество текста, больше CPU у автора и у зрителей без аппаратного AV1-декодера; «Совместимость (H.264)» — аппаратное декодирование у всех зрителей. Хранится в prefs (`streamCodec`). Камера всегда «Авто».
- **Слои**: H.264 — обычный rid-simulcast (у H.264 нет SVC), `q` 640×360 + пресет; livekit-client 2.22 на этом пути `contentHint: detail` не трогает (он переписывает его только для SVC без simulcast). AV1/VP9 — «SVC simulcast», `L1T3` на каждом rid (ниже).
- **Без `backupCodec`**: у LiveKit один кодек на трек, зритель декодирует опубликованный. Декодирование H.264/VP9/AV1 на M4 — аппаратное, VP8 — программное.
- **Диагностика**: `StatsOverlay` пишет «enc H264 High hw · dec AV1 hw» — кодек и профиль H.264 из getStats (`sdpFmtpLine`), hw/sw по `encodingInfo`/`decodingInfo`; в строках слоёв — `encoderImplementation` (`VideoToolbox`, `OpenH264`, `libaom`) и размер.

#### Профиль H.264: High по умолчанию (docs/09 #67, 28.09)

- **Почему High.** LiveKit v1.13 регистрирует H.264 как Constrained Baseline `42e01f` (первым) и High `640032` и упорядочивает ответ издателю по этому списку. Без вмешательства любой H.264-стрим уходит в CB, а Chromium на macOS не отдаёт CB аппаратному кодировщику (`IsH264ConstrainedBaselineProfileAvailableForAcceleratedEncoder`, только Windows/Linux/ChromeOS/Android) — кодирует OpenH264. High `64001f` кодирует VideoToolbox на обоих слоях: 720p/15 40,8 → 12,4 % ядра (docs/14 «Аппаратный H.264 на macOS»). На Windows/Linux High тоже аппаратный (Media Foundation / VA-API), CABAC и 8×8 дают текст лучше при том же битрейте.
- **«Авто»** пробует `encodingInfo` с `video/H264; profile-level-id=64001f; packetization-mode=1` (голый `video/H264` значит `42e01f` и на Mac всегда `powerEfficient: false`). Если High аппаратный — «Авто» = **H.264 High hw** и для стрима, и для камеры (на M4 так и есть). Среда без High-энкодера (Firefox/OpenH264, сборки Chromium без проприетарных кодеков) — High не пробуется.
- **Как ставится профиль — без гонок.** `lib/media/h264Publish.ts`: слушатель `ParticipantEvent.LocalSenderCreated`. livekit-client эмитит его синхронно сразу после `addTransceiver` и до `engine.negotiate()` этой публикации; между ними только микрозадачи, offer создаться не может. Слушатель находит transceiver по `sender` (`room.engine.pcManager.publisher.getTransceivers()`) и вызывает `setCodecPreferences`: из H.264 — только High (`64001f`, затем Constrained High `640c`), pm=1 перед pm=0, остальные кодеки (VP8/VP9/AV1, rtx, red, ulpfec) после. Baseline `42001f` и Main **убраны**: LiveKit (pion) сопоставляет H.264 по `profile_idc`, и предложенный `42001f` совпадает с его `42e01f` раньше, чем High (проверено на dev LiveKit). Предпочтения живут на transceiver'е, поэтому ренеготиации их сохраняют; при переподключении livekit-client заново публикует трек — событие срабатывает снова. Отмечается трек (`setH264Profile(track, 'high')`), а не комната: «Совместимость» и другие кодеки не трогаются. Если `setCodecPreferences` бросает или High нет в `RTCRtpSender.getCapabilities` — трек уходит как раньше (CB), это только лог.
- **Приём.** SFU пересылает High-поток, в SDP зрителя он подписан тем кодеком, о котором договорился зритель (`42e01f`), — декодеры H.264 в браузерах не привязаны к профилю. Проверено `pnpm -F @calaba/desktop e2e:media` (dev LiveKit, издатель — Google Chrome с `64001f` на обоих слоях): Chrome, Chromium Playwright (в его списке приёма High нет вовсе), WebKit Playwright и Firefox декодируют, `framesDecoded` растёт ≈ 15 к/с. Мобильный Safari (iOS) не проверялся — ориентир WebKit; `decoderImplementation` без захвата браузеры не показывают.
- **«Совместимость (H.264)»** = Constrained Baseline, программный на macOS (подсказка в настройке говорит, что нагрузка выше, чем в «Авто»). Нужна, если у зрителя что-то не декодирует High.
- **Чётные слои.** Аппаратный H.264 принимает только чётные размеры, нечётный слой молча уходит в OpenH264 (экран 2560×1664 в 720p = 1107×720, миниатюра 553×360). Перед публикацией H.264 `alignCaptureForH264` (`h264Layout`): у каждого нижнего слоя целый масштаб (`round(короткая сторона / слой)`, ≥ 2, кратный масштабу слоя выше), захват обрезается вниз до кратного 2 × масштаб (`applyConstraints` с `exact` и `resizeMode: 'crop-and-scale'`, кап fps сохраняется), нижние слои публикуются ровно `захват / масштаб`: 1104×720 + 552×360; камера 720p — 1280×720 / 640×360 / 320×180 без изменений. Размер берётся с первого настоящего кадра (`ImageCapture.grabFrame`, ≤ 1,5 с, иначе `getSettings`): до него захват экрана сообщает запрошенные 1920×1080, а ScreenCaptureKit отдаёт 1658×1078 — раньше миниатюра 553×359 так и уходила в OpenH264 (docs/14 «Стрим экрана: захват»). Размер закрепляется всегда, даже если уже ровный. Если захват всё же сменил размер (окно: SCK уточняет прямоугольник содержимого после первых кадров; источник меньше закреплённого не растягивается), сторож в опросе статистики стрима (раз в 2 с, `hasOddH264Layer` по `frameWidth/Height`) даёт миниатюре масштаб с чётными сторонами (`evenLayerScale`, ±8 % от 360) через `RTCRtpSender.setParameters` — захват не трогаем: новое `exact` на окне заставляет SCK заново вписать содержимое, и кадр съёживается. Верхний слой SCK всегда отдаёт чётным. Остаётся: снижение разрешения адаптацией (`balanced`, стрим «Видео») — верхний слой может стать нечётным до следующей публикации (docs/12).

#### Стоимость стрима у ведущего (docs/14 «Стрим экрана: захват», 29.09)

- Захват — ScreenCaptureKit и для окна, и для экрана (Chromium 152); размер задаёт пресет (`max` width/height) прямо в конфигурации SCK, Retina масштабируется у источника. Системный пикер (`useSystemPicker`) использует тот же класс захвата — не переключаемся.
- На M4 стрим 1080p/15 «Текст» со зрителем стоит +6…7 % ядра к голосу (статичный код 13,6 %, прокрутка 14,5 % против 7,6 % у голоса). Частота кадров, своё превью и оверлей пометок на это почти не влияют (в пределах шума замера); кодер из двух слоёв VideoToolbox — ≈ 1,6.
- Один слой вместо двух у H.264 дал бы ещё ≈ −2 п. п. (один прогон), но зрители в PiP тогда получают полный слой 1080p вместо 640×360 — не включено, повторить замер (docs/14).

### Эффективность доставки (главное для трафика)

- **`dynacast: true`** — SFU говорит паблишеру не кодировать слои, которые никто не смотрит.
- **`adaptiveStream: true`** — SDK подписывается на слой по фактическому размеру `<video>`-элемента на экране зрителя. Превью стрима в углу чата (например 320×180) → низкий SVC-слой (~0.3–0.4 Mbps), развернул на весь экран → верхний слой. Для `detail` (`L1T3`) пространственных слоёв нет — превью получает полное разрешение с низким fps (см. «Захват»).
- **Подписка только на то, что смотришь:** зритель не подписан на видео стримов, которые не видны на экране (свернуты/другая вкладка).

Оценка трафика (30 человек, 3 стрима, каждый смотрит один):

| | Клиент, входящий | SFU, исходящий |
|---|---|---|
| Типично (текст/код, 2 говорящих) | 0.1–0.3 Mbps + ~64 kbps аудио | 10–20 Mbps |
| Пик (все смотрят видео-контент в 1080p) | ~2 Mbps | ~60 Mbps |
| Худший случай без оптимизаций (все смотрят все 3 стрима на потолке) | 6 Mbps | ~180 Mbps — так делать не будем |

Сервер с 1 Gbps портом — с большим запасом.
- Паблишер видит «N смотрят» — из данных gateway/LiveKit.
- Ограничение MVP: **до 3 одновременных стримов в комнате** — проверяется на сервере при запросе права публикации screen.

### UI стрима

- В окне чата — плавающая плитка (PiP) в углу; клик → развернуть на область чата или в отдельное окно (второй BrowserWindow для второго монитора).
- Отдельное окно стрима живёт на уровне звонка: календарь, другая комната или пространство его не закрывают. На desktop оно поверх других приложений, где это поддерживается оконной системой (macOS: также на других Spaces и поверх полноэкранных окон); в вебе — обычное отдельное окно браузера. Размер и видимость самого pop-out управляют adaptive stream; свёрнутый pop-out ставит видео на паузу, скрытое основное окно — нет. При возврате видео в чат, закрытии окна, завершении стрима или выходе из звонка окно и наблюдатели освобождаются; общий медиатрек не останавливается.
- Переключатель между стримами, если их несколько; невыбранные — маленькие превью (низкий слой) или совсем не подписаны (настройка «экономить трафик»).
- **Свой стрим (self preview, docs/09 #18а)**: стример видит собственный стрим в том же списке, что и чужие (`RemoteStream.local`), — плитка/stage/PiP/pop-out рисуют захваченный `LocalVideoTrack` из `LocalTrackPublication` напрямую: второй подписки через SFU нет, трафика и декодирования нет, «N смотрят» его не считает. Звук своего стрима не воспроизводится никогда (правило эха 1: только чужой звук и только через `<audio>`), поэтому у своего стрима нет регулятора громкости и меню качества — вместо него пресет, который отправляется.
- **Указка и карандаш (ADR-0028, docs/09 #42)**: зрители с правом говорить рисуют поверх стрима; координаты нормированы к кадру (0..1) и идут по LiveKit data (reliable, topic `annot`, protobuf `AnnotMessage`, ≤ 1 КБ, отправка ≤ 20 сообщений/с, приём ≤ 30/с на отправителя). Медиа не затрагивают: видео не перекодируется, рисунок — canvas поверх `<video>` у каждого зрителя. Приём проверяет грант отправителя (микрофон ∈ `canPublishSources`), живость стрима и запрет ведущего. Ведущий видит рисунки в click-through окне поверх расшаренного экрана с `setContentProtection(true)` — окно не попадает в захват (проверено на macOS 27: ни в thumbnail, ни в кадре `getDisplayMedia`); Linux и шаринг окна — только превью в приложении.
- **Полный экран (docs/09 #18б)**: desktop — `BrowserWindow.setFullScreen(true)` окна, где нажата кнопка (главное или pop-out; IPC `window:setFullScreen`, bounds сохраняются в main и восстанавливаются после выхода); веб — `requestFullscreen()` на контейнере видео. Видео-элемент тот же — adaptive stream сам поднимает слой под размер экрана.

## Видео (камера, v0.2)

Решение и обоснование — ADR-0018. Сервер (лимиты, `camera/request`, `VOICE_CAMERA_STOP`) — docs/05 «Камеры».

| Параметр | Значение |
|---|---|
| Кодек | по железу (ADR-0032): аппаратный H.264 → AV1 → VP9; аппаратного нет — VP9 (иначе AV1, H.264, VP8); без backup codec |
| Слои | simulcast q/h/f: 320×180 @24 / 640×360 @30 / 1280×720 @30, каждый L1T3 |
| Потолки | 0,15 / 0,5 / 1,5 Мбит/с |
| Захват | 720p30 (камера ▾ «Качество»: 1080p30 — верхний слой 1920×1080, 2,5 Мбит/с), `contentHint: motion`, `degradationPreference: balanced` |
| Тариф (ADR-0024) | качество и fps не выше выданного `/camera/request`; стрим — не выше пресета и fps из `/stream/request` |
| CPU-лимит | `qualityLimitationReason: cpu` три замера подряд → захват 640×360@24 до конца сессии |

- **Подписка:** все камеры комнаты, кроме «Не показывать видео» (unsubscribe) и своей с другого устройства. С «Экономить трафик» — только основная камера (закреплённая или активного говорящего), не выше 360p. Активный говорящий для видео меняется только после 2 с речи — без мигания. Слой подбирает adaptive stream по размеру плитки.
- **Кодек вне Chromium** (веб в Firefox/Safari): H.264 simulcast (иначе VP8).
- **Реконнект:** после полного реконнекта LiveKit или повторного `/join` камера включается снова сама.
- **Звук:** у камеры его нет, `<video>` всегда `muted`. Правила эхоподавления не затрагиваются.
- **UI:** PiP камеры говорящего при открытом чате. Вид звонка — до 6 плиток, крупная плитка у говорящего или выбранного. Если смотрят стрим, он главный, камеры — полосой под ним.

### Камера: фон (ADR-0035)
- **Частота сегментации — настройка пользователя 8/16/20/25 к/с, по умолчанию 20** (`prefs.cameraBgFps`, «Плавность»; меняется вживую; запасной путь — 6 к/с независимо от настройки).

Размытие фона (лёгкое / сильное) или картинка вместо фона. Выбор — `prefs.cameraBackground`, на устройство, для всех комнат и звонков; меняется в превью камеры и в меню ▾ у кнопки камеры, на живой камере — сразу.

- **Конвейер:** `LocalVideoTrack.setProcessor` с нашим процессором (`lib/media/background`, ленивый чанк). В Electron 44 / Chromium 152 `MediaStreamTrackProcessor` и `MediaStreamTrackGenerator` есть только в окне, а трек нельзя передать в воркер, поэтому оба создаются в окне, в воркер передаются их потоки. UI-поток кадров не касается.
- **Воркер:** WebGL2 на `OffscreenCanvas`. MediaPipe Image Segmenter работает в том же контексте: маска не уходит с GPU. Модель (2.1) — **selfie_multiclass_256x256** на GPU-делегате, человек = 1 − уверенность класса «фон», край `smoothstep(0.3, 0.95)` (мягкий, владелец 03.10); на программном GL (SwiftShader/WARP/llvmpipe) и CPU-делегате — selfie landscape 256×144, край 0.3–0.7 (`segModel`, `SEG_MODELS` в `logic.ts`). Вход модели — кадр, уменьшенный до её размера (`setAutoResizeCanvas(false)`, иначе MediaPipe растянул бы общий холст). Сегментация — 20 к/с, но не чаще кадров камеры (владелец, 03.10: на 8 к/с маска отставала от поворота головы и проступали куски фона, 15 — лучше, но мало), на запасной модели — 6 к/с и подсказка «нагружает процессор». Маска: EMA по времени (τ 60 мс), человек потерян (< 3 % кадра) — держим прошлую маску 500 мс, решение на GPU по 1×1-уровню мипмапа, доля читается асинхронно (PBO + fence, без остановки конвейера). Край — joint bilateral 5×5 на ¼ размера по яркости кадра (ослабленный: σ² 8 по расстоянию, 0,04 по яркости — край мягче). Размытие — разделимый Гаусс на ¼ размера (σ 4 и 12 px в 720p), фон предумножен на (1 − маска): человек не «растекается» в размытие. Проходов на кадр: картинка — 2, размытие — 4.
- **Модели и WASM** упакованы в приложение и веб-сборку (`resources/mediapipe/`: multiclass 16,4 МБ + landscape 0,25 МБ, источник и лицензия — `SOURCE.txt`; WASM — из `@mediapipe/tasks-vision`; всё через `?url` → `assets/`, в десктопе — внутри `app.asar`). Скачивается и грузится только выбранная модель и только при первом включении фона; до загрузки кадры идут без эффекта, в превью — «Загружаем фон…». В лог: `camera background ready` (модель, делегат, к/с, GL-рендерер) или `camera background failed` (причина).
- **Захват и ограничения:** с процессором `track.mediaStreamTrack` — это выход процессора. Размер, fps, выравнивание H.264, `contentHint`, `ended` и `backgroundBlur` относятся к захвату: `cameraSource(track)` (`lib/media/camera.ts`). Смена камеры перезапускает только источник воркера. CPU-лимит (360p) уменьшает и работу фона.
- **Аппаратный путь:** если `getSupportedConstraints().backgroundBlur` и камера умеет (`getCapabilities().backgroundBlur` содержит `true`, Windows Studio Effects), оба уровня размытия — `applyConstraints({ backgroundBlur: true })` без нашей сегментации, подсказка «системное». Картинки — всегда наш конвейер. На Mac M4 такого ограничения нет.
- **Где недоступно (2.1, дополнение ADR-0035 «отказы»):** секции «Фон» и «Внешний вид» не прячутся, а выключены с причиной — Safari и Firefox (нет `MediaStreamTrackProcessor`), мобильный веб, нет контекста WebGL2 на `OffscreenCanvas` (проба один раз за сессию), режим «Слабый компьютер» (docs/09 #44 — `lowEndMode()` в `services/cameraBackground.ts`, пока `false`), отказ конвейера в этом запуске. Отказ после выбора (модель/WASM/делегат, воркер, 30 кадров подряд с ошибкой, 24 сегментации без маски) → причина в лог, выбор сбрасывается на «Нет» (при отказе GL/воркера — и эффекты), тост «Фон выключен — <причина>». GPU-делегат не стартовал → CPU-делегат (6 к/с). Скрытое окно ничего не меняет: кадры нужны собеседникам. Диагностика: `node scripts/bg-probe.mjs` (конвейер в Electron из `app.asar` и в Chromium, JSON-отчёт; workflow `bg-probe.yml`, Windows); качество края и CPU моделей — `node scripts/bg-quality.mjs` (кадры вебкамер из `e2e-marketing/photos`).
- **Свои картинки:** JPEG / PNG / WebP ≤ 10 МБ → кроп 16:9 по центру → WebP 1280×720 + миниатюра 320×180, в IndexedDB (`calaba-camera-backgrounds`), до 5; на сервер не уходят. Превью зеркальное, собеседники видят фон незеркальным.
- **Встроенные фоны** — данные, а не код: `src/renderer/assets/backgrounds/manifest.json` (`id`, `file`, `thumb`, `name` на ru/en/es/zh-CN) и WebP рядом. Сейчас — сгенерированные заглушки (`node tools/gen-backgrounds.mjs`). Заменить набором фотографий: `node tools/import-backgrounds.mjs <папка>` (JPEG/PNG/WebP, имена файлов = id, подписи — `names.json` в папке) → 1280×720 WebP ≤ 150 КБ + миниатюры, манифест переписан, старые файлы удалены.
- **Требования к фотографиям фона:** 16:9, исходник 1920×1080; центр кадра пустой (там будет человек), интересное — по краям и сверху; дальний план с малой глубиной резкости (мягко размыт, как на портретном объективе); ровный мягкий дневной свет; без людей, текста, логотипов, зеркал и экранов. Сюжеты владельца: офис с панорамными окнами, лофт-переговорная, домашний кабинет, горная терраса, веранда у моря, кафе, библиотека, минималистичная студия.
- **Фон → 2 слоя simulcast** (компромисс): камера, включённая с фоном, публикуется слоями 180p + 720p без 360p (`cameraPublishOptions(…, background)`). Кадр процессора — RGBA-холст, и GPU-процесс конвертирует его для кодера на каждый слой (кадр камеры идёт в VideoToolbox как есть); слой 360p стоит ≈ 3 % ядра на M4 (docs/14). Цена: плитке среднего размера достаётся 720p (больше трафика и декодирования у зрителя) или 180p. Слои выбираются при публикации: фон, включённый на уже идущей камере, оставляет три слоя до её перезапуска.
- **Цифры CPU** — docs/14 «Фон камеры». Тест на проводе — `e2e-media/background.spec.ts`.

### Камера: эффекты (ADR-0035, дополнение)

«Улучшить внешность» (сила 0–100, по умолчанию 40) и «Низкая освещённость» — `prefs.cameraEffects`, на устройство, независимо от фона; переключаются в превью камеры (секция «Внешний вид» под «Фоном») и в меню ▾ у кнопки камеры (два переключателя, сила — только в превью). Где фон скрыт (Safari, Firefox, телефон, «Слабый компьютер»), скрыты и эффекты.

- **Тот же процессор и воркер**, что у фона (`lib/media/background`): эффекты — проходы компоновщика, модель для них не нужна (компоновщик создаётся на первом кадре без MediaPipe). Фон «Нет» и оба эффекта выключены — процессора нет, камера идёт как есть. Процессор есть — публикация двумя слоями simulcast, как с фоном.
- **Улучшить внешность — без сегментации и без модели лица:** билатеральный фильтр 5×5 на ¼ размера прямо из кадра (отводы — 2×2-боксы с шагом 2 px в 720p, веса по расстоянию и разнице яркости), затем в выходном проходе сглаженная картинка подмешивается только на пикселях цвета кожи (YCbCr, диапазоны Chai–Ngan с мягкими краями, не в глубокой тени) и только там, где локальный контраст мал (глаза, брови, волосы, контур остаются резкими). С фоном — ещё и только на человеке (маска уже есть). Сила: доля сглаженного `0,85·√(s/100)` (40 → 0,54) и допуск по яркости 0,04 + 0,06·s/100 (`effects.ts`). Проходов: один на ¼ + выходной. Системного API нет (Windows Studio Effects не умеет) — всегда наш конвейер.
- **Низкая освещённость:** раз в секунду кадр уменьшается до 256×144 на CPU-холсте воркера, гистограмма яркости → средняя. Включается при средней < 0,25, выключается при > 0,33 (гистерезис); кривая — гамма `ln 0,40 / ln средней`, не сильнее 0,5 (белое остаётся белым, ничего не пересвечивается), половина по яркости (цвет сохраняется) + половина по каналам; фон-картинку не трогает. Кривая плавно следует за решением (τ 0,8 с). Вместе с ней — лёгкое шумоподавление (4 отвода с весом по яркости, до 0,6 при самой сильной кривой). Светлая комната (и закрытый объектив, средняя < 0,02) — кривая 1: кадры идут мимо GL и холста, стоимость — только замер раз в секунду. В тёмной — один выходной проход (с фоном — ноль лишних).
- **Тест на проводе** — `e2e-media/background.spec.ts -g effects`: тёмная синтетическая комната → средняя яркость у зрителя растёт ≥ 1,5×, с обоими эффектами кадры идут; фейковая камера Chromium (светлая) — кривая 1, 0 кадров через GL. Unit — `effects.test.ts` (сила, решение по экспозиции, гистерезис, рампа). Цифры CPU — docs/14 «Эффекты камеры».

## Изображения: клиентское сжатие и HEIC

(docs/09 #114, владелец 29.09.) Картинки, которые клиент сам превращает в «свою» форму, никогда не уходят оригиналом; код — `renderer/lib/image/`.

- **Аватар** (профиль, боты) — центральный квадрат → **512×512** (2× от самого крупного показа 96–128 px на 2×-экранах, с запасом) → `canvas.toBlob('image/webp', 0.85)`; если браузер вернул не WebP (Safari < 16 — PNG или `null`) — `image/jpeg` 0.88 на белом фоне. Иконка пространства — так же, **256×256**. Меньше стороны не растягиваем. Сервер принимает аватар ≤ **512 KB** (было 5 MB; старый клиент с фото с телефона получит 413 и должен обновиться); реальный WebP — 30–80 KB.
- **Ориентация** — `createImageBitmap(file, {imageOrientation: 'from-image'})` (EXIF учитывается до обрезки).
- **HEIC/HEIF** (фото iPhone): Chromium его не декодирует. Лестница `lib/image/decode.ts`, шаги 2–3 — только для HEIF (по `ftyp`, иначе по имени/типу): ① `createImageBitmap` (JPEG/PNG/WebP/GIF/AVIF, Safari ≥ 17 — и HEIC); ② Electron macOS/Windows — байты по IPC `files:decode-image` в main (`main/imageDecode.ts`): `nativeImage.createFromBuffer` HEIC не читает, поэтому системный эскизник `createThumbnailFromPath` (macOS — Quick Look, HEIC всегда, ориентация учтена; Windows — только с установленным «HEIF Image Extensions»). Quick Look растягивает картинку в запрошенную рамку, поэтому рамка — видимый размер из заголовка (`ispe` основного элемента, стороны меняются при нечётном `irot`, `shared/heif.ts`), вписанный в 4096; результат других пропорций (> 2 %) отбрасывается — тогда шаг ③. Назад — JPEG 90; Linux — сразу `null`; ③ веб, Linux, Windows без кодека — сервер `POST /api/files/convert?to=jpeg` (ниже); ④ никто не открыл — тост «HEIC не поддерживается на этой платформе — сохраните фото как JPEG».
- **Вложение HEIC** в чат перед загрузкой (`services/chat.sendMessage`) — JPEG 0.9, ≤ 4096 px по большей стороне, имя `.jpg`; в композере до отправки — плашкой файла (превью HEIC браузер не покажет). Остальные вложения — как есть. Пикеры картинок принимают `.heic/.heif` (`IMAGE_ACCEPT`), перетаскивание и вставка — любые файлы, как раньше.
- **Сервер** `POST /api/files/convert?to=jpeg` (авторизация, лимит загрузок пользователя): multipart `file`, только HEIF (иначе 415), ≤ 25 MB (413); ничего не хранит, отвечает `image/jpeg`. ffmpeg ≥ 7.1 + ffprobe (`FFMPEG_PATH`/`FFPROBE_PATH`, в образе api — статическая сборка 8.0): CLI ffmpeg берёт у сетки плиток (iPhone — 48 плиток 512²) только первую, поэтому сервер читает раскладку через `ffprobe -show_stream_groups`, склеивает `xstack` + `crop`, поворот/отражение берёт сам из `irot`/`imir` основного элемента (ffmpeg их к сетке не применяет), вписывает в 4096 px, метаданные выбрасывает. Одна конверсия за раз, 20 с на ожидание и работу (503 — «занято»); нет ffmpeg — 501, клиент показывает тост ④.

## Результаты спайка (2026-09-25)

Стенд: MacBook Air M4 (10 ядер), macOS 27, Electron 44.4.5 (Chrome 152), livekit-client 2.22.3, livekit-server 1.13.7 (`compose.dev.yml`, `--dev`), два окна одного процесса через локальный SFU (loopback, RTT ≈ 1 мс, без потерь). CPU — **% одного ядра** процесса renderer публикующего окна (Electron `getAppMetrics` на macOS нормирован на все ядра, пересчитан; сверено с `ps`). Тестовые источники — canvas «редактор кода» (статичный текст с мигающим курсором / непрерывный скролл); CPU renderer включает отрисовку canvas, поэтому «статичный» ряд ≈ базовая стоимость источника. Цифры — среднее за 6 с после 8 с прогрева.

### Аудио
- Пайплайн `getUserMedia(AEC3, AGC)` → RNNoise worklet → `LocalAudioTrack` работает в Electron 44, включая prod-сборку с `file://`. Opus mono, `usedtx=1;useinbandfec=1`, `targetBitrate` = выбранному (32 000).
- Закрытый гейт (`track.mute()`, трек опубликован): **0.1 kbps** исходящего аудио. Открытие мгновенное (без republish).
- Реальный микрофон + речь из динамиков (`say`): VAD RNNoise доходит до 1.0, гейт открывается на фразах и закрывается в паузах > 400 мс; второй участник получает ~28 kbps, `audioLevel` 0.12.
- PTT (uiohook, синтетическая F13 через System Events): down → передача сразу, up → mute через 200 мс (замер: клавиша удерживалась ~1 с — unmute на t=110 мс, mute на t=1322 мс ≈ отпускание + 200 мс). С 0.3.x хвост настраивается (по умолчанию 20 мс), см. «Задержка отпускания» выше.
- `setSinkId` на всех `<audio>` переключает вывод и возвращает на default; `webAudioMix: false`.
- RNNoise вкл/выкл на лету: пайплайн пересоздаётся, `replaceTrack` без republish, встроенный NS переключается (`noiseSuppression: true` при выкл.).

Реальный экран (Retina 2940×1912, на экране работают окна приложения с обновляющейся статистикой):
- 1080p15 → 1658×1078@15 (соотношение сторон сохраняется): **228 kbps, 32 % ядра**.
- original → 2940×1912@29: **664–815 kbps, 72–80 % ядра**.

Нужно разбирать отдельно (флаги Chromium, Windows MediaFoundation).
- Потолок битрейта работает (1080p скролл упирается в 2.0 Mbps, `targetBitrate` ≈ `maxBitrate`). Статичный текст стоит 18–40 kbps, это ниже табличной оценки «30–300 kbps».

### SVC / adaptive stream: главное открытие
- **livekit-client 2.22 при публикации screen share с SVC-кодеком без simulcast принудительно ставит `scalabilityMode = 'L1T3'` и перезаписывает `contentHint` трека на `'motion'`** (`LocalParticipant.publishTrack`, комментарий SDK про баги Chrome с L3T3 и лимитом 5 fps для L1T3 на screenshare-пути). Поэтому `L1T3`, `L2T3_KEY` и `L3T3_KEY` для экрана **дают один и тот же поток** (замерено: у всех трёх `scalabilityMode: L1T3`, одинаковые битрейты). Выбор `detail → L1T3 / motion → L3T3_KEY` из ADR-0005 сейчас не применяется, а `detail` фактически заменяется на `motion`.
- При `L1T3` превью 320×180 получает **полный поток**: 1920×1080@15, ~760 kbps на реальном экране, 2 Mbps на скролле. SFU снижает только пространственный слой, временные слои для превью не срезаются. Адаптивности для превью нет.
- **Решение, проверенное в спайке: AV1 «SVC simulcast»** (`simulcast: true` + `scalabilityMode: 'L1T3'`, в UI «L1T3 + simulcast 360p»). Каждый rid кодируется как L1T3; нужен livekit-server > 1.13.6 (у нас 1.13.7). SDK в этом режиме **не трогает** `contentHint` (остаётся `detail`). Слои: `q` 640×360 (~250 kbps потолок) + `h` полный пресет.
  - Превью 320×180: зритель получает 640×360@15, **8 kbps на статике / ~250 kbps на скролле** (вместо 19 / 2000 kbps с L1T3). Слой `h` dynacast выключает у паблишера, пока никто не смотрит крупно.
  - Развернули (элемент 1400×788): переключение на `h` за ~2 с (dynacast включает слой + keyframe), битрейт растёт за ~10 с (разгон BWE). Свернули: обратно на `q` меньше чем за 1 с, `h` снова выключается.
  - CPU паблишера: 1080p 33 % против 32 % у single L1T3; original 68 % против 72–80 %. Низкий слой почти ничего не стоит, `h` при этом не кодируется, пока никто не смотрит крупно.

### Решения по открытым пунктам
1. **`L1T3` vs `L2T3_KEY` для `detail`**: вопрос снят. С livekit-client 2.22 non-simulcast SVC для screen share всегда `L1T3` + `motion`. **Рекомендация: AV1 + simulcast(L1T3 на rid) для screen share**, это даёт настоящий низкий слой для превью и сохраняет `contentHint: detail`. Нужен новый ADR (поправка к ADR-0005) и пин livekit-server ≥ 1.13.7. Проверить на медленном канале (эмуляция потерь/полосы) и на Windows.
2. **Системный звук на macOS**: захват через кастомный пикер + `loopbackWithMute` + `MacLoopbackAudioForScreenShare,MacSckSystemAudioLoopbackOverride` **работает** (баг electron#52738 на этой машине не воспроизвёлся: аудио-трек есть, внешний `afplay` ловится на −23 dBFS). Но **`restrictOwnAudio: true` не исключает звук нашего процесса**: тон из обычного `<audio>` приложения попадает в loopback на −11.7 dBFS (так же и с `--disable-features=AudioServiceOutOfProcess`). То есть голоса участников ушли бы обратно в комнату. По ADR-0004 системный звук на macOS **по умолчанию выключен**, в UI есть предупреждение. Windows (`loopbackWithMute` — mute ли это всего вывода у стримера?) не проверен. **Пересмотрено 28.09 (docs/09 #68, п. 4 выше):** мерили `loopbackWithMute`, с которым `restrictOwnAudio` не применяется; с `loopback` наш звук исключается (−65 дБ против −32 дБ), macOS 14.2+ — `supported`.
3. **Библиотека RNNoise**: `@timephy/rnnoise-wasm` (RNNoise 0.2, синхронный WASM для AudioWorklet), свой worklet берёт VAD-вероятность. `@sapphi-red/web-noise-suppressor` не подошёл, потому что его worklet отбрасывает VAD.

### Что спайк не смог проверить в одиночку
- Реальное эхо с колонками и 2–3 людьми (AEC3 vs macOS voice processing), эхо после смены устройства вывода. Нужны люди (TESTING.md, раздел «Desktop media spike»).
- Резкость текста на глаз у медленного зрителя, медленный/мобильный канал (всё мерилось на loopback без потерь).
- Windows / Linux: loopback, PTT (X11/Wayland), аппаратные энкодеры.
- Субъективное качество RNNoise (слушать надо людям).

## Клиент: факты реализации (этап 3, 2026-09-25)

Замерено в приложении (`apps/desktop`) на локальном стенде: два клиента на одной машине, livekit-server 1.13.7 `--dev`, API из `apps/server`.

- **Гейт VAD/PTT и явный mute разведены.** Гейт и PTT переключают только `mediaStreamTrack.enabled`. Self-mute, deafen, модераторский mute и отсутствие SPEAK идут через LiveKit `track.mute()`. Правила закреплены в `lib/voiceLogic.ts`, есть unit-тесты. Причина: сервер берёт `VoiceState.muted` из mute трека микрофона (webhook `track_muted`), поэтому мьют по VAD давал бы при каждой паузе webhook и `VOICE_STATE_UPDATE` всем участникам.
- **Подписки.** `autoSubscribe: false`: микрофоны подписываются всегда, стрим (видео и его звук) — только когда его смотрят.
  - Плитка PiP 320×180 получает слой 640×360.
  - Развёрнутый стрим (элемент 732 px) — слой 1920×1080.
  - Всплывающее окно показывает тот же трек в 1920×1080.
  - Счётчик «N смотрят» у стримера работает: сообщения по LiveKit data, топик `calaba.watch`.
- **Громкость участника** — `element.volume`, максимум 100 %. Усиление выше 100 % потребовало бы WebAudio, а это ломает AEC (правило 1). Звуки интерфейса (вход и выход, mute) тоже идут через `<audio>`.
- **Модерация.** Серверный mute, `POST /api/rooms/{id}/voice/{userId}/mute`, доходит до клиента событием `TrackMuted` на своём микрофоне. Клиент показывает «Модератор выключил вам микрофон» и переводит себя в self-mute, чтобы гейт не включил микрофон обратно. Отключение (`…/disconnect`) приходит как `DisconnectReason.PARTICIPANT_REMOVED`.
- **Наблюдение по dev-стенду.** В `compose.dev.yml` у LiveKit не настроены webhooks, поэтому voice-state участников появляется только через reconcile (до 30 с). До этого `PATCH /api/voice/self` отвечает `409`, и клиент повторяет его, получив свой `VoiceState`. Для ручных тестов «кто в комнате» стоит настроить webhook `http://host.docker.internal:<порт API>/api/rtc/webhook` в LiveKit стенда разработки.

### Стенд (2026-09-25, этот Mac → `app.141-105-69-177.sslip.io`, LiveKit за Caddy/TLS)
- **Путь ICE:** `srflx→host` UDP, RTT ≈ 34–37 мс (эпизодически до 100), потери 0–0,2 %. При принудительном relay (`CALABA_FORCE_RELAY=1`) — TURN по UDP, RTT ≈ 34 мс. TURN/TLS 443 не проверен: для этого нужна сеть, где UDP закрыт.
- **Голос:** ≈ 31–45 кбит/с на речи, 0,1 кбит/с в тишине.
- **Стрим 1080p15, реальный Retina-экран, AV1 simulcast.** Слой `h` 1658×1078@15 — 80–110 кбит/с на статике, до 940 при смене картинки. Слой `q` 553×359 — 16–174 кбит/с. Зритель получает `h`, декодирует через VideoToolbox. CPU renderer стримера — 18–32 % ядра.
- **Стрим «Оригинал».** Слой `h` 2940×1912@20–26 — 234–1792 кбит/с, `q` 554×360 — 23–174 кбит/с. CPU renderer — 40–64 % ядра. Пресет доступен, только если его разрешает комната (в «Team» по умолчанию 1080p).
- **Скрытое окно зрителя:** `backgroundThrottling: false` в Electron закрепляет `document.visibilityState` в «visible», поэтому страница сама скрытие не видит. main сообщает «окно показано / скрыто / свёрнуто» (`window:shownChanged`), `lib/windowVisibility.ts` подменяет `visibilityState`/`hidden` и шлёт `visibilitychange` — adaptive stream ставит видео на паузу, dynacast выключает слои у стримера, декодирования нет (замер: 17,5 → 7,0 % CPU, docs/14-energy.md). Окно, перекрытое другими окнами (не скрытое), и ⌘H пока не распознаются (docs/12).
- **Устойчивость.** Заморозка renderer на 20 с: события дошли по тому же сокету, LiveKit восстановил сессию сам. Заморозка на 95 с: gateway `1006` → `INVALID_SESSION(resumable=false)` → IDENTIFY; голос вернулся через ≈ 4 с. Если LiveKit не может восстановить сессию сам, клиент повторяет `/join` (1, 2, 4… с, до 5 попыток).

### Что проверяют только люди (по-прежнему открыто)
