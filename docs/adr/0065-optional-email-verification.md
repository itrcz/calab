# ADR-0065: Подтверждение почты по желанию — `EMAIL_VERIFICATION=optional` (2026-10-05)

## Контекст
- ADR-0023 (27.09): неподтверждённый аккаунт может входить и читать, но создание пространств, приглашения, боты, новые DM, внешние участники встреч — 403 `EMAIL_NOT_VERIFIED`; клиент показывает шаг онбординга и неубираемую плашку с кодом.
- Security review 26.09, H2: регистрация на стенде переведена в `REGISTRATION_MODE=invite` (без кода — только первый пользователь), чтобы чужие не занимали общий диск и не создавали пространства.
- ADR-0027: код email-приглашения не доказывает адрес; вступление по нему — только после подтверждения адреса кодом из письма.
- Владелец, 05.10: «регистрироваться может кто угодно, без кода приглашения; код из письма не должен ничего блокировать».

Открытая регистрация без кода приглашения уже есть (`REGISTRATION_MODE=open`). Не хватает только того, чтобы подтверждение почты перестало быть барьером, — не открыв при этом подмену адреса.

## Решение
1. **Переменная `EMAIL_VERIFICATION=required|optional`** (по умолчанию `required` = поведение ADR-0023; проверяется в `config.Validate` как `REGISTRATION_MODE`, пустое значение в собранном в коде конфиге = `required`). Без `SMTP_HOST` ничего не меняется: адреса подтверждены при регистрации в любом режиме.
2. **Действия — через один гейт.** `auth.EmailGate` (нулевое значение = `required`, т. е. забытая обвязка остаётся закрытой) заменяет все проверки «чтобы сделать X, нужна подтверждённая почта»: создание пространства, ссылки-приглашения, email-приглашения, поиск и добавление по почте (сам приглашающий), создание бота, гостевая ссылка комнаты, гостевая ссылка временной комнаты, новый DM, внешние адреса встречи. При `optional` гейт пропускает.
3. **Доверие к адресу — без изменений.** Адрес остаётся неподтверждённым (`email_verified_at IS NULL`, `me.email_verified = false`), и всё, что полагается на то, что адрес принадлежит пользователю, по-прежнему проверяет `email_verified_at` само, в любом режиме:
   - поиск по почте и добавление по id (`LookupInvitee`, `addMember` — только подтверждённые аккаунты);
   - вступление по коду email-приглашения (`boundInvite` → `auth.RequireVerified`, 403 `EMAIL_NOT_VERIFIED`) и автовступление после подтверждения (`AcceptEmailInvites`, `OnEmailVerified`);
   - OAuth/OIDC-провайдер: claims `email` / `email_verified` только для подтверждённого адреса (`oauthprovider/token.go`, `userinfo.go`);
   - суперадмин (`auth/identity.go`, `identitymutation.go`, `pbconv.Me`);
   - письма о встречах: Reply-To организатора и адресаты-участники (`calendar/mailer.go`, `public.go`).

   Угроза, которая остаётся закрытой: кто-то регистрирует ivan@company.com раньше Ивана. Админ, ищущий Ивана по почте, этот аккаунт не находит и добавить не может; email-приглашение Ивану не вступает за него (ни автоматически, ни по коду); ни один OIDC-клиент не получит `email_verified=true`. Список закреплён unit-тестом `auth.TestEmailTrustInventory` (рефакторинг, пропустивший одну из этих проверок через гейт, падает) и интеграционным `TestOptionalVerifySquatting`.

   **Если адрес занят.** Настоящий Иван при регистрации получает 409 «адрес уже зарегистрирован» и идёт в «Забыли пароль»: код сброса приходит в его ящик, сброс подтверждает адрес, отзывает все сессии захватчика (и выданные через них OAuth-гранты) и запускает ждущие email-приглашения (`OnEmailVerified`). Аккаунт — со всем, что захватчик успел создать (пространства во владении, боты), — переходит к Ивану; токены ботов сброс не отзывает (бэклог, docs/12). Закреплено `TestOptionalVerifySquatterReclaimed`.
4. **Подтверждение остаётся доступным.** `POST /api/auth/verify/send` и `/verify` работают как раньше; клиент предлагает подтвердить адрес в настройках профиля («Не подтверждена» · «Подтвердить»), ничего не напоминает. При `optional` код не отправляется сам ни при регистрации, ни при входе — кроме случая из п. 5.
5. **Исключение — приглашённый по почте.** Если для неподтверждённого адреса ждёт живое email-приглашение (регистрация по его коду или просто с приглашённым адресом), вступление возможно только после подтверждения (ADR-0027). Такому пользователю код отправляется, как раньше, а клиент показывает шаг онбординга и плашку с текстом «чтобы вступить». 403 `EMAIL_NOT_VERIFIED` при вступлении по email-коду (приглашение пришло уже после входа) тоже включает плашку.
6. **Контракт.** Режим и исключение клиент узнаёт из `RegisterResponse` / `LoginResponse` / `Ready`: `email_verification_optional` и `email_invite_pending`. Почему не `Me` и не `GET /api/version`:
   - онбординг монтируется сразу после регистрации/входа, до READY, — решение о шаге нужно уже в ответе регистрации/входа; READY повторяет его для каждой сессии (в том же месте, где сервер уже сообщает свои настройки, — `plan_contact`);
   - `Me` собирается в десятке мест без доступа к конфигу (`pbconv.Me`), а клиент заменяет `me` целиком по `USER_UPDATE`: поле, забытое в одном из мест, переключало бы плашку туда-сюда;
   - `GET /api/version` клиент читает только в вебе и только после READY.

   Флаг `email_invite_pending` вычисляется одним `EXISTS` по `email_invites` только для неподтверждённых при `optional`; ошибка запроса = «приглашение ждёт» (лучше спросить лишний раз).
7. **Старые клиенты** против сервера с `optional` не ломаются: поля им неизвестны, они показывают прежнюю плашку «Подтвердите почту» (код можно запросить «Отправить снова») — допустимо. Новый клиент против старого сервера получает `false`/`false` = прежнее поведение.

## Злоупотребления при открытой регистрации
Что есть:
- регистрация и вход: token bucket по IP (`AUTH_RATE_BURST` / `AUTH_RATE_PER_MINUTE`, 10 / 10 в минуту), `LOGIN_ACCOUNT_ATTEMPTS` на адрес;
- пространства: `MAX_WORKSPACES_PER_USER` (5 во владении), `WORKSPACE_CREATES_PER_HOUR` (3), квота нового пространства `DEFAULT_WORKSPACE_QUOTA_BYTES`, общий потолок диска `STORAGE_MAX_TOTAL_BYTES`, лимиты тарифов (участники, боты);
- исходящая почта: приглашения — 20 сразу / 30 в час на пользователя, поиск по почте — 20 в минуту, письма — `MAIL_PER_ADDRESS_PER_HOUR` (3), `MAIL_EVENTS_PER_ADDRESS_PER_HOUR` (10), `MAIL_PER_HOUR` на инстанс (200); встречи — 30 сразу / 120 в час;
- новые DM — 10 сразу / 30 в час, и только с теми, с кем есть общее пространство; гостевые аккаунты — 5 в час на IP.

Чего нет (бэклог, docs/12): капчи / proof-of-work на регистрации; глобального и по-подсетевого лимита регистраций (ботнет умножает лимит по IP на число адресов); блок-листа одноразовых доменов; чистки никогда не использованных неподтверждённых аккаунтов. Отдельный риск `optional`: неподтверждённый аккаунт может отправлять письма с нашего домена (email-приглашения, приглашения на встречи внешним адресам) — в пределах лимитов выше; репутация домена отправителя — на операторе. Включать `optional` стоит вместе с наблюдением за логами почты (`mail sent` / `mail: giving up`) и числом новых аккаунтов.

## Последствия
- Для открытой регистрации оператор ставит две переменные: `REGISTRATION_MODE=open` и `EMAIL_VERIFICATION=optional` (compose передаёт обе; `.env.example`, `apps/server/README.md`, docs/06 «Почта»).
- Proto: три пары полей (`auth.proto`, `gateway.proto`), миграций нет; новый запрос `HasPendingEmailInvite`.
- Клиент: `features/auth/verifyAsk.ts` решает, спрашивать ли; плашка подписана на булев селектор (не перерисовывается от посторонних изменений `me`); шаг онбординга фиксируется при монтировании, READY может только убрать его (сессия, восстановленная без флагов); `ChangeEmailDialog` получил режим `verify`.
- Права (docs/16): там, где написано «подтверждённая почта» для действия, — с оговоркой про `optional`; доверие к адресу — без оговорок.
