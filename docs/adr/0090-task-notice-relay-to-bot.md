# ADR-0090: Передача уведомлений о задачах выбранному боту (2026-10-12)

Дополняет [ADR-0089](0089-task-notification-triggers.md) (триггеры уведомлений), [ADR-0031](0031-bots.md) и
[ADR-0051](0051-bot-api-v2.md) (боты, вебхук, gateway).

## Контекст
Бриф GPTunneL (12.10): человек настраивает уведомления о задачах в Calab один раз, а бот (Опса) получает ровно те
уведомления, которые Calab решил показать этому человеку, и переносит их в Telegram — без второй настройки на
стороне бота. Решение «показать ли» принимает сервер (`internal/boards/notify.go`: `decide` → `sendNotices`) по
личным данным (`users.task_notify_off`, подписка и «Отписаться», уровень и mute пространства); снаружи его не
повторить: боту недоступны чужие настройки и подписки, события досок на вебхук (`taskActivity`) идут без адресата.

## Решение
1. **Настройка пользователя** `users.task_notify_bots uuid[] NOT NULL DEFAULT '{}'` (≤ 10), рядом с
   `task_notify_off`, глобально. Протокол: `UserSettings.task_notify_bots repeated string` (только чтение),
   `UpdateMeRequest.task_notify_bots` — обёртка `TaskNotifyBots { repeated string bot_user_ids }` по образцу
   `TaskNotifyOff` (присутствие = заменить список). Проверки: каждый id — бот, состоящий хотя бы в одном
   пространстве вместе с пользователем, с вебхуком или gateway; пользователь не бот и не гость.
2. **Событие** `DispatchEvent.task_notice` (следующий номер после `billing_update = 96`) —
   `TaskNoticeRelay { workspace_id, user_id, Task task, TaskNotice notice, task_url, board_key, board_name }`.
   `task` — как его видит человек, без данных смотрящего (subscribed / muted / unread / viewer_state сброшены),
   e-mail вычищены как в остальных событиях ботам (`eventWithoutEmails`).
3. **Точка отправки** — там же, где человеку уходит `TaskUpdate` с `notice`: для каждого бота из его
   `task_notify_bots`, **который состоит в пространстве задачи**, — в очередь вебхука бота и в канал gateway-бота.
   Метёлки (`DUE_SOON`/`OVERDUE`, напоминания о согласовании ADR-0082) идут через тот же путь и попадают в
   relay автоматически. Ничего не уходит в канал пространства и другим ботам.
4. **Видимость — по согласию пользователя.** Бот получает уведомление независимо от своего `VIEW_BOARD`: человек
   явно доверил ему свои уведомления, и бот получает только то, что получил бы этот человек (в т. ч. с закрытых
   досок ADR-0029/0048 и задач с доступом по карточке ADR-0059/0076). Граница: бот должен быть участником
   пространства задачи (иначе relay для этой задачи пропускается), бот не заблокирован пользователем и не удалён.
   Удаление бота из пространства / удаление бота чистит его из `task_notify_bots` всех пользователей (или
   пропускается при отправке — без утечки).
5. **Клиент.** Настройки → Уведомления → «Задачи»: внизу секция «Передавать боту» — строка на каждого бота
   пространств пользователя с вебхуком/gateway (аватар, имя, пространство, тумблер), подпись «Бот получит ваши
   уведомления о задачах по этим настройкам». `PATCH /api/me` полным списком, оптимистично с откатом. Телефон —
   тот же экран. Четыре локали.

## Последствия
- `proto` (`TaskNoticeRelay`, `TaskNotifyBots`, поля), `make gen`; миграция 00084; `internal/users`,
  `internal/boards` (точка relay), `internal/bots` (доставка, кэш списка как `webhookBots`, инвалидация на
  `PATCH /api/me`); docs/19 (таблица событий, Webhook), docs/04 (поле), docs/05.
- Изменение протокола и путь доставки данных ботам — второе ревью обязательно (CLAUDE.md п. 5).
- Не делаем: уведомления о сообщениях комнат/DM, отдельные триггеры для бота, подписку на доску.

## Альтернативы
- **Только доски с `VIEW_BOARD` бота** — безопаснее по умолчанию, но для закрытых досок (HR) боту пришлось бы
  давать доступ к доске целиком — это шире, чем уведомления одного человека. Отклонено.
- **Бот повторяет логику сам по `taskActivity`** — нужны чужие настройки и подписки; невозможно без утечки.
