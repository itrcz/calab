# ADR-0067. Телефон: общий веб-клиент в тонкой оболочке Expo + WebView

Статус: принято (2026-10-02). Заменяет этап B [ADR-0021](0021-mobile.md) (отдельный клиент на
React Native с `packages/core`); этап A (мобильный веб) остаётся основой.

## Контекст

Этап B ADR-0021 вёл к второму UI: экраны и навигация на React Native поверх выделенного ядра.
Каждый новый раздел (доски, заметки, календарь, приложения пространства) пришлось бы делать
дважды, и мобильная версия отставала бы от веба. Мобильный веб (MobileShell, ≤ 768 px) уже
закрывает телефон: одна колонка, шторки, safe areas, клавиатура. Сессия веба — HttpOnly
SameSite cookie на том же origin, что и API (ADR-0015).

## Решение

1. **Один UI.** React DOM renderer (`apps/desktop/src/renderer`) — единственный источник экранов,
   навигации, переводов и бизнес-правил для браузера, Electron и телефона. На телефоне раздел
   требует адаптивности и проверки touch, а не отдельной реализации.
2. **Оболочка `apps/mobile`:** Expo + `react-native-webview`, один полноэкранный WebView с
   существующим HTTPS веб-клиентом. Vite остаётся; renderer не переносится в Metro, отдельной
   мобильной веб-сборки нет. Origin задаёт env `EXPO_PUBLIC_CALAB_URL` (только https, без пути и
   учётных данных); хостов в коде нет. Origin совпадает с API намеренно: работает существующая
   cookie-сессия, нативного хранения или обновления токенов нет. Сессия постоянная
   (не incognito), при ошибках cookie и хранилище не очищаются.
3. **Оболочка владеет только** экраном загрузки и ошибки с «Повторить», кнопкой «назад» Android,
   политикой навигации и разрешениями ОС для `getUserMedia` и съёмки, а на iOS — передачей
   скачанного файла системному листу «Поделиться» ([ADR-0068](0068-phone-file-downloads.md)).
   Шапок и таббаров нет.
   Safe areas применяет веб (`viewport-fit=cover` + `env(safe-area-inset-*)`), оболочка своих
   отступов не добавляет.
4. **Навигация.** Контентом приложения становится только точный origin: сравниваются
   `URL.origin`, а не префиксы или суффиксы строк. Сторонний https грузится во фрейме, только
   если событие доказывает, что это iframe приложения: iOS сообщает `isTopFrame: false` и
   `mainDocumentURL` нашего origin. Без такого доказательства (каждый запрос Android) переход
   считается переходом верхнего фрейма: чужой origin не грузится, а только уходит в ОС
   (fail-closed). Внешние http(s) и `mailto:` уходят в системный браузер или почту: новые окна и
   переходы верхнего фрейма после загрузки приложения. Жест для новых окон проверяет не
   библиотека, а блокировщик всплывающих окон движка (`javaScriptCanOpenWindowsAutomatically`
   выключен). `javascript:`, `data:`, `file:`, `blob:` и прочие схемы блокируются. Встроенный
   `originWhitelist` библиотеки не используется: он работает только в JS, сравнивает по префиксу
   и сам открывает промахи через `Linking`.
5. **Моста нет.** Нет `onMessage`, `injectedJavaScript` и нативных методов для страницы. Будущий
   мост — узкий платформенный адаптер слоя `platform` (не методы под доски или чаты). Он доступен
   только основному документу точного origin, и каждая операция авторизуется явно. Если
   изоляцию от сторонних iframe нельзя доказать на выбранном API WebView, привилегированный метод
   не включается. Мост оформляется отдельным ADR.
6. Нативные проекты (`ios/`, `android/`) генерирует `expo prebuild`, в git они не попадают.
   Идентификаторы приложения и привязка EAS приходят из env.

## Последствия

- Обычная фича — это правка общего веба. На телефоне она появляется после перезагрузки страницы,
  без пересборки и подписи, пока возможности оболочки не меняются. Новая потребность ОС —
  явное расширение оболочки и новая сборка.
- Ограничения WebView (фоновое аудио, CallKit/Telecom, push, скачивание файлов, цвет статус-бара
  по теме) закрываются платформенным адаптером или драйвером вокруг общей логики, а не
  переписыванием экранов. Перед решением о нативном медиа-драйвере звонки проверяются на
  устройствах.
- Граница origin — решение JS в `onShouldStartLoadWithRequest`, а не нативная проверка.
  На iOS (react-native-webview 13.16.1) навигация ждёт ответа JS без тайм-аута, но `isTopFrame`
  библиотека вычисляет сравнением `request.URL == request.mainDocumentURL`, а не по WKFrameInfo.
  На Android библиотека отбрасывает `isForMainFrame()`, ждёт ответа JS 250 мс и затем
  **разрешает** загрузку; о POST-переходах движок не спрашивает вовсе. `onLoadStart` →
  `stopLoading` срабатывает уже после начала загрузки: это страховка, не граница.
- **Android не проверен для релиза.** Нужны нативная проверка origin основного фрейма
  (fail-closed при тайм-ауте и для POST) и проверка на устройстве, в том числе со сторонним
  приложением пространства в iframe: если движок спросит о переходе внутри iframe, без
  идентичности фрейма переход уйдёт в системный браузер, а не загрузится на месте. Объём
  Android сохраняется; первая сборка — iOS.
- Electron по-прежнему обновляется своим механизмом.
- Наработки RN-эксперимента (CallKit, push, нативное медиа) не подключаются. Их переносят
  выборочно, когда до них дойдёт план.
