# ADR-0083: Точка — второй эквайер (RU, ₽), рынок по выбору владельца до первой оплаты

Дата: 2026-10-10. Статус: **принят, фаза 1; реальные платежи выключены** (`BILLING_TOCHKA_ENABLED=false`).
Уточняет [ADR-0080](0080-seat-billing.md) §2.1, §6, §9, §11.2 и §13; где тексты расходятся — действует этот.
Исследование API: снимок `llms-full.txt` и `swagger.json` от 10.10.2026, живые запросы на боевом
токене (только чтение и две неоплаченные ссылки по 1 ₽, см. «Проверки»).

## Контекст

Ядро биллинга (ADR-0080 v5) спроектировано под эквайера за абстракцией `internal/billing/provider`;
Stripe — первый (Global, $). Для RU (₽) мерчант в Точке уже подключён: торговая точка `REG`,
`paymentModes=[sbp, card, …]`, облачная касса `digitalKassaTochka` (чеки 54-ФЗ банк фискализирует сам).
У Точки два продукта: интернет-эквайринг Точка.API (платёжные ссылки и подписки, hosted-форма,
без PCI) и Pay Gateway (свой UI, токены карт и СБП, нужен AOC PCI DSS и онбординг). Фаза 1 строится
на первом.

Решения владельца 10.10.2026: юрлицо, налоговый режим и НДС — как в публичной оферте (ООО «Громтех»,
АУСН, без НДС); токен уже с нужными правами; чеки — облачная касса банка; ручное пополнение
150..500 000 ₽; живая проверка 1–2 ₽ с возвратом — вместе с владельцем. Рынок определяется так
(владелец, 10.10): язык интерфейса — только подсказка, рынок фиксируется первой оплатой, суперадмин
закрывает эквайер для новых клиентов без выкладки.

## Решение

### 1. Что умеет адаптер (`providers/tochka`)

- **Ручное пополнение**: `POST /acquiring/v1.0/payments_with_receipt`, один способ на ссылку —
  `card` («Карта МИР») или `sbp` («СБП»); в матрице это две строки `tochka:card`, `tochka:sbp` рынка
  `ru`, плательщик выбирает. `paymentLinkId` = id нашего checkout, `consumerId` = id billing account,
  `ttl` = остаток жизни checkout (≤ 35 мин), `preAuthorization` не используется.
- **Чек 54-ФЗ**: одна позиция «Пополнение баланса Calab», `full_prepayment`, `service`, `шт.`,
  `taxSystemCode=usn_income` (АУСН «доходы»; `TOCHKA_TAX_SYSTEM`), `vatType=none` (`TOCHKA_VAT_TYPE`),
  `Client.email` — e-mail плательщика, иначе владельца. Чек на зачёт аванса банк не выпускает —
  открытый вопрос ADR-0080 §13 остаётся.
- **Деньги**: суммы банка — десятичные рубли в JSON number/string; разбираются точно в копейки
  `int64` (`money.ParseDecimal`), отправляются как `money.Decimal()`; float нигде.
- **TLS**: сертификат `enter.tochka.com` выпущен Russian Trusted Sub CA (Минцифры), его нет в системных
  хранилищах. Клиент адаптера доверяет системным корням + вшитым Root/Sub CA; проверка TLS не
  отключается, другие клиенты сервера эти корни не получают.
- **Ошибки**: таймаут, 5xx, 429 и нечитаемый 2xx — `ErrUnknownOutcome`; 404 и 424 «not found» —
  `ErrNotFound` (банк отвечает 424 на неизвестную операцию); 424 «заказ … существует» — дубль
  `paymentLinkId`; прочие 4xx — окончательный отказ. Сообщения без токена, тел запросов и ссылок.

### 2. «Сверяемое списание» вместо ключей идемпотентности

Ключей идемпотентности у Точки нет нигде. Вводится `CapReconcilableCharge`: создание **не**
идемпотентно, но каждое движение денег видно в операции (`Order[]`, статус платежа), поэтому
неизвестный исход разрешается чтением, а не повтором. `Cap.SafeRetry()` = `CapIdempotentCharge`.

- **Ссылка**: повтор создания после потерянного ответа идёт с тем же `paymentLinkId`; банк отвечает
  424 «существует» (проверено вживую), адаптер находит ссылку в списке операций за окно дат и
  возвращает её. Другая сумма/consumer под тем же id — `ErrUnknownOutcome`, ссылка не используется.
- **Возврат** отправляется не более одного раза: `billing_refunds.dispatched_at` коммитится до
  запроса; повтор того же admin `request_id`, сверка и перезапуск только читают (`ListRefunds` по
  `Order[]` → `ApplyRefund` сопоставляет с ожидающим возвратом той же суммы). Ничего не нашлось
  за 24 ч — `needs_review`, деньги остаются в резерве.
- **Автопополнение** (фаза 2): `Registry.OffSession` по-прежнему требует `CapIdempotentCharge`;
  Точка допускается только вместе с диспетчером без повторов (одна попытка, unknown блокирует,
  сверка по `Order[]` подписки, ADR-0080 §11.2).

### 3. Вебхуки только об успехе → обязательный опрос

- `POST /api/billing/tochka/webhook`: тело — «голый» JWT RS256. Подпись проверяется **закреплённым**
  ключом (опубликованный 10.10.2026 вшит в адаптер; `TOCHKA_WEBHOOK_PUBLIC_KEY` — замена или массив
  на время ротации; URL ключа из запроса не используется; `server tochka key` сверяет с
  опубликованным). Неверная подпись — 400, ничего не сохраняется.
- Тело — подсказка: в inbox пишется только id операции; перед зачислением операция перечитывается
  (`GET /payments/{id}`), сумма и статус берутся из ответа, не из вебхука. Один кредит на операцию —
  прежний `UNIQUE(provider, provider_account, livemode, provider_payment_id)`.
  `EventID` = хеш (тип, операция, статус, способ, сумма, `transactionId`, клиент): повторная доставка —
  одна строка inbox.
- Проверенные, но не наши вебхуки (другой тип, чужой `customerCode`/`merchantId` — тестовые вебхуки
  банка при регистрации, `AUTHORIZED`) сохраняются как `ignored` и получают 200.
- Банк не сообщает об отказе, истечении и возвратах (`CapSuccessOnlyWebhooks`), а не-200 повторяет
  30 раз раз в 10 с и бросает. Поэтому открытые checkout такого провайдера опрашиваются с
  отступом (`billing_checkouts.next_poll_at/polls`): 30 с, 1, 2, 4, 8 мин, далее раз в 15 мин, пока
  не закроются (`EXPIRED` → expired, оплачено → кредит). Ожидающие возвраты дочитываются сверкой
  раз в 5 мин. Работает и совсем без вебхука.
- Регистрация URL — шаг оператора (`server tochka webhook set <url>`), не при старте. Один URL на
  `client_id`; банк создаёт вебхук, только если тестовые вебхуки получили 200, поэтому прод-URL
  регистрируется после выкладки с `BILLING_TOCHKA_ENABLED=true`.

### 4. Возвраты, споры

- Карта и СБП по ссылке — `POST /payments/{id}/refund`, полный и частичный; статус возврата берётся
  из статуса платежа (`ON-REFUND` → pending, `REFUNDED`/`REFUNDED_PARTIALLY` → succeeded), id —
  `{operationId}:{orderId}`. `isRefund=false` — окончательный отказ, резерв возвращается.
- Цифровой рубль (и платежи подписок — фаза 2) API не возвращает: `provider.ErrNotSupported`,
  запрос не отправляется, возврат сразу `needs_review`; оператор возвращает в интернет-банке, сверка
  находит возврат в `Order[]` и закрывает строку (если банк его там показывает; иначе — release по
  ADR-0080).
- API споров нет (`CapDisputes` не выставлен): чарджбеки — из выписки/почты банка вручную.

### 5. Рынок: выбор владельца, фиксация первой оплатой, открытые эквайеры

- Рынок **нового** счёта открыт, если его эквайер настроен (`BILLING_*_ENABLED` + `BILLING_PROVIDERS`)
  и суперадмин не закрыл его для новых клиентов (`billing_provider_settings.accept_new`, по умолчанию
  открыт; `GET/PUT /api/admin/billing/providers`, аудит «было → стало»). Режимы: оба рынка, только
  Россия, только Global, «связаться с нами» (закрыты оба — разрешено).
- До первой оплаты (`billing_accounts.entry_seq = 0`, нет ни одного `billing_payments`, нет открытого
  checkout) рынок, валюта и эквайер счёта меняются: владелец — явным `market` в quote ACTIVATE
  (self-serve создаёт счёт сразу в выбранном рынке), суперадмин — `POST /api/admin/billing/accounts/{id}/market`
  с `expected_revision` и аудитом. Одна функция ядра `SwitchMarketIn` под блокировкой счёта; checkout
  под той же блокировкой перепроверяет рынок, поэтому гонка «оплата против смены» не смешивает
  валюты. После первого кредита смена — 409 `BILLING_MARKET_FIXED`; дальше как ADR-0080 §2.1
  (закрыть/вернуть остаток и новый счёт), UI для этого в v1 нет.
- Сервер берёт рынок только из явного запроса, проверяя, что он открыт (422
  `BILLING_MARKET_UNAVAILABLE`). Клиент лишь предвыбирает: запомненный выбор пользователя на этом
  устройстве, иначе язык интерфейса (ru → Россия), и только когда открыты оба рынка; при одном
  открытом рынке переключателя нет, в режиме «связаться» шаг оплаты не показывается, цены — по
  Global, у платных тарифов — «Связаться с нами» (`PLAN_CONTACT_URL` / `PLAN_CONTACT_EMAIL`).
  На экране тарифа рядом с переключателем — продавец и валюта рынка (ADR-0080 §2.1).
- Счёт, закреплённый оплатой, платит через свой эквайер, даже если тот закрыт для новых.
- `GET /api/billing/public/offers` (без сессии, `Cache-Control: max-age=300`, лимит 30/мин на IP):
  режим, цены за место в сутки открытых рынков (Global в режиме «связаться»), контакт — для лендинга.
  Никаких данных счетов.

### 6. Конфигурация

`BILLING_TOCHKA_ENABLED`, `TOCHKA_API_TOKEN`, `TOCHKA_CUSTOMER_CODE`, `TOCHKA_MERCHANT_ID`,
`TOCHKA_API_URL`, `TOCHKA_TAX_SYSTEM`, `TOCHKA_VAT_TYPE`, `TOCHKA_WEBHOOK_PUBLIC_KEY`,
`TOCHKA_CLIENT_ID` — только env (`apps/server/README.md`, `infra/docker/.env.example`). У Точки нет
тестового режима оплат: `Livemode` всегда true (кроме песочницы), защита — выключенный по умолчанию
флаг и сверка `customerCode`/`merchantId` каждой операции.

## Последствия

- Ядро не менялось в денежной части: тот же inbox, один кредит на операцию, один `SELECT … FOR UPDATE`
  счёта, сеть вне транзакций. Добавлены: `CapReconcilableCharge`, `CapSuccessOnlyWebhooks`,
  `ErrNotSupported`, `CheckoutReq.ReceiptEmail`, миграция `00077_billing_tochka.sql`
  (настройки эквайеров, опрос checkout, `dispatched_at` возвратов).
- Цены RU — уже существующие версии `ru` (6 / 18 ₽ за место в сутки).
- Вне фазы 1: автопополнение картой через подписку без графика (фаза 2), привязка СБП через
  Pay Gateway (фаза 3, PCI/онбординг), счета для юрлиц.

## Проверки и открытые вопросы

- Вживую 10.10.2026 (боевой токен, без оплат): список клиентов/точек/операций, две ссылки 1 ₽ с одним
  `paymentLinkId` — вторая получила 424 «заказ … существует», ссылка истекла (`EXPIRED`) примерно через
  10 мин после `ttl=5`; неизвестная операция — 424 «Order not found». В ответе чтения позиция чека
  показана как `full_payment`, хотя отправлена `full_prepayment` — проверить на чеке живой оплаты.
- Оплата 1–2 ₽ и возврат — вместе с владельцем (шаги в PR): форма чека, `paymentType`, появление
  возврата в `Order[]`, приём карт не-МИР (тогда подпись «Карта МИР» можно расширить).
- АУСН «доходы» или «доходы минус расходы» — подтвердить у бухгалтера (`TOCHKA_TAX_SYSTEM`).
