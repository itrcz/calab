# ADR-0060: Автоматизации досок — правила «Когда → Если → Тогда» и Git-связи (2026-10-03)

**Статус: принято.** Релиз — следующий минорный после 2.1.0, **после** мержа ADR-0059 (общие файлы `internal/boards`,
`boards.proto`). Миграция **00062** (00060 — ADR-0059, 00061 — ADR-0061). События шлюза: **92–94** (после 87–91
ADR-0058; классифицировать в `gateway/identity.go: eventScope`, канал пространства, маршрут — зрителям доски).
Опирается на ADR-0042/0049/0058 (журнал `task_activity`, `TaskFilter` + `Translate`, вебхук и `internal/webhook`,
фичи доски, свипер), ADR-0048 (`MANAGE_INTEGRATIONS`), ADR-0024 (тарифы).

## Контекст
Владелец (03.10): «автоматизации для досок: разрабы могут делать с гитом интеграции, менеджеры — после согласования
двигать статус автоматом; подумать, какие могут быть автоматизации, чтобы было удобно и гибко». Решения владельца:
v1 = правила **и** Git-связи; Git — GitHub + GitLab + Gitea/Forgejo через входящие вебхуки без OAuth-приложений;
тариф Team+; настраивает `MANAGE_BOARD`, Git-вебхук — ещё и `MANAGE_INTEGRATIONS`.

Принцип: **не скриптовый движок, а сборка из того, что уже есть** — триггеры = виды записей `task_activity`,
условия = сохранённый `TaskFilter` (тот же поповер фильтра и тот же `Translate` в SQL), действия = существующие
операции над задачей через те же функции, что REST (`change`, approval gate, чек-листы), выполняемые в той же транзакции.

## Решение

### 1. Модель
```
board_rules        id uuidv7, board_id → boards CASCADE, name (1..60), enabled bool, position,
                   trigger jsonb (RuleTrigger, protojson), condition jsonb? (TaskFilter), actions jsonb (RuleAction[],
                   1..5), created_by, created_at, updated_at, runs_count int, last_run_at?, last_error?    (≤ 20 на доску)
board_rule_runs    id uuidv7, rule_id → board_rules CASCADE, task_id → tasks SET NULL, trigger_kind text,
                   ok bool, error text?, actions_applied smallint, created_at        (≤ 100 на правило: лишние чистит свипер)
board_git          board_id PK → boards CASCADE, provider ('github'|'gitlab'|'gitea'), secret_enc bytea (sealbox),
                   created_by, created_at, last_event_at?, last_error?, events_count int
task_git_links     id uuidv7, task_id → tasks CASCADE, kind ('branch'|'pr'|'commit'), provider, repo (owner/name),
                   ref (ветка / номер PR / sha), title (≤ 200), url (≤ 2048), state ('open'|'merged'|'closed'|''),
                   author (≤ 100), created_at, updated_at;  UNIQUE (task_id, kind, provider, repo, ref); ≤ 50 на задачу
```
`tasks` без изменений; у задачи появляется `repeated TaskGitLink git_links` только в `GET /tasks/{id}` (как `checklists`)
и счётчик `git_links_count` в карточке.

### 2. Правило: триггер → условие → действия
**Триггер** (`RuleTrigger`, oneof):
- `task_created` · `status_changed {to_status_id?, from_status_id?, to_type?}` · `approval_changed {state:
  APPROVED|REJECTED}` · `assignees_changed {added?: bool, removed?: bool, lead?: bool}` · `label_changed {label_id,
  added: bool}` · `priority_changed {to_priority?}` · `checklist_completed` (все пункты всех чек-листов) ·
  `comment_created` · `git {event: BRANCH_CREATED|PR_OPENED|PR_MERGED|PR_CLOSED|COMMIT_PUSHED}` ·
  **по расписанию** (свипер досок, раз в 15 мин): `due_in {days: 0..30}` (срок наступит через N дней; 0 = сегодня) ·
  `overdue {days: 0..30}` (просрочена на N дней) · `stale {days: 1..90}` (нет изменений N дней, статус не завершён).
  Расписание срабатывает **один раз на задачу на день** (ключ `(rule_id, task_id, date)` в `board_rule_runs`).
- Все триггеры по изменениям берутся из записей `task_activity` транзакции (`change` в `tasks.go`) — журнал, вебхук
  и правила видят одно и то же; Git-события — из входящего вебхука (§4).

**Условие** — `TaskFilter` (опционально). Проверяется после изменения тем же `Translate`:
`SELECT EXISTS (SELECT 1 FROM tasks t WHERE t.id = $1 AND <cond>)` внутри транзакции. Для `status_changed` можно
условие «из статуса» — поле триггера, не фильтра (состояние «до» в фильтре не выразимо).

**Действия** (`RuleAction`, oneof; ≤ 5, выполняются по порядку, атомарно — одна ошибка откатывает действия правила,
но **не** исходное изменение пользователя: правило выполняется в savepoint’е):
- `set_status {status_id}` — через тот же путь, что `PATCH` (approval gate действует: несогласованную «дальше» не
  двинет — ошибка в лог правила) · `set_assignees {mode: SET|ADD|REMOVE|CLEAR, user_ids, lead_user_id?, special:
  CREATOR|ACTOR}` · `set_labels {add_ids, remove_ids}` · `set_priority {priority}` · `set_due {days_from_now | clear}`
  · `set_approvers {user_ids, required}` · `add_checklist {name, items[] (шаблон, ≤ 100)}` · `comment {template ≤ 2000;
  переменные {key} {title} {status} {actor} {assignees} {due} {url}}` · `notify_room {room_id, template}` (сообщение
  от имени «Автоматизация» в текстовую комнату пространства — системное `SystemMessage.automation`, `payload = 5`,
  рендер как карточка задачи с текстом) · `notify_dm {to: ASSIGNEES|LEAD|CREATOR|APPROVERS, template}` (уведомление
  «Задачи» существующего типа `TASK_RULE`, с настройкой уровня как у остальных) · `create_subtasks {titles[] ≤ 10}` ·
  `archive`.
- **Актор** действий — особый `actor_id = NULL` + `rule_id` в `task_activity` (новая колонка `rule_id uuid?`), в журнале
  и вебхуке — `"actor": null, "rule": {"id","name"}`; клиент пишет «Автоматизация: имя правила». Права пользователя не
  проверяются — правило действует от имени доски (его создал `MANAGE_BOARD`); инварианты (approval gate, фичи доски,
  лимиты) — проверяются.
- **Цепочки.** Изменения, сделанные правилом, тоже порождают записи журнала и могут триггерить другие правила той же
  доски: глубина ≤ 3, одно правило — не более одного раза в цепочке, цикл — ошибка `RULE_LOOP` в лог. Правила других
  досок (перенос) не запускаются.
- Отключённое правило (`enabled = false`) и правила архивной доски не выполняются; удалённый статус/лейбл/пользователь в
  действии → действие пропускается с записью в лог, правило помечается `last_error`, UI показывает «⚠ требует внимания».
- **Шаблоны** при первом открытии вкладки (клиент, не сервер): «Согласовано → В работу», «Отклонено → назад к автору»,
  «Все пункты чек-листа → Готово», «PR открыт → На ревью», «PR смержен → Готово», «Просрочено → Срочно + комментарий»,
  «Новая задача → назначить …», «Без движения 14 дней → напомнить исполнителю».

### 3. API правил
- `GET/POST /api/boards/{id}/rules`, `PATCH/DELETE /api/rules/{id}`, `POST /api/rules/{id}/test {task_id}` (сухой прогон:
  проверить условие и перечислить действия без выполнения — `RuleTestResponse {matches, actions[] {kind, summary,
  problem?}}`), `GET /api/rules/{id}/runs?limit` (≤ 100, новые первыми). Право — `MANAGE_BOARD`; боты — читать можно,
  менять — 403 `BOT_NOT_ALLOWED`. Тариф: `automations` в лимитах тарифа (Team+), иначе `409 PLAN_LIMIT`; при понижении
  тарифа правила перестают выполняться (не удаляются), UI показывает плашку.
- Валидация: `name`, `trigger` корректен для фич доски (триггер по срокам при выключенной фиче `DUE_DATES` — 409
  `FEATURE_DISABLED`), `actions` 1..5, ссылки (статусы/лейблы/пользователи) существуют и принадлежат доске/пространству,
  шаблоны ≤ 2000, `TaskFilter` проходит `Translate` в режиме «проверка».
- События шлюза: `BOARD_RULE_UPDATE = 92 {workspace_id, board_id, rule}` (create/update), `BOARD_RULE_DELETE = 93`,
  `TASK_GIT_LINKS_UPDATE = 94 {workspace_id, board_id, task_id, links[], count}` — зрителям доски (`routeBoards`,
  участникам по карточкам ADR-0059 — `TASK_GIT_LINKS_UPDATE` своей задачи). `Board.rules_count` для списка.

### 4. Git-связи
- **Настройка**: `PUT /api/boards/{id}/git {provider, secret?}` (`MANAGE_BOARD` **и** `MANAGE_INTEGRATIONS`; секрет как у
  вебхука доски — свой 16..256 или сгенерированный, возвращается **один раз**), `GET` → `{provider, has_secret, url,
  last_event_at, events_count, last_error}`, `DELETE`. URL для репозитория: `<PUBLIC_APP_URL>/api/git/boards/{board_id}/
  {provider}` — его человек вставляет в настройки репозитория (GitHub: Webhooks → content type `application/json`,
  secret; GitLab: Secret token; Gitea: HMAC secret). Инструкция с копируемым URL — в UI, на трёх провайдеров.
- **Приём**: `POST /api/git/boards/{id}/{provider}` — **публичный маршрут без сессии** (как `/api/rtc/webhook`): проверка
  подписи провайдера (GitHub `X-Hub-Signature-256` HMAC-SHA256; GitLab `X-Gitlab-Token` сравнение в константное время;
  Gitea `X-Gitea-Signature` HMAC-SHA256), тело ≤ 1 МБ, лимит 60/мин на доску, ответ `204`; неверная подпись — `401`,
  неизвестное событие — `204` (игнор). Идемпотентность — `X-GitHub-Delivery` / `X-Gitlab-Event-UUID` / `X-Gitea-Delivery`
  в Valkey на 24 ч. Классификация route census — публичная (как `/api/rtc/webhook`), identity scope не применяется.
- **Разбор** (`internal/boards/git/*.go`, по провайдеру → общая структура `GitEvent {kind, repo, ref, title, url, state,
  author, keys[]}`): события `push` (ветки: `create`/`push` — имя ветки и сообщения коммитов), `pull_request` /
  `merge_request` (`opened`, `reopened`, `closed` с `merged`, `edited` заголовка). **Ключи задач** ищутся регуляркой
  `\b([A-Z0-9]{2,6})-(\d+)\b` в имени ветки, заголовке PR/MR, теле PR и сообщениях коммитов; ключ сопоставляется с
  задачей **этой доски** по `board.key` (чужие доски — игнор: вебхук привязан к доске). На задачу — ≤ 50 связей, старые
  коммиты вытесняются.
- **Результат**: upsert `task_git_links` (PR меняет `state`/`title`), запись журнала `git` (`before/after` — связь),
  событие `TASK_GIT_LINKS_UPDATE`, вебхук доски `task.updated` с `changes[field=git]`, триггер правил `git {event}` —
  всё в одной транзакции. Smart-commit `FNG-12 #done` / `#status:<имя>` — **не в v1** (бэклог: переходы делать правилами
  «PR смержен → Готово», это явнее).
- **Клиент**: в панели задачи секция «Git» (под вложениями; `GitBranch`-иконка): строки — иконка вида (ветка / PR
  открыт зелёный / смержен фиолетовый / закрыт серый / коммит), `repo#123` или имя ветки, заголовок, автор, относительное
  время; клик — внешняя ссылка (`shell.openExternal`, подтверждение домена как у ссылок). На карточке канбана — чип
  `⎇ 2` (счётчик). В настройках доски — вкладка «Git»: провайдер, секрет, URL с кнопкой «Скопировать», статус последнего
  события, инструкция.

### 5. Выполнение и производительность
- Правила загружаются один раз на транзакцию изменения (`ListEnabledRules(board_id)` — индекс `(board_id) WHERE enabled`;
  доска без правил — один индексный lookup, как вебхук). Условие — один `EXISTS`. Действия — те же функции, что REST.
- Расписание: свипер досок (`sweep.go`, уже раз в час) получает тик 15 мин для правил по срокам: один запрос на доску с
  такими правилами (`tasks` с `due_on` в окне / `updated_at` старше N), пропуская уже выполненные сегодня.
- Лог: `board_rule_runs` — вставка в той же транзакции; свипер обрезает до 100 на правило и удаляет старше 90 дней.
- Шлюз: `BOARD_RULE_*` — только зрителям с `MANAGE_BOARD`? Нет — всем зрителям доски (правила — часть доски, видны в
  настройках только управляющим, но счётчик и «Автоматизация» в журнале нужны всем); клиент прячет вкладку без права.

### 6. Клиент — настройки доски → вкладка «Автоматизации» (`features/boards/Rules.tsx`, docs/08 «Доски»)
- Список правил: карточки-строки — тумблер, название, подпись «Когда … → тогда …» (генерируется из структуры), счётчик
  срабатываний, время последнего, «⚠» при `last_error`; D&D-порядок; «+ Правило» и «Из шаблона ▾».
- Редактор (лист 560 px): три блока с заголовками **Когда** / **Если** / **Тогда**. «Когда» — select триггера с
  параметрами (чипы статусов/лейблов). «Если» — тот же компонент фильтра, что на доске (`lib/boards/filterFields`),
  «+ условие». «Тогда» — список действий (≤ 5): каждое — строка с иконкой, select вида и параметрами (пикер участников,
  статусы, шаблон текста с подсказкой переменных), «+ действие», перетаскивание порядка. Внизу: «Проверить на задаче…»
  (пикер задачи → результат сухого прогона: совпало / не совпало, список действий, проблемы красным), «Сохранить».
- «Журнал» правила — список срабатываний: время, задача (ключ → панель), результат, ошибка.
- В ленте активности задачи — записи с актором «⚙ Автоматизация: имя правила»; в тосте при изменении, сделанном
  правилом (например, карточка уехала в другой статус), ничего особенного — обычный `TASK_UPDATE`.
- Тариф ниже Team — вкладка показывает `PlanPill` и объяснение, правила read-only.
- Производительность: вкладка грузит правила по открытию; события `BOARD_RULE_*` обновляют одну строку. i18n 4 языка.
  Визуальных прогонов нет; QA скриншотами: список, редактор, Git-секция панели задачи, настройки Git.

- `packages/protocol`: unit на `ruleSummary()` (подпись «Когда … → тогда …») — общая функция для клиента и ботов.
- Docs: `04` (таблицы), `16` (права: правила, Git), `19-bot-api*` (чтение правил, 403, `SystemMessage.automation`,

## Не входит (бэклог docs/12)
Smart-commits; GitHub App/OAuth с обратной связью в PR (статус-чек, комментарий); действия «вызвать URL» (есть вебхук
доски) и «создать задачу по расписанию» (повторяющиеся задачи — отдельная тема); правила уровня пространства; вручение
ачивок правилом (ADR-0061 — после обоих); условия по «до» состояния кроме статуса; переменные с датами в шаблонах
сверх `{due}`.

## Последствия
- Менеджерский сценарий «согласовано → в работу» и девелоперский «PR смержен → готово» — без ботов и внешнего кода.
- Условия и фильтры доски — одна модель: новое поле фильтра автоматически доступно в правилах.
- Появляется публичный входящий маршрут с проверкой подписи — security-ревью обязательно; лимиты и идемпотентность
  защищают от шторма событий из крупных репозиториев.
