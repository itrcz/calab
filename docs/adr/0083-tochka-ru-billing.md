# ADR-0083: Точка — второй эквайер (RU, ₽), рынок по выбору владельца до первой оплаты

Дата: 2026-10-10. Статус: **принят, фаза 1; реальные платежи выключены** (`BILLING_TOCHKA_ENABLED=false`);
фаза 2 (сохранённая карта, один клик) — код готов, выключена до живой проверки
(`TOCHKA_RECURRING_ENABLED=false`); фаза 3 (привязка СБП) — адаптер готов, выключен, ждёт онбординга банка.
Уточняет [ADR-0080](0080-seat-billing.md) §2.1, §6, §9, §11.2 и §13; где тексты расходятся — действует этот.
Исследование API: снимок `llms-full.txt` и `swagger.json` от 10.10.2026, живые запросы на боевом
токене (только чтение и две неоплаченные ссылки по 1 ₽, см. «Проверки»).

## Контекст

Ядро биллинга (ADR-0080 v5) спроектировано под эквайера за абстракцией `internal/billing/provider`;
Stripe — первый (Global, $). Для RU (₽) мерчант в Точке уже подключён: торговая точка `REG`,
`paymentModes=[sbp, card, …]`, облачная касса `digitalKassaTochka` (чеки 54-ФЗ банк фискализирует сам).
У Точки два продукта: интернет-эквайринг Точка.API (платёжные ссылки и подписки, hosted-форма,
без PCI) и Pay Gateway (свой UI, токены карт и СБП, нужен AOC PCI DSS и онбординг). Фаза 1 строится
на первом.

Решения владельца 10.10.2026: юрлицо, налоговый режим и НДС — как в публичной оферте (ООО «Громтех»,
АУСН, без НДС); токен уже с нужными правами; чеки — облачная касса банка; ручное пополнение
150..500 000 ₽; живая проверка 1–2 ₽ с возвратом — вместе с владельцем. Рынок определяется так
(владелец, 10.10): язык интерфейса — только подсказка, рынок фиксируется первой оплатой, суперадмин
закрывает эквайер для новых клиентов без выкладки.

## Решение

### 1. Что умеет адаптер (`providers/tochka`)

- **Ручное пополнение**: `POST /acquiring/v1.0/payments_with_receipt`, один способ на ссылку —
  `card` («Карта МИР») или `sbp` («СБП»); в матрице это две строки `tochka:card`, `tochka:sbp` рынка
  `ru`, плательщик выбирает. `paymentLinkId` = id нашего checkout, `consumerId` = id billing account,
  `ttl` = остаток жизни checkout (≤ 35 мин), `preAuthorization` не используется.
- **Чек 54-ФЗ**: одна позиция «Пополнение баланса Calab», `full_prepayment`, `service`, `шт.`,
  `taxSystemCode=usn_income` (АУСН «доходы»; `TOCHKA_TAX_SYSTEM`), `vatType=none` (`TOCHKA_VAT_TYPE`),
  `Client.email` — e-mail плательщика, иначе владельца. Чек на зачёт аванса банк не выпускает —
  открытый вопрос ADR-0080 §13 остаётся.
- **Деньги**: суммы банка — десятичные рубли в JSON number/string; разбираются точно в копейки
  `int64` (`money.ParseDecimal`), отправляются как `money.Decimal()`; float нигде.
- **TLS**: сертификат `enter.tochka.com` выпущен Russian Trusted Sub CA (Минцифры), его нет в системных
  хранилищах. Клиент адаптера доверяет системным корням + вшитым Root/Sub CA; проверка TLS не
  отключается, другие клиенты сервера эти корни не получают.
- **Ошибки**: таймаут, 5xx, 429 и нечитаемый 2xx — `ErrUnknownOutcome`; 404 и 424 «not found» —
  `ErrNotFound` (банк отвечает 424 на неизвестную операцию); 424 «заказ … существует» — дубль
  `paymentLinkId`; прочие 4xx — окончательный отказ. Сообщения без токена, тел запросов и ссылок.

### 2. «Сверяемое списание» вместо ключей идемпотентности

Ключей идемпотентности у Точки нет нигде. Вводится `CapReconcilableCharge`: создание **не**
идемпотентно, но каждое движение денег видно в операции (`Order[]`, статус платежа), поэтому
неизвестный исход разрешается чтением, а не повтором. `Cap.SafeRetry()` = `CapIdempotentCharge`.

- **Ссылка**: повтор создания после потерянного ответа идёт с тем же `paymentLinkId`; банк отвечает
  424 «существует» (проверено вживую), адаптер находит ссылку в списке операций за окно дат и
  возвращает её. Другая сумма/consumer под тем же id — `ErrUnknownOutcome`, ссылка не используется.
- **Возврат** отправляется не более одного раза: `billing_refunds.dispatched_at` коммитится до
  запроса; повтор того же admin `request_id`, сверка и перезапуск только читают (`ListRefunds` по
  `Order[]` → `ApplyRefund` сопоставляет с ожидающим возвратом той же суммы). Ничего не нашлось
  за 24 ч — `needs_review`, деньги остаются в резерве.
- **Автопополнение** (фаза 2): `Registry.OffSession` по-прежнему требует `CapIdempotentCharge`;
  Точка допускается только вместе с диспетчером без повторов (одна попытка, unknown блокирует,
  сверка по `Order[]` подписки, ADR-0080 §11.2).

### 3. Вебхуки только об успехе → обязательный опрос

- `POST /api/billing/tochka/webhook`: тело — «голый» JWT RS256. Подпись проверяется **закреплённым**
  ключом (опубликованный 10.10.2026 вшит в адаптер; `TOCHKA_WEBHOOK_PUBLIC_KEY` — замена или массив
  на время ротации; URL ключа из запроса не используется; `server tochka key` сверяет с
  опубликованным). Неверная подпись — 400, ничего не сохраняется.
- Тело — подсказка: в inbox пишется только id операции; перед зачислением операция перечитывается
  (`GET /payments/{id}`), сумма и статус берутся из ответа, не из вебхука. Один кредит на операцию —
  прежний `UNIQUE(provider, provider_account, livemode, provider_payment_id)`.
  `EventID` = хеш (тип, операция, статус, способ, сумма, `transactionId`, клиент): повторная доставка —
  одна строка inbox.
- Проверенные, но не наши вебхуки (другой тип, чужой `customerCode`/`merchantId` — тестовые вебхуки
  банка при регистрации, `AUTHORIZED`) сохраняются как `ignored` и получают 200.
- Банк не сообщает об отказе, истечении и возвратах (`CapSuccessOnlyWebhooks`), а не-200 повторяет
  30 раз раз в 10 с и бросает. Поэтому открытые checkout такого провайдера опрашиваются с
  отступом (`billing_checkouts.next_poll_at/polls`): 30 с, 1, 2, 4, 8 мин, далее раз в 15 мин, пока
  не закроются (`EXPIRED` → expired, оплачено → кредит). Ожидающие возвраты дочитываются сверкой
  раз в 5 мин. Работает и совсем без вебхука.
- Регистрация URL — шаг оператора (`server tochka webhook set <url>`), не при старте. Один URL на
  `client_id`; банк создаёт вебхук, только если тестовые вебхуки получили 200, поэтому прод-URL
  регистрируется после выкладки с `BILLING_TOCHKA_ENABLED=true`.

### 4. Возвраты, споры

- Карта и СБП по ссылке — `POST /payments/{id}/refund`, полный и частичный; статус возврата берётся
  из статуса платежа (`ON-REFUND` → pending, `REFUNDED`/`REFUNDED_PARTIALLY` → succeeded), id —
  `{operationId}:{orderId}`. `isRefund=false` — окончательный отказ, резерв возвращается.
- Цифровой рубль (и платежи подписок — фаза 2) API не возвращает: `provider.ErrNotSupported`,
  запрос не отправляется, возврат сразу `needs_review`; оператор возвращает в интернет-банке, сверка
  находит возврат в `Order[]` и закрывает строку (если банк его там показывает; иначе — release по
  ADR-0080).
- API споров нет (`CapDisputes` не выставлен): чарджбеки — из выписки/почты банка вручную.

### 5. Рынок: выбор владельца, фиксация первой оплатой, открытые эквайеры

- Рынок **нового** счёта открыт, если его эквайер настроен (`BILLING_*_ENABLED` + `BILLING_PROVIDERS`)
  и суперадмин не закрыл его для новых клиентов (`billing_provider_settings.accept_new`, по умолчанию
  открыт; `GET/PUT /api/admin/billing/providers`, аудит «было → стало»). Режимы: оба рынка, только
  Россия, только Global, «связаться с нами» (закрыты оба — разрешено).
- До первой оплаты (`billing_accounts.entry_seq = 0`, нет ни одного `billing_payments`, нет открытого
  checkout) рынок, валюта и эквайер счёта меняются: владелец — явным `market` в quote ACTIVATE
  (self-serve создаёт счёт сразу в выбранном рынке), суперадмин — `POST /api/admin/billing/accounts/{id}/market`
  с `expected_revision` и аудитом. Одна функция ядра `SwitchMarketIn` под блокировкой счёта; checkout
  под той же блокировкой перепроверяет рынок, поэтому гонка «оплата против смены» не смешивает
  валюты. После первого кредита смена — 409 `BILLING_MARKET_FIXED`; дальше как ADR-0080 §2.1
  (закрыть/вернуть остаток и новый счёт), UI для этого в v1 нет.
- Сервер берёт рынок только из явного запроса, проверяя, что он открыт (422
  `BILLING_MARKET_UNAVAILABLE`). Клиент лишь предвыбирает: запомненный выбор пользователя на этом
  устройстве, иначе язык интерфейса (ru → Россия), и только когда открыты оба рынка; при одном
  открытом рынке переключателя нет, в режиме «связаться» шаг оплаты не показывается, цены — по
  Global, у платных тарифов — «Связаться с нами» (`PLAN_CONTACT_URL` / `PLAN_CONTACT_EMAIL`).
  На экране тарифа рядом с переключателем — продавец и валюта рынка (ADR-0080 §2.1).
- Счёт, закреплённый оплатой, платит через свой эквайер, даже если тот закрыт для новых.
- `GET /api/billing/public/offers` (без сессии, `Cache-Control: max-age=300`, лимит 30/мин на IP):
  режим, цены за место в сутки открытых рынков (Global в режиме «связаться»), контакт — для лендинга.
  Никаких данных счетов.

### 6. Конфигурация

`BILLING_TOCHKA_ENABLED`, `TOCHKA_API_TOKEN`, `TOCHKA_CUSTOMER_CODE`, `TOCHKA_MERCHANT_ID`,
`TOCHKA_API_URL`, `TOCHKA_TAX_SYSTEM`, `TOCHKA_VAT_TYPE`, `TOCHKA_WEBHOOK_PUBLIC_KEY`,
`TOCHKA_CLIENT_ID` — только env (`apps/server/README.md`, `infra/docker/.env.example`). У Точки нет
тестового режима оплат: `Livemode` всегда true (кроме песочницы), защита — выключенный по умолчанию
флаг и сверка `customerCode`/`merchantId` каждой операции.

## Фаза 2: сохранённая карта, автопополнение в RU, оплата в один клик (поправка 10.10.2026)

Решение владельца 10.10: «если человек вручную пополняет с уже привязанной картой/СБП — автоматом
после подтверждения спишем, не открывая платёжную страницу». Флаги: `TOCHKA_RECURRING_ENABLED`
(привязка карты в Точке), `BILLING_SAVED_METHOD_TOPUP_ENABLED` (один клик, оба эквайера),
`BILLING_AUTO_TOPUP_ENABLED` (как раньше, теперь и RUB). Все выключены по умолчанию.

### Привязка карты в Точке

- Пополнение картой с «сохранить карту» создаёт вместо ссылки **подписку без графика**:
  `POST /subscriptions_with_receipt`, `recurring: true`, без `Options`, без `saveCard` (иначе банк
  проводит только первое списание), с тем же чеком 54-ФЗ, `paymentLinkId` = id checkout,
  `consumerId` = id счёта. У подписки нет `ttl`: checkout истекает у нас, поздняя оплата всё равно
  зачисляется (один кредит на операцию). Только карта; СБП-привязка — фаза 3 (Pay Gateway).
- Подписка — та же платёжная операция (`GET /payments/{id}` и список операций её видят, проверено
  вживую): первая оплата зачисляется по старому пути с id операции, после оплаты в ней появляется
  `CofToken` (`cardType`, `maskedPan`) — по нему сохраняется карта `billing_payment_methods`
  (`provider_pm_id` = id подписки, бренд и последние 4 цифры).
- Отвязка: банк не меняет статус подписки без графика (`POST …/status` → 424 «Subscription not
  found», проверено вживую), поэтому «Удалить» отвязывает карту у нас и отзывает согласие; банк
  карту не забывает, но мы её больше не списываем.

### Списание без ключа идемпотентности

`Charge Subscription {amount}` отвечает только `result: bool` — без id платежа и причины отказа.
Каждое списание — новая запись `approval` в `Order[]` подписки (первая — оплата привязки, её
`ListCharges` не возвращает). Отсюда «сверяемое списание» для попыток:

1. под блокировкой счёта — одна попытка списания сохранённой картой на счёт (автопополнение и
   один клик в одной очереди `billing_autotopup_attempts`, `kind` auto/manual);
2. до запроса читаются списания подписки, снимок (`order_snapshot`) коммитится вместе с
   `dispatched` — до сетевого вызова;
3. запрос отправляется **один раз**; списание этой попытки — новая запись после снимка с той же
   суммой, ещё не записанная платежом (`{operationId}:charge:{orderId}`), зачисляется через inbox;
4. `result: false` без новой записи — отказ (`declined`); 4xx — отказ, ничего не списано;
   потерянный ответ — `unknown`: фон только читает `Order[]` (через 24 ч — ошибка в логе для
   оператора, через 7 дней — `not_found`), повтора нет; открытая попытка блокирует новые списания;
   поздняя запись не теряется (второе ревью, 10.10): раз в час фон 7 дней перечитывает `Order[]`
   закрытых отказом/`not_found` попыток (при отсутствии открытой) и зачисляет запись им
   (failed → succeeded), а перед каждым новым списанием карты запись после её сохранения без
   платежа в базе зачисляется как `import` — в снимок она не прячется;
5. 3-D Secure при списании по подписке нет (MIT): `requires_action` у Точки не бывает.
   Вебхук списания несёт id подписки — он перечитывает уже зачтённую оплату привязки и ничего не
   добавляет; списание находит диспетчер. После restore БД сверка автопополнения импортирует
   списания подписок, которых нет в базе.

`Registry.OffSession` допускает провайдера с `CapOffSession` и либо `CapIdempotentCharge` (Stripe:
повтор с тем же ключом), либо `CapReconcilableCharge` + `ChargeLister` (Точка); диспетчер
различает их по `Caps().SafeRetry()`. Провайдер фазы 3 (`tochkapay`, тоже `CapReconcilableCharge`) без `ChargeLister` сюда не
допускается: его списание находится по нашему `paymentUid` (= id попытки), и диспетчеру для него
нужен поиск по этому id вместо снимка — шаг включения фазы 3.

### Автопополнение RUB

Те же правила, что у Stripe: долг + 30 дней, ≤ 1 новой попытки в 24 ч, потолок владельца —
по умолчанию 50 000 ₽, максимум 500 000 ₽ (= лимит ручного пополнения), минимум списания 150 ₽.
Отказ — письмо владельцу и следующая попытка не раньше чем через 24 ч.

### Оплата в один клик (оба эквайера)

- `POST …/billing/saved-method-topups {payment_method_id, amount, request_id}`: та же проверка
  суммы, что у checkout; `request_id` + хеш тела (повтор — та же попытка, другое тело — 409);
  одна попытка в полёте на счёт (409 `BILLING_PAYMENT_PENDING`, в том числе при идущем
  автопополнении); 5 запросов в минуту на счёт. Ответ — состояние: `PROCESSING`,
  `REQUIRES_ACTION` (+ `action_url`), `SUCCEEDED` (`credited`), `FAILED` (+ код).
- Stripe подтверждает PaymentIntent **on-session** (`return_url`, без `off_session`): карта с 3-D
  Secure отвечает `requires_action` со страницей `next_action.redirect_to_url` (`hooks.stripe.com`),
  клиент открывает её в окне оплаты (ADR-0084) и опрашивает `GET …/saved-method-topups/{id}`,
  который перечитывает платёж; без подтверждения платёж отменяется через 30 мин. Отказ
  показывается в приложении, не письмом.
- Точка — тот же `Charge Subscription` и сверка, что у автопополнения.
- Платёж в истории — `PAYMENT_ORIGIN_SAVED_METHOD`. Суперадмин видит сохранённые карты счёта
  на странице счёта.

### Возвраты

Возврат платежа подписки (и привязки, и списаний) через API невозможен: `Refund` отвечает
`ErrNotSupported`, возврат сразу `needs_review`, оператор возвращает в интернет-банке.

### Живая проверка (владелец, перед включением `TOCHKA_RECURRING_ENABLED`)

10.10.2026 вживую проверены только формы: создание подписки без графика 2 ₽ (ответ как у ссылки,
`recurring: true`), чтение её как операции (`Order: []`, статус подписки `Preparing`), отказ смены
статуса (424). Оплата и списание — с владельцем: привязать карту на 2 ₽, списать 2 ₽, убедиться,
что (а) `CofToken` появился, (б) списание видно в `Order[]` как `approval` с суммой, (в) пришёл
вебхук и какой у него `operationId`, (г) банк прислал чек на списание (сумма, `paymentMethod`),
(д) возврат обоих платежей в интернет-банке виден в `Order[]`. Если (б) не подтвердится, фаза 2
остаётся выключенной: без записи в `Order[]` списание нельзя сверить.

## Последствия

- Ядро не менялось в денежной части: тот же inbox, один кредит на операцию, один `SELECT … FOR UPDATE`
  счёта, сеть вне транзакций. Добавлены: `CapReconcilableCharge`, `CapSuccessOnlyWebhooks`,
  `ErrNotSupported`, `CheckoutReq.ReceiptEmail`, миграция `00077_billing_tochka.sql`
  (настройки эквайеров, опрос checkout, `dispatched_at` возвратов).
- Цены RU — уже существующие версии `ru` (6 / 18 ₽ за место в сутки).
- Фаза 2 (выше): миграция `00078_billing_saved_method.sql` (вид попытки, снимок `Order[]`,
  `requires_action`, происхождение платежа `saved_method`). Вне фаз 1–2: привязка СБП через
  Pay Gateway (фаза 3, PCI/онбординг), счета для юрлиц.

## Проверки и открытые вопросы

- Вживую 10.10.2026 (боевой токен, без оплат): список клиентов/точек/операций, две ссылки 1 ₽ с одним
  `paymentLinkId` — вторая получила 424 «заказ … существует», ссылка истекла (`EXPIRED`) примерно через
  10 мин после `ttl=5`; неизвестная операция — 424 «Order not found». В ответе чтения позиция чека
  показана как `full_payment`, хотя отправлена `full_prepayment` — проверить на чеке живой оплаты.
- Оплата 1–2 ₽ и возврат — вместе с владельцем (шаги в PR): форма чека, `paymentType`, появление
  возврата в `Order[]`, приём карт не-МИР (тогда подпись «Карта МИР» можно расширить).
- АУСН «доходы» или «доходы минус расходы» — подтвердить у бухгалтера (`TOCHKA_TAX_SYSTEM`).

## Фаза 3: привязка СБП через Pay Gateway (2026-10-10)

Статус: **адаптер `providers/tochkapay` готов, выключен** (`BILLING_TOCHKA_SBP_BINDING_ENABLED=false`);
включение ждёт онбординга банка (ниже «Что просим у банка»).

### Что выяснили

- Рекуррентный СБП есть только в Pay Gateway («Приём платежей», OpenAPI `API Приёма платежей` 1.0,
  `https://enter.tochka.com/uapi/pay/v1.0/sites/{siteUid}/…`): УПК `qrcType=TOKEN` — привязка счёта без
  оплаты (или `DYNAMIC` + `paymentToken` — оплата с привязкой); результат — `GET …/sbp/qrc/{id}/tokenization/result`
  и вебхук `sbp-token-issued` / `sbp-token-declined` (токен + `memberId` банка плательщика); списание —
  `POST …/payments` с `paymentMethod.type=SBP_TOKEN`; возврат — `POST …/payments/{paymentUid}/refunds`.
  В Точка.API (платёжные ссылки) СБП-подписок нет: QR только `01`/`02` (статический/динамический),
  подписки — только карта (swagger и документация 10.10).
- Наш JWT платёжных ссылок **принимается** шлюзом: `GET` с несуществующим `siteUid` → 404
  `MERCHANT_SITE_NOT_FOUND`, не 401 (записано в `testdata`). Наши `merchantId`, `terminalId`, `customerCode`
  как `siteUid` — тоже 404. Блок — сайт, который заводит банк, а не доступ.
- PCI DSS: AOC требуется для «методов с передачей карточных данных» («Платёж через форму мерчанта»);
  УПК и СБП-токены карт не касаются. Вводная страница «Приём платежей» называет AOC без оговорок —
  нужно письменное подтверждение банка, что для SBP-only AOC не нужен.
- Подпись `Signature` (RSA-2048, SHA-256, PKCS#1 v1.5, base64 одной строкой) — только у создания
  платежа, подтверждения и возврата; публичный ключ (PEM, base64) передаётся банку при подключении.
- Тестовый контур настоящий: тестовый `siteUid`, ответы с `isTest=true`, сценарии в
  `paymentToken.tokenizationPurpose` (`createQrc`) и `comment` платежа (`payWithToken`).
- Ограничения: привязка счетов ИП и юрлиц недоступна (`SUBSCRIPTION_UNAVAILABLE`) — только физлица;
  API отзыва привязки и списка привязок нет (отзывает плательщик в своём банке; токен храним мы);
  **чеков 54-ФЗ в шлюзе нет** (в отличие от `payments_with_receipt`).

### Решение

1. Отдельный провайдер `tochkapay` (не часть `tochka`: другой продукт, сайт, подпись, статусы
   `WAITING/COMPLETED/DECLINED`, вебхуки). Возможности `CapOffSession | CapRefund | CapPartialRefund |
   CapReconcilableCharge`; без `CapHostedCheckout` (ручное пополнение остаётся на ссылках с чеком) и без
   `CapIdempotentCharge`.
2. `provider.AccountBinder` (`CreateBinding`, `GetBinding`), `Registry.Binder(market, currency, method)` и
   `provider.SBPBindingRow()` (RU, ₽, СБП, только автопополнение). Строка добавляется только с флагом;
   `BILLING_PROVIDERS` не меняется — рынок `ru` по-прежнему обслуживает `tochka`.
3. Наши id у банка: привязка = `merchantQrcId`, `paymentUid` = id попытки автопополнения, `refundUid` =
   id возврата, `customer.account` = id billing account, остальное — `metadata`.
4. Без слепых повторов: перед созданием платежа или возврата адаптер читает его по нашему id и не
   создаёт то, что банк уже знает; потерянный ответ — `ErrUnknownOutcome`, разрешается
   `GetPayment(paymentUid)`. Ответ банка на повтор `paymentUid` не документирован, поэтому
   `Registry.OffSession` допускает шлюз только вместе с диспетчером без повторов фазы 2 (как карту).
   Если банк подтвердит «повтор `paymentUid` → отказ, второго списания нет», можно заявить `CapIdempotentCharge`.
5. Режимы: `TOCHKA_PAY_LIVE=false` — любой ответ `isTest=false` → `ErrLivemodeForbidden` (токен боевого
   сайта к нам не попадёт); `true` — тестовый ответ → ошибка. Платёж или УПК без `isTest` — отказ в обоих
   режимах (fail closed). У результата привязки `isTest` нет: токен отдаётся только после чтения её УПК и
   проверки режима. Сценарии банка уходят только на тестовый сайт.
6. Вебхук `POST /api/billing/tochkapay/webhook`: RS256 JWT, тот же закреплённый ключ, что у Точка.API;
   `payment-updated` → `payment_*`, `refund-updated` → `refund_updated`, `sbp-token-issued` → `method_saved`
   **без токена** (токен берётся только из `GetBinding`), чужой сайт — `ignored`. Деньги — прежний путь:
   inbox перечитывает платёж, один кредит на `paymentUid`.
7. Ошибки: 404 `MERCHANT(_SITE)_NOT_FOUND` — ошибка конфигурации, а не «платежа нет»; 423, 429, 5xx —
   unknown; 400/403 (`SIGNATURE_VERIFICATION_ERROR` и др.) — окончательный отказ.
8. `server tochkapay pubkey` печатает ключ для банка; `server tochkapay smoke` на тестовом сайте проходит
   привязку, списание 1 ₽, повтор без второго списания и возврат — проверка допущений адаптера
   (404 результата до решения плательщика; отказ на повтор `merchantQrcId` / `paymentUid` / `refundUid`).

### Не сделано (после онбординга и фазы 2)

- Owner API и UI «Привязать СБП» (ссылка/QR, опрос `GetBinding`, запись в `billing_payment_methods`
  с `provider=tochkapay`, `kind=sbp`, `brand=memberId`, согласие на автопополнение) — после сохранённых
  методов фазы 2 на main.
- Диспетчер автопополнения для `CapReconcilableCharge` (фаза 2) — им же пойдёт СБП.
- Чеки 54-ФЗ на списания по токену (кассой банка или своей).

### Что просим у банка

Подключить «Приём платежей» (Pay Gateway) только для СБП: привязка счёта (УПК `TOKEN`) и оплата по
привязке (`SBP_TOKEN`), без карточных данных. Нужны: тестовый и боевой `siteUid`; регистрация нашего
публичного ключа подписи (и id ключа, если нужен); подтверждение, что для SBP-only AOC PCI DSS не
требуется; URL вебхуков `https://app.calab.io/api/billing/tochkapay/webhook`; ответ, принимается ли
действующий JWT для шлюза или нужен отдельный; ответ на повтор `paymentUid`; как фискализировать
списания по токену облачной кассой Точки (`digitalKassaTochka`); тариф СБП-списаний; лимиты.
